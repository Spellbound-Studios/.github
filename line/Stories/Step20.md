## The stories of step 20: the Navigation spike and the packing slice (NV1, PK)

Step 20 answers Navigation's one open question with numbers and gives Core the wire half that Networking waits on. Ten stories: NV1 five, PK five. The split is the plan's; the outcomes are the epics'. Facts are marked **verified** with the date or **verify before building on it**. Two repositories change: Core (into `dev`, in a worktree cut from `origin/dev`) and `.github` (into `main`, carrying this section and the spike's written result); the spike itself runs in `NavigationDev`, a Unity project outside every repository, and leaves nothing behind but its record.

Applies to every story of the step:

- **Rules:** the rules of steps 1 to 17 hold (spelled-out names, one type per file, explicit access modifiers, no comments or XML docs, logging through Core, the studio's Rider formatting, the copyright line on every new C# file; a gap is raised and stops the story; the lead never touches git beyond the worktrees the step names; nothing merges to a branch a game follows without the developer's hand). Core's runtime assembly depends on the engine modules only.
- **Rules:** packing is the save format, the wire format and WorldObjects' instance data, so a changed layout means re-save and no reader for an old layout is kept (rule 15); nothing in Core knows a connection or a player (rule 14); no value a game tunes is a constant; a hot path has a `_NoAllocation` test. `IPacker.Pack(ref Span<byte>)` and `Unpack(ref ReadOnlySpan<byte>)` keep their shape, because every consumer implements them (Switchboard, GeoForge, Saboteer's terrain and chalk, Corsairs' stores and modules, counted 2026-10-29); the step adds to the surface and removes only what no consumer calls.
- **Rules:** a spike is throwaway: it uses Burst, Collections and Mathematics and not Core, installs no Spellbound package, reads no checkout, touches no game and builds no package; its numbers are taken on the reference PC (AMD Ryzen 9 9950X3D, 16 cores, 63 GB) in the editor with Burst on, warm, the median of several runs, and the written result names the machine, the editor and the commit the data types came from.
- **Verified (2026-10-29):** Core `dev` is at 70f6b4e (step 17's merge). `Packer` is a static class over `Span<byte>` whose primitive reads and writes go through `BitConverter`, beside a parallel set of `*Bitwise` twins that no consumer outside Core calls (searched the workspace 2026-10-29: only `Packer.cs`, the benchmark sample and `PackerTests.cs` name them). `ToBytes`, `BuildPayload`, `PackListToBytes`, `PackArrayToBytes` and `SmartToBytes` each repeat one stack-then-rent loop with `StackBufferSize` 4,096 and `MaxRentedBuffer` 64 megabytes as constants and a static size hint. No read is bounded: a short payload throws from the span. There is no varint, no bit writer, no quantisation and no delta. `CoreKit.Packing.Describe` reflects a type's fields and reads no bytes. Step 17 counted 789 edit-mode tests (781 passed, 8 skipped for want of a graphics device) and 9 play-mode tests.
- **Verified (2026-10-29):** Switchboard's `MessagePacker` carries private `TryReadUInt`, `TryReadInt`, `TryReadULong`, `TryReadLong` and `TryReadString` over Core's throwing reads, and Saboteer's and Corsairs' `ChatNetwork` call its `TryUnpack` with the profile's maximum packed bytes (the raise of the Switchboard review fixes). They are the first callers of the decode limits and are not edited in this step.
- **Verified (2026-10-29):** GeoForge at `dev_1.0` (decc9c2, 2026-10-28) keeps a chunk's voxels as a run list, `NativeList<SparseVoxelData>` (a `VoxelData` of `sbyte Density` and `byte MaterialIndex` plus the index its run starts at), built by `DenseToSparseVoxelDataJob` in `GeoChunkEngine.SetVoxels` and read through `GetsSparseVoxelData()`; solid is a density of zero or more; a 128-voxel chunk is 131 data voxels a side (`ChunkDataWidthSize = ChunkSize + 3`), 2,248,091 voxels indexed `x + z * width + y * area`; `DensityRange` says whether a whole chunk is all above or all below zero; the package depends on Core, Entities, Mathematics, Burst and Collections. GeoForge's layout is moving in another session, so the spike reads the repository on GitHub at that commit and not the checkout.
- **Regression contract:** every byte today's `Packer` writes for the primitive, string, vector, quaternion, byte array, list, array and smart forms is the same byte after the step, proved by a golden byte test written before the first change; `TrySmartUnpack`, `SmartListFromBytes` and `AreBytesEqual` behave as before; `CoreKit.Packing.Describe` is unchanged; Switchboard's `MessagePacker` and both games' chat layers compile unchanged against the result (they call `Packer.Write*`, `Read*` and `BuildPayload`); WorldObjects' `DeltaResolver` path through `SmartToBytes` and `TrySmartUnpack` is unchanged; Core's edit-mode and play-mode suites pass; `packagecheck check` over Core fails no rule it passed before.
- **Regression contract:** no game and no package other than Core changes; GeoForge's checkout is not read.
- **Done, for each story:** compiles clean in the worktree or the spike project through the Unity command line, its tests pass, and the pull request's report lists what landed.

- **Outcome:** `NavigationDev`, a throwaway Unity 6000.4.8f1 project outside every repository, holds GeoForge's run-list representation copied from the GeoForge repository at `dev_1.0`: `VoxelData`, `SparseVoxelData`, `DenseToSparseVoxelDataJob`, `SparseToDenseVoxelDataJob` and the run binary search, with GeoForge's chunk layout and its Perlin terrain signed distance as the source of voxels, plus a cave variant that carves tunnels through the terrain so an open search has interior space; one chunk's run list at three seeds reports its run count beside its dense size.
- **Rules:** the types are copied from GitHub at the named commit and thrown away with the project; the spike installs no Spellbound package and reads no checkout.
- **Regression contract:** none; nothing of the developer's changes.
- **Done:** the project opens headless through the Unity command line, Burst compiles, and the run counts are in the written result.

### NV1-2 Tiles and bytes

- **Outcome:** a Burst job builds occupancy tiles from a chunk's run list: 16 by 16 by 16 cells with a one-corner border (17 cubed, 4,913 bits, 615 bytes of bits), one bit per corner from the sign of the density, and a tile that is all open or all solid stores a flag and no bits; measured: tile build time per chunk and per stored tile, bytes per stored tile, bytes per chunk and the stored tile count, each beside the plan's arithmetic (64 to 128 stored tiles and 39 to 79 kilobytes for a 128-voxel chunk against 4.5 megabytes dense).
- **Rules:** the build reads the run list, never a dense copy, because that is what the field will read from GeoForge's seam; times exclude the Burst compile.
- **Regression contract:** none.
- **Done:** the table per seed, terrain and cave, in the written result.

### NV1-3 The searches

- **Outcome:** cell classes from the eight corner bits (Open, Surface, Solid) and two Burst searches over the implicit graph of a chunk's tiles: a Surface search for a walker (a Surface cell with the cell above it open, its neighbours on the surface, a step and drop limit of one cell) and an Open search for a flier (Open cells, 26 neighbours), each an A* over a binary heap with a node budget; measured as nodes expanded per millisecond over random start and goal pairs, with the success rate, the path length, the expanded count and the memory the working sets hold at the budget beside it.
- **Rules:** the working sets are allocated once and reused; the cost is per node so the figure carries to the package's hierarchy, which the spike does not build.
- **Regression contract:** none.
- **Done:** the two figures with their distributions in the written result.

### NV1-4 The mixed-resolution seam

- **Outcome:** a refined region (a quarter of the ground cell, four fine cells per ground cell per axis) inside a box in the chunk, its fine occupancy resampled from the density by trilinear interpolation with a built shape rasterised into it conservatively; the ground level around it derived by the one rule (a coarse cell is blocked if any child is blocked, open only if all children are open, and a mixed cell is refined); a search that starts on the ground level, crosses into the region and leaves it; a soundness check that walks every edge of every found path against the finest data; and the moat matrix: a trench narrower than a ground cell inside the region stops a walker at the fine level and never reads as open at the coarse level.
- **Rules:** the seam joins a coarse cell to the fine cells on the shared face and never passes through a cell the rule calls mixed; no portal is modelled (a doorway is a link and links are NV4's).
- **Regression contract:** none.
- **Done:** the matrix of cases (open ground into open fine and back, the moat, a wall across the seam) with pass or fail per case and the count of unsound edges, which must be zero.

### NV1-5 The written go or no-go

- **Outcome:** the written result in this section with every number beside the arithmetic it replaces, judged against budgets stated before the numbers are read, and a Decision issue in the Roadmap repository that blocks NV2 with the question, the recommendation, the alternative and what waits.
- **Rules:** the budgets: the tiles of a 128-voxel chunk build within 8 ms on the reference PC (one worst frame of Corsairs' bar, because a chunk's tiles build once at load and rebuild per edit only where the edit's bounds intersect); a chunk's tiles hold within 200 kilobytes (under one twentieth of the dense array); the Surface and Open searches expand 1,000 nodes per millisecond or more (so a 10,000-node search is 10 ms, time sliced under a budget); and the seam matrix has zero unsound edges. A number outside its budget is a no-go unless the written result says why it is not. On a no-go the result says what NV2 onward re-size to.
- **Regression contract:** none.
- **Done:** the section, the Decision issue created by the hand-off script, and the developer closing it in writing.

### PK-1 Packing into a caller-owned or pooled buffer

- **Outcome:** `Packer.TryPack<T>(in T value, Span<byte> destination, out int written)` and `Packer.TryPack(PackWriter writer, Span<byte> destination, out int written)` pack into a buffer the caller owns and answer false with nothing counted when it is too small; `Packer.PackPooled<T>(in T value)` and `PackPooled(PackWriter writer)` return a `PooledPackedBytes` (a disposable holder over a rented array with `Bytes`, `Array`, `Length` and a `Dispose` that returns it) so a transport sends without a fresh array; `PackingLimits` (the stack buffer size and the largest payload, defaults 4,096 bytes and 64 megabytes) is a struct every allocating door takes as an optional last argument, `PackingLimits.Default` otherwise; the one stack-then-rent loop lives in one place; `CoreKit.Packing` gains `TryPack` and `PackPooled` beside `Describe`.
- **Rules:** the limits are parameters with defaults, never constants; the pool is `ArrayPool<byte>.Shared`, the runtime's own; the success path of `TryPack` allocates nothing.
- **Regression contract:** the step's; `ToBytes` and `BuildPayload` return the same bytes as before.
- **Done:** tests for a buffer that fits, one byte short, an empty destination, the pooled holder's bytes equal to `ToBytes`, a double dispose, the limits taken from the argument, `TryPack_NoAllocation`, and the golden byte test unchanged.

### PK-2 Decode limits

- **Outcome:** every read has a bounded twin that answers false and leaves the span where it was instead of throwing: `TryReadByte` through `TryReadQuaternion`, `TryReadString(ref buffer, out string, int maximumBytes)`, `TryReadBytes(ref buffer, out byte[], int maximumBytes)`, `TryUnpackArray<T>(ref buffer, int maximumCount, out T[])`, `TryUnpackList<T>`, and `TryUnpack<T>(ReadOnlySpan<byte> bytes, out T value)`, which also refuses trailing bytes; `DecodeLimits` (maximum string bytes, maximum byte run, maximum count, with defaults) for the forms that take one; `CoreKit.Packing.TryUnpack` beside `Describe`.
- **Rules:** a Try read never throws for any input and never advances on failure; a negative or over-limit length is a failure, not an exception; the throwing reads stay for bytes this build wrote itself. The report names Switchboard's `MessagePacker` and both games' `ChatNetwork` as the first callers; they are not edited here.
- **Regression contract:** the step's.
- **Done:** tests per primitive at a short buffer, the string and byte limits, a negative length, a count above the limit, trailing bytes refused, a message-shaped payload truncated at every length never throws, and `TryRead_NoAllocation`.

### PK-3 The bit writer with varints and quantisation

- **Outcome:** `BitWriter`, a ref struct over a `Span<byte>` (`WriteBits(uint, int bitCount)`, `WriteBits(ulong, int)`, `WriteBool`, `WriteVarUInt`, `WriteVarInt` by zig-zag, `WriteVarULong`, `WriteVarLong`, `WriteQuantized(float, in Quantization)`, `Align`, `BitsWritten`, `BytesWritten`, and a `TryWriteBits` that refuses what does not fit); `BitReader`, its mirror, every read a Try that fails at the end of the span; `Quantization`, a range and a bit count built by `Quantization.Linear(minimum, maximum, bitCount)` with `Quantize(float)`, `Dequantize(uint)` and `Step`; and byte-aligned varints on `Packer` (`WriteVarUInt`, `ReadVarUInt`, `TryReadVarUInt` with the signed and long forms) for length prefixes on the wire.
- **Rules:** bits go least significant first into little-endian bytes, written down in the tests as golden bytes; a varint is seven bits per byte with the high bit as continuation, so a reader can be checked against Protocol Buffers' and PurrNet's; a quantised value round-trips within half a step; nothing allocates.
- **Regression contract:** the step's; nothing that exists changes.
- **Done:** golden byte tests for bits, varints at every byte boundary (0, 127, 128, 16,383, 16,384, the maximum, the long forms), zig-zag at the negative extremes, quantisation at both ends of the range and the error bound over a sweep, bounded reads at every bit count, and `BitWriter_NoAllocation`.

### PK-4 Standard reads as fast as the bitwise path

- **Outcome:** the standard reads and writes are as fast as the bitwise ones and there is one path: the primitives go through `BinaryPrimitives` little-endian (a fixed layout on every platform, where `BitConverter` wrote the machine's order), the `*Bitwise` twins are deleted, the benchmark sample measures the one path, and an edit-mode test records the throughput of one million integer and float writes and reads as a measurement in the report, before and after.
- **Rules:** measure before changing (the `BitConverter` path against the bitwise path, warm, the median of several runs), then change, then measure again; the bytes on this machine do not change, proved by the golden byte test.
- **Regression contract:** the step's.
- **Done:** the before and after table in the report, the twins gone from the surface, and the tests that named them rewritten against the one path.

### PK-5 The pure delta pack and unpack

- **Outcome:** `DeltaPacker.Pack(ReadOnlySpan<byte> baseline, ReadOnlySpan<byte> current, Span<byte> destination, out int written)` writes the difference between two packed payloads as runs (a varint count of unchanged bytes, a varint count of changed bytes and those bytes, repeated to the end, then the current's tail when it is longer) and `DeltaPacker.TryUnpack(baseline, delta, destination, out written)` rebuilds the current from the baseline and the delta, refusing a delta that is malformed or does not fit; `DeltaPacker.LargestDeltaBytes(currentLength)` sizes a destination; `CoreKit.Packing.PackDelta` and `TryUnpackDelta` beside `Describe`. Pure: Core records nothing about what any peer holds; which baseline each player confirmed is Networking's (rule 14, NW6).
- **Rules:** the delta of a payload against itself is the smallest form; no allocation on either path; the format is written down in the tests as golden bytes; `TryUnpack` never throws.
- **Regression contract:** the step's.
- **Done:** tests for identical payloads, one changed byte, a changed run at the start, the middle and the end, a longer current, a shorter current, a thousand seeded random pairs round-tripped, a malformed delta refused, a destination too small refused, `DeltaPack_NoAllocation`, and the delta bytes of a 1,024-byte payload with eight changed bytes reported beside the full payload.

### The written result of the Navigation spike (NV1, 2026-10-29)

Run on this machine on 2026-10-29 in `NavigationDev`, a throwaway Unity 6000.4.8f1 project outside every repository (batch mode, no graphics, managed code in Debug, Burst 1.8.23 with safety checks off in the measured jobs, Collections 6.4.0 as the editor resolves it, Mathematics 1.3.2), on the reference PC (AMD Ryzen 9 9950X3D, 32 logical cores, 63 GB, 31 job workers, six other editors open). GeoForge's run-list types, its chunk layout and its Perlin terrain signed distance were copied from the GeoForge repository on GitHub at `dev_1.0` (decc9c2, 2026-10-28) and read from no checkout. Six chunks: three seeds of the plain terrain and three with three capsule tunnels cut through it. Every tile build was checked bit for bit against a build from the dense array, every found path was checked against the dense voxels, and the seam's soundness checker evaluates the trilinear field and the shapes itself and flagged five deliberately bad edges. The full tables and the raw logs are in `NavigationDev/ProbeOutput` on the reference PC; the spike code stays there and ships nowhere.

**The answer is go.** Every budget stated in NV1-5 before the numbers were read is met:

|---|---|---|
| The tiles of a 128-voxel chunk build within 8 ms | 0.75 to 0.99 ms on one thread by walking the run list, 0.12 to 0.19 ms over 64 slabs in parallel (median of 9 after a warm run); a binary search per corner, the other way of reading the run list, costs 49 to 54 ms on one thread and is not the way | none stated |

Facts the spike found that shape NV2 onward:

- **GeoForge's run list is large.** A 128-voxel chunk of the plain terrain is 131,000 to 132,000 runs (1.03 MB, 23.5 percent of the dense array) and 168,000 to 172,000 with caves (1.34 MB, 30 percent), because the signed-distance gradient of 32 leaves about eight voxels per column with distinct unsaturated densities and each is its own run. The tile build is linear in runs and stays under a millisecond, but W2a's run-list read hands Navigation a megabyte per chunk, not the tens of kilobytes the word "sparse" suggests.
- **The Open search's cost is expansions, not speed per node.** With the Euclidean heuristic the spike was asked for, A* under-estimates the 26-neighbour step cost and fills an ellipsoid around the straight line: 72 of 1,185 found paths needed more than 100,000 expansions. The same pairs with a 3D octile heuristic (exact for the step costs in empty space, admissible and consistent) expand 1,229 nodes a search on the terrain and 1,306 in the caves, with the same optimal costs; the eight remaining budget hits all have the goal in a tunnel and the start in the air above it. NV2 uses the octile heuristic from its first story, and the free-space octree of NV3 is what answers the tunnel case.
- **The node store.** A flat array over the chunk's cells with a generation stamp (no clear between searches) ran 9 to 25 percent faster than a hash map, which costs 0.12 to 0.30 ms to clear at a 1,048,576 capacity; the worst search touched 229,530 nodes, which fits a 262,144-slot map (6.3 MB) and a 1.2 MB heap per searching thread.
- **Where the surface sits against the tile layers decides the byte count more than the terrain's shape does.** A surface inside one 16-cell layer stores 64 tiles; one that straddles a layer boundary stores 84; each further layer a taller or steeper surface touches costs up to 64 tiles, about 39 KB.
- **The mixed-resolution rule as built.** The area text's rule says a coarse cell is blocked if any child is blocked, open only if all are open, and mixed is refined; applied to a walker, a ground cell that holds the ground surface always has solid children, so inside the refined region the walker uses fine nodes only, and the ground-level classes are open (all children open), blocked (all solid) and mixed (refined). The trench's ground cells read mixed, never open, under either reading. Seam edges join a coarse walkable cell outside the region to the walkable fine cells of the facing border layer within one metre of height, across the four side faces.
- **Corner-based classes block one cell of clearance beside a wall** (a cell sharing a wall's solid corners is not walkable), and rasterising a 0.5 m gap into fine corners instead of fine cells would close it; the fine level therefore keeps built shapes as per-cell overlays. That is the resolution ladder's rule for NV4.
- **GeoForge's `GetCoordByVoxelPosition` floors `(v - 1) / 128`**, so a chunk owns voxels 1 to 128 and the tile corners read voxels 1 to 129; the halo voxels 0 and 130 are never read. GeoForge's `PerlinTerrainDataFactory` adds its x and z offset twice (once as the chunk origin, once inside the noise sample); the spike reproduced it exactly, and it only shifts the noise.

Not measured: a player build (every figure is the batch editor's, Burst on, managed code in Debug); a search across a chunk border; more than one refined region; the speed of the mixed coarse-and-fine search and the time to build a refined region (both ran for soundness only); the fine data stored as corner bits (40,187 bytes is arithmetic, the spike stored one byte per fine cell); the 6000.3 floor row.

On the go, NV2 onward keep their sizes. The fallback left the plan on 2026-11-05 by the developer's decision of 2026-10-31.

The spike's NavMesh comparison figures are kept as evidence, a data point and not a decision, at Planning/PackageLine/Evidence/NavMeshComparison.md.

**Facts the step changed, both parts.** PK-4's story named `BinaryPrimitives` as the one path; measured first in the editor (Mono), it was slower than both existing paths (34 to 39 ms a column against 29 to 31 for `BitConverter` and 18 to 28 for the bitwise twins), so the one path is the bitwise one and the figures are in the Core pull request. The golden byte test, written on the base before the first change, exposed a latent defect in `SmartPackerRegistry`: Mono initialised its generic static cache when the calling method was compiled, re-entered the registry load and registered the first smart packer used outside play mode with hash 0; fixed in the same pull request. Collections resolved as the editor's built-in 6.4.0 whatever the manifest asked for.

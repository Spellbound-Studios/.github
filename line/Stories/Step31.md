### L8-5 List, Delete, FlushToDisk, the queued save of a store already saving, the durable record

### L8u-1 UpgradeRegistry, the step delegate, the chain at load, UpgradeAll and its job, Upgraded in the report

- **Outcome:** `public delegate void SectionUpgradeStep(ReadOnlySpan<byte> stored, Store target)`; `UpgradeRegistry` with `Add(sectionName, fromFingerprint, step)` (a second step for the same pair throws, naming it) and `TryGet(sectionName, fromFingerprint, out step)`; `Saves.Upgrades` is the registry a game fills at start. The chain at load: a record refused by name whose (name, stored fingerprint) has a step runs it with the record's bytes and the store; the step fills the current sections through `target.Section<T>()` (one, several or a renamed one) or hands an intermediate layout to `target.Offer(sectionName, layoutFingerprint, bytes)`, which Persistence reads as if from the file: the current fingerprint is unpacked, another fingerprint with a step runs the next step, and a fingerprint with no step leaves the section refused and reported with that fingerprint; a step that returns without throwing has upgraded its record, whatever it filled (so two old sections merged into one current section both count); a step that throws leaves the section refused with the exception's message as the reason, counts `persistence.load.upgrade_failures` (reason the section name), and leaves nothing behind (the sections it materialised are rolled back); a name the catalog no longer knows is offered to the registry under its old name before it counts as unknown, so a renamed section is upgraded by a step registered under the old name; `LoadResult.Upgraded` lists the names upgraded, and the next save writes the current layout, so with this door alone a player's save is upgraded the first time it is opened. `Saves.UpgradeAll(kind, observations)` returns an `UpgradeJob` (`Total`, `Done`, `Failed` as a list of `UpgradeFailure` with `Key` and `Reason`, `Completed`, `Completion`, `Advance()`): the job lists the kind through the storage when made (synchronously, as `Load` reads) and each `Advance` takes one store: loads it with the steps and, when `Upgraded` is not empty, saves it, advancing that save on the following calls until captured before the next store; a refused load or a failed save is a failure by key, and a store that still holds a refused section after the steps is not rewritten (a failure by key naming the section), so the job never drops bytes without the player opening the save; a store whose load lists an unknown section under the `Drop` policy is not rewritten either (nothing is dropped by the job), and a key whose queue holds a save still capturing is a failure by key naming it, so an upgrade run during an autosave never rewrites it with an upgraded stale copy;

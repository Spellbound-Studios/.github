## The answer in brief

- The developer's reading of the Entities code is a little short of the truth. Entities does five jobs in today's code, not one: it draws (Entities Graphics), it stores the instance rows the awaken and sleep job reads, it groups instances by chunk for bulk delete, it runs the per-second timer query, and it hosts WorldForge's generation driver, seed and layout and GeoForge's blob assets. Only the first is about draw calls.
- Unity's feature the developer called "BatchRendererGroup for GameObjects" is the GPU Resident Drawer. Both games already switch it on in their PC quality asset (`m_GPUResidentDrawerMode: 1`). It is the right tool for props that are GameObjects. It is the wrong tool for a world's trees held as data: it needs a Mesh Renderer on a GameObject per instance, and the 6000.4 manual itself sends data-driven cases to BatchRendererGroup ("Use the GPU Resident Drawer instead, except for advanced use cases").
- Verdict on the draw path (decided 2026-10-23): Instancing draws with Unity's BatchRendererGroup. No Entities, no Entities Graphics stopgap, no second method, no renderer of our own beyond the culling routine that BatchRendererGroup asks its caller for (Unity's own Resident Drawer and Entities Graphics both pass one: `InstanceCullingBatcher.cs:520-525`, `EntitiesGraphicsSystem.cs:1033`). That routine is decided (2026-10-24): skip by distance and view cone, pick the level by distance, no fade between levels and no occlusion culling at first. One measurement on the reference machine, against today's path, ends in a written go or no-go. I do not claim the path passes without that measurement.
- Verdict on the data: the instance rows become native columns inside WorldObjects. Nothing in the line needs Entities to store, query or wake an instance. That removes `com.unity.entities` from Core, GeoForge, WorldForge and Saboteer.
- Pooling is the clearest case of Unity shipping what we maintain: `UnityEngine.Pool` replaces Core's `ObjectPool`. Resources-folder registries are the second: Unity's manual discourages the folder for production and offers Preloaded Assets and Addressables.
- Unity's new animation system is paused (Unite 2025 roadmap, quoted on Unity's forum, 2025-11-21); nothing in the line waits for it. Domain reload is already off by default for new projects in 6.6, 6.7 LTS is "our final release built upon Mono" with an experimental CoreCLR player, and Unity 7.0 alpha (2026-10-05) is the first CoreCLR editor without domain reload; that puts static state, `AppDomain` scans and `DomainUnload` callbacks in our packages on a clock. Core packages, including the ECS ones, follow the editor: "You can't pick different versions of core packages for your version of the Unity Editor", which breaks any library that names Entities across the two LTS lines.
- Ten claims from other areas were answered on 2026-10-23 (section "Claims from other areas, answered"): none moves the line. Thirteen facts were read in the 6000.4 pages or the installed Pipeline package, and the importer, UI Toolkit, Mesh LOD, BatchRendererGroup, BakeMesh, Terrain and Project Auditor pages were read again on 6000.3 at checkpoint 3. Every instance entity carries two shared components, `PresetHashComponent` (40 values in Corsairs today) and `ChunkParentComponent` (one value per loaded chunk). Be careful with archetypes that have multiple shared component types ... susceptible to fragmentation" (`components-shared-optimize.md`), and it points to the Archetypes window to check chunk utilisation (the window exists in 6.4; Unity 6.5 removed it and moved the information to the Entities Profiler's Memory module, S32). ### Pooling: calling code

Before, a Core subclass per pooled type (`DecalProjectorPool.cs`, abridged), rented and returned:

```csharp
public sealed class DecalProjectorPool : ObjectPool<DecalProjector> {
    private readonly DecalProjector _prefab;
    private readonly Transform _parent;

    public DecalProjectorPool(DecalProjector prefab, Transform parent) {
        _prefab = prefab;
        _parent = parent;
    }

    protected override DecalProjector Create() {
        if (_prefab != null)
            return Object.Instantiate(_prefab, _parent);

        var host = new GameObject("DecalProjector");
        host.transform.SetParent(_parent, false);

        return host.AddComponent<DecalProjector>();
    }

    protected override void Reset(DecalProjector item) {
        if (item != null)
            item.gameObject.SetActive(false);
    }

    protected override void Discard(DecalProjector item) {
        if (item == null)
            return;

        if (Application.isPlaying)
            Object.Destroy(item.gameObject);
        else
            Object.DestroyImmediate(item.gameObject);
    }
}

var projector = pool.Rent();
pool.Return(projector);
```

After, Unity's pool configured where it is built, no subclass; the three overrides become the three delegates the constructor takes:

### The store and the awakening: the contract

WorldObjects keeps one set of columns per partition. A partition is a reference frame and a cell of that reference frame: the default reference frame is the world, so a world partition is the region the line already names, and a reference frame such as a ship or a cart owns its own partitions. A row's pose is local to its partition's reference frame. The awaken and sleep job reads the columns in place.

```csharp

    public NativeList<quaternion> Rotations;
```

The reference frame is the partition's key and not a column, so a row costs the same whichever reference frame it rides: about 47 bytes (12 + 16 + 4 + 2 + 8 + 1 + 2 + 2 across separate columns, computed; the 8 is the 64-bit `InstanceId`, a lease Core defines and Networking allocates, so a row leaving one region and arriving in another keeps its id), against 52 bytes copied per instance per query today, and the per-preset radii live in a table indexed by `PresetIndices`. `ReferenceFrameId` and the pose conversion are Core's reference frame vocabulary (Line, Core section; `ReferenceFramePose.ToLocal` and `ToWorld`, Runtime.md); the reference frame binding is not Core's, it lives in Character.Body, and the store reads a reference frame's pose through the reference frame noun only. `ReferenceFrameId` zero is the world (Runtime.md:212), so a world partition is the partition whose key carries the default reference frame.

**A reference frame moves, its rows do not.** Take a cart carrying crop crates, or a submarine carrying placed supplies. The crates are rows of the reference frame's partition with poses local to the cart. When the cart moves, the store reads one pose from the cart's `IReferenceFrame` per tick and writes nothing to any row, so a moving reference frame costs one pose read and no region move. The reference frame's partitions are listed in the world's interest as one entry each, from the reference frame's bounds (the reference frame's world pose and the partition's local bounds), so a travelling ship never moves a row between world regions and never dirties a world region's replication hub. Replication of a reference frame's rows is area 6's. The contract this area states is that a reference frame partition has a stable key (its `ReferenceFrameId`), that its rows change only when something is placed, removed or moved on the reference frame, and that the reference frame's own pose travels as the reference frame owner's data through the reference frame map Networking already holds (Networking.md).

- **Loading and unloading.** `Reparent(instance, referenceFrame)` removes the row from its partition and appends it to the other, converting the pose with `ReferenceFramePose` at the current tick. It happens when something is placed on a deck or lifted off it, never per tick. It dirties the two partitions it touches, once each.
- **Waking.** Viewers come from Core's `IViewerSource` and its default `ViewerRegistry` and from nothing else. The registry is the world instance's own, one per world instance and never static, and the store reads the registry of the world instance that owns it (Networking's claim of 2026-10-24: the streamer fills that same instance). A viewer that crosses to another world is removed from one registry and listed in the other, and the store releases everything that viewer held on `Removed`. The registry raises `Moved` after the gate it owns (default 4 m, Networking.md). On each `Moved` the store turns the viewer's world position into the partition's local space and compares it with the position last evaluated there, so a viewer standing on a sailing ship fires `Moved` in world space and triggers no evaluation against the ship's rows. A reference frame that moves past the gate re-evaluates the viewers listed for it, in local space. The transform is rigid: a reference frame with a non-unit scale is a validation error, because a radius would no longer be a radius.
- **Drawing.** An `InstanceBatch` of a reference frame partition carries the reference frame's pose. How the batch path applies a pose to a whole batch (a matrix composed on upload, or a per-instance transform rewritten) is not documented in the pages I read and is a measurement case in U3, sequence S5: 500 crates on a moving cart.
- **Who steps the scene.** The store, the awakening job and proxy creation assume nothing about who steps a scene. The world instance's driver steps a world's own physics scene and leaves a scene that holds a `PredictionManager` alone (decided 2026-10-24: PurrDiction's manager steps a predicted world's physics); proxies are made in the world's scene either way, and the job reads rows and viewer positions and never the physics step. U4a tests the store against a scene its test steps itself and against a scene nothing steps.
- **Presenting.** A proxy of a framed row is created as a child of the reference frame's host object when the reference frame registered one (Character.Body's reference frame sources are components on a transform), so its physics rides the reference frame as a rider's does. Without a registered host it is created in the world and the module that needs it follows the reference frame. This is a presenter default, not a store concern.

**Waking is incremental, per moving viewer.** Each partition keeps one grid of cells per radius band, built once when the partition fills and updated when a row is added, removed or moved. A band is the presets whose awaken radii lie within a factor of two of each other (a policy field, `AwakeningBandRatio`, default 2), and its cell edge is the largest awaken radius in the band. A field of 3 m crops and a 60 m windmill are two bands with two grids, so a crop is never searched through a 60 m cell. Each (viewer, partition) pair keeps the rows that viewer holds awake: a list and a bit per row. A row's `ViewerCounts` is the number of viewers holding it, and a row is awake while the count is above zero. When a viewer moves past the gate in the partition's reference frame:

1. Release. For each row the viewer holds, if the row is beyond its preset's sleep radius, clear the bit and lower the count; a count that reaches zero puts the row on the sleep list.
2. Acquire. For each band, for each cell of that band's grid the awaken sphere around the new position touches (up to three cells along each axis, so at most 27 in 3D and 9 in 2D per band, because the sphere is two radii wide and the edge is one), for each row not already held, if it is inside its preset's awaken radius, set the bit and raise the count; a count that rises from zero puts the row on the awaken list.

The cost of one evaluation is the rows the viewer holds plus the rows in the cells its sphere touches, summed over the bands. It does not depend on how many rows the partition has elsewhere, on viewers that did not move, or on how many viewers are listed. A viewer that arrives acquires, one that leaves releases everything it holds, and a row created later is tested once against the viewers listed for its partition (a cost of creation, not of every tick). The job writes two lists, to awaken and to sleep, and uses no hash set. Bulk delete is releasing a partition. The per-second timer pass walks the rows whose `Flags` carry the timer bit, in the awake partitions only. The bits of a viewer cost rows divided by 8 bytes per listed partition: 10,000 rows is 1.25 KB per viewer, 250 KB for 200 viewers in one region, computed.

The policy exposes the cell edge and a cap on evaluations per tick; the movement gate belongs to the viewer registry, so GeoForge's chunk interest and this job never disagree about when a viewer moved. A viewer past the cap waits for the next tick, which raises awakening latency and never changes the result. The cap is reported when it bites (below), so an operator sees it before a player does.

The arithmetic the design is held to, with its assumptions stated. Today's job loops every viewer for every instance (`EventSurfaceProximityJob.cs:41-62`). My first draft binned viewers into regions, which bounds which viewers are checked and not how many rows, so it still cost the rows of a region times the viewers listed there: 10,000 rows x 20 viewers x up to 8 regions is 1.6 million distance tests in a tick, against the 0.4 ms budget the line's own example sets (Runtime.md, `worldobjects.index.awaken_job`). With the incremental form, take a ship under a crew of 20 sailing at 8 m/s past a 4 m gate. Each viewer crosses the gate about every 0.5 s, 25 fixed steps at 50 a second (the starting value of a setting, assumed by the arithmetic; nothing is derived from it), so on average under one viewer is evaluated per tick. Assume, for the arithmetic only, 10,000 rows spread evenly over a 256 m square 2D region and an awaken radius of 50 m: the cells are 50 m, a sphere touches up to nine, which is 22,500 square metres of the 65,536, so about 34 percent of the rows, 3,400, are tested per evaluation, plus the rows held. That is on the order of a few thousand distance tests per tick, against 1.6 million. I got the first figure wrong: I had counted four cells for a sphere that spans three along each axis, and the earlier 1,600 and 16 percent were too low by half. The assumptions are mine (region size and density are fixed by no area) and the benchmark replaces them. The bands exist because one grid sized to the largest radius makes a small radius pay for the largest: 3 m crops beside one 60 m building would test about 400 times the area they need (the ratio of the two radii, squared, in 2D). The mixed case is a benchmark case of its own (U4, below).

The case that does not shrink is density: 200 players in one town whose 10,000 rows sit in the cells the players stand in. A walking player (5 m/s) crosses the gate every 40 ticks, so about five evaluations a tick of up to 10,000 rows, 50,000 tests. 200 players all sprinting in step would be 2 million, which is exactly what the evaluation cap and the benchmark's third case exist for. I do not claim either fits the 0.4 ms budget; U4 measures it.

What is internal and what is public: the columns are `internal`; Instancing, Navigation and Networking read a public read-only view of a partition (`PartitionRows`) through their bridges. Whether the columns are `NativeList` or `NativeArray` per fixed-size partition is a detail of epic U4a that its first story measures. `NativeList` is Unity.Collections, so WorldObjects declares Burst, Collections and Mathematics as packages at the floor.

**State per row, for doors.** `States` holds one `ushort` per row, whose meaning the preset defines (a door's open and closed are two values). `WorldObjects` writes it through one call that also raises the partition's version number, and `PartitionRows` exposes it read-only beside preset index, pose and flags, for asleep and awake rows alike. Navigation therefore reads a door's state without a proxy, and its tile version moves when a state changes. Pathfinding.md calls this view `RegionRows`; the name here is `PartitionRows` because a reference frame's partition is not a region, and Pathfinding's file follows (claim in the result).

**Proxies in every build.** A proxy is a collider and logic with no renderer (`tree_es.prefab`), so the store, the awakening job and proxy creation run in every build, the dedicated server included. The picture is only ever a batch, and Instancing compiles under `!UNITY_SERVER`. The one drawn GameObject a preset can spawn (a falling tree, an animated prop) is created behind the same define. This is the collision and picture split GeoForge's presenter has, and it is smaller here because the proxy never held the picture; the proxy factory itself is the WorldObjects pitch's.

## Directions

**A. Quarantine Entities inside the line (rejected).** Move `ECS` and `EntityPrefabRegistry` out of Core into `WorldObjects.Entities` and `Instancing.Entities` and keep one entity per instance as both store and picture. It is an alternative to removing Entities from the contract. Rejected because the data store would still sit on an API that now moves with the editor (ECS packages track the editor from 6.4; Journaling deprecated in 6.5, managed components and multi-playback deprecated in 6.6, S9), because a dedicated server with no drawing would still compile Entities, and because Saboteer would still reach Entities through GeoForge's blobs. Nothing of it survives: no Entities method and no Entities Graphics stopgap (the developer, 2026-10-23).

**B. Native columns and Instancing over BatchRendererGroup (taken).** The store is columns in WorldObjects; the picture goes through `IInstanceDrawMethod`, whose one shipped method is Unity's BatchRendererGroup; one measurement gates it; Entities is nowhere.

**C. GameObjects and the Resident Drawer for everything (rejected).** One GameObject with a Mesh Renderer, a collider and logic per instance in every loaded region; Unity's drawer batches them; delete the store and our drawer. It is an alternative to B's store and seam, and it is the shortest code. Rejected as the only path for four reasons found in the documentation and the code: the Resident Drawer's rules exclude renderers with `MaterialPropertyBlock`, animator hierarchies and per-instance callbacks (S1); a sleeping instance would still cost a GameObject, so "asleep costs nothing" is lost, and that is the property that lets a server hold regions it does not simulate; a dedicated server (the MMO) needs rows with no GameObject at all; and the manual does not say what 20,000 runtime-created renderers cost (S1 says only "If you change or create GameObjects each frame, the GPU Resident Drawer updates with the changes"). It is not shipped. It was the alternative of the question the developer answered on 2026-10-24 (no, Instancing holds the culling routine), because it is where cross-fade between levels of detail and occlusion culling come from.

**D. GPU-driven everything (Beyond the brief, not proposed).** Instance data in one graphics buffer, compute culling, indirect draws, impostors for far trees, one path from grass to the horizon. It needs shaders written for indirect draw arguments (`Graphics.RenderMeshIndirect` page, S7) and gives up the URP Lit through DOTS instancing that B's batch renderer keeps. It is the right next step if the bakeoff shows the CPU side of B's batch renderer is the limit; the seam is where it would plug in.

### Beyond the brief (not proposed)

- **Show the ledger to buyers.** Each package's store page and the Spellbound window say which Unity systems it builds on and which it replaced, with the judged version. It is a trust feature and a forcing function; it costs a public promise to keep rows current.
- **A forest to the horizon from one buffer** (direction D): compute culling, indirect draws and impostors, with Horizon handing the far trees to the same drawer. It is the boldest version of this area and is held back only by shader work and the missing measurement.

## The answer in four lines

1. The hard problems are not four bugs, they are one shape: a body or a stack of items whose truth changes owner (animation to physics, ground to ship, container to container, client to authority), and every bug lives at a handover. The reusable asset is therefore a small number of handover mechanisms plus a way to see them, not a package of fixes.
2. Five mechanisms, each in the package that already owns its noun: **observations with a flight recorder and guards** (Core, collected by Diagnostics), **reference frames** (Core holds the noun; Character.Body holds the binding and rides), **motion claims** (Character.Body), **containment** (Character.Body, with a GeoForge bridge), **inventory transactions** (Inventory). Under them sits the **simulation vocabulary** the line gave this area (a tick, a seeded stream, an identity allocation seam, all in Core), which every guard, binding and recorder window below is expressed in, so a simulation assembly has no use for `Time.time` or `UnityEngine.Random`.
3. A written doctrine of seven rules, each enforced by a check area 7 owns, so a seventh game cannot reintroduce the bugs.
4. One acceptance test the whole area is built to pass: the scenario of `Areas.md` as a play-mode soak that fails when any guard fires.

## The scenario, walked under the design

A crew member on a Corsairs ship loots a chest, is knocked into a ragdoll, and lands on terrain. Step by step, with what the design does at each:

| Step | What happens | Mechanism that handles it | What is recorded |
|---|---|---|---|
| 1. Boards the ship | The player's `ReferenceFrameRider` probes along the up direction every fixed step (Core's up provider, world up by default), finds a collider whose parent implements `IReferenceFrame`, and hands it to a `ReferenceFrameBinding` (Character.Body), which holds the frame for 0.5 s after the last sighting so a hop does not unbind | Reference frame binding | `character.reference_frame.bound`: subject, reference frame id, tick |
| 2. The ship moves | A simulated reference frame (server-simulated hull) is synced by PurrNet; the rider is synced relative to it (`SetSoftParent`, `NetworkRigidbodyBase.cs:1557`, velocities relative to the parent). Reference reference frames move before riders in the fixed step (execution order set on the components) | `Character.Networking` bridge, which targets the protocol assembly `Spellbound.Networking.Replication`, maps reference frame id to the network identity | nothing per step; a counter `character.reference_frame.parent_mismatch` if the owner says "riding" and the copy is not parented |
| 3. Loots a chest | One `InventoryTransaction` moves the stack, all or nothing, with the intent key checked against Core's `IntentLedger`. Whoever may write both containers commits it: in an owner-authoritative game a player's own container changes at once on the owner and replicates from there, and in a game that keeps a server as the writer the client sends the intent and the server commits. A second delivery of the same intent returns the first receipt. | 4. Knocked down | Ragdoll takes a claim on the body's `MotionClaims`; the body's current driver (walking, in the Character sample) is suspended with a handoff (world pose, world velocity, bound reference frame, up). The hips keep the ship as their reference frame | Motion claims, ragdoll driver | `character.motion.claimed`: driver id, priority, tick |
| 5. Leaves the ship | The ship moves away; the binding releases after its hysteresis; the world velocity at release is relative velocity plus the reference frame's velocity at that point, so the fall continues the ship's motion | Reference frame binding | `character.reference_frame.released`: reason, tick |
| 6. Falls toward terrain not yet built | The `SupportGate` asks the containment space whether a collider exists under the body. Not ready: the body takes a hold claim (kinematic, no gravity) until it is ready or a timeout trips the guard | Containment, GeoForge bridge reading chunk mesh readiness | `character.support.held`: seconds waited. A timeout is a guard trip |
| 7. ## After

### The front doors

One front door per mechanism, each with a one-line use.

**Observations (Core).** Declared once per package as static fields that hold a key and a description and nothing else, reported with one call against a context the world instance owns (an `ObservationContext`: the counters, gauges, costs, budgets, quality levels, recorder and guard state of one world). Two worlds on a shard are two contexts, so a reading, a budget or a repair backoff of one never reaches the other:

```csharp
public static class CharacterObservations {
    public static readonly Counter Rescues = CoreKit.Observations.Counter("character.containment.rescues",
        "A body was moved out of terrain or back above the world. Read the reason.");
    public static readonly Occurrence ReferenceFrameBound = CoreKit.Observations.Occurrence("character.reference_frame.bound",
        "A body started riding a moving reference frame.");
}

CharacterObservations.Rescues.Add(context, reasonId);
CharacterObservations.ReferenceFrameBound.Record(context, subjectId, referenceFrameId.Value, tick);
```

A world instance creates its context and hands it to the mechanisms that report (`CoreKit.Observations.CreateContext(worldName, settings)`). One rule covers every front door of every package that reports: it takes the context as an explicit argument, the last one, and never looks one up. A game with no world instance creates one context at start and passes the same one to every front door it calls, so one `SetQualityLevel` and one budget reach all of them:

```csharp
var context = CoreKit.Observations.CreateContext("race", observationSettings);
var drawer = InstancingKit.CreateDrawer(settings, visuals, context);
var sky = HorizonKit.Create(horizonSettings, context);
context.SetQualityLevel("instancing.draw", 2);
```

A game that does not want the readings passes `ObservationContext.Discard`, one immutable instance that records nothing and holds no state. Core keeps no default context that records and no static reading, so a simulation assembly has nothing static to mutate, and a racing game that installs the drawing packages and no WorldObjects routes their costs to Diagnostics through the context it made. The package check (area 7) reads `Declared()` and fails a package that declares a key and has a front door with no context parameter. The calling code of Instancing, Horizon and Volumetrics follows the rule, and so do the doors of UI and Switchboard: `UIKit.Views`, `SwitchboardKit.Connect`, `SwitchboardKit.Host` and the `TextLog` constructor each take the context last. Those are claims on their owners, answered below. A package's static field is an immutable key, which is what the line's rule on static mutable state (Living C12) allows; the registry that maps a key to its declaration is append-only inside Core, not inside the simulation assembly. Diagnostics reads every live context through `ObservationContexts.All` (Core's list of contexts, added to on create and removed on dispose, never read by a simulation assembly), and every reading and every operation names its world: `core observations --world <name>`.

Four kinds exist and no more: `Counter` (only goes up), `Occurrence` (one record in the recorder), `Gauge` (a current value, such as rows awake) and `Cost` (a measured amount with a unit, a budget and a quality level, such as awakening job milliseconds). A rate (awakenings per second) is derived by the collector from a counter and never declared. Everything is readable as a plain struct, so a bound row, a probe and a package check read the same thing:

```csharp
public readonly struct ObservationReading {
    public readonly ObservationKey Key;
    public readonly ObservationKind Kind;
    public readonly double Value;
    public readonly double Budget;
    public readonly int QualityLevel;
    public readonly ObservationUnit Unit;
    public readonly uint Version;
}

int count = context.Read("worldobjects", readings);
uint packageVersion = context.PackageVersion("worldobjects");
IReadOnlyList<ObservationDeclaration> declared = CoreKit.Observations.Declared();

`Read` fills a caller-owned list without allocating. A key that changes every frame, such as instances visible after culling, therefore costs one format per refresh and not one per frame: with 120 open rows that is 120 x 4 = 480 label updates a second against 120 x 60 = 7,200 at 60 frames a second (computed, not measured). `Declared` lists every key with kind, unit, description and default budget from the declarations alone with nothing running; that is what the package check (area 7) reads to enforce one observation per package and a budget on each in a package whose sentence has a hot loop. A budget is a default in the declaration and a value the consumer overrides in `ObservationSettings` or by `SetBudget` on a context; a quality level is a number the consumer sets, and the declaring package decides what it means. Keys are `package.subject.name`, so the names other areas proposed (`worldobjects.region.rows`, `instancing.visible`, `navigation.tiles.built`, `networking.flush.bytes`) fit unchanged. Core's operation host declares a `Cost` per operation group, so the call count and duration of every operation is a reading with no code in the package. A label such as Instancing's active method is a Gauge whose value is a registered reason name, so a dump prints the word. A hot-path package ships a probe: an operation (area 2) that runs a fixed workload and returns `CoreKit.Observations.Read` as a snapshot in Core-packed bytes, which the line tier compares with the budget and with the last release's snapshot on the same machine; `CoreKit.Observations.Compare(a, b)` returns the ratio per key.

The description is a required argument: it is what `core observations` prints for an agent and what the black box window shows a designer. A reason is a name registered once through Core's hash registry (`CoreKit.Observations.Reason("embedded")`), so a dump prints `embedded` and not a number. **A guard (Core).** A named invariant with the repair backoff `BaseFloater` hand-wrote:

`Check` increments the counter, writes the occurrence with the preceding window flagged for the dump, and applies the policy: three repairs inside two seconds returns `Hold` for five seconds, the numbers `BaseFloater` serializes today, as fields of a `GuardPolicy` asset. The policy is the guard's; the state is the context's, kept per (guard, subject): a window start, a repair count and a hold-until tick, 8 + 4 + 8 = 20 bytes, 32 with an 8-byte key and padding. An entry exists only for a subject that has failed a check inside its window and is dropped when the window passes, so five thousand healthy bodies cost nothing and five thousand failing ones cost 5,000 x 32 = 160,000 bytes in that world (computed). Body 1 of world A and body 1 of world B are different entries because their contexts differ, and three bodies failing together never put a fourth on `Hold`. `Tick` is a count of steps the host advances: Core owns the type, the host owns the clock, so a server, a test and a recording drive it alike. It is 64 bits and needs no wrap-safe comparison: at the games' starting 20 ticks a second, 2^64 steps last 18,446,744,073,709,551,616 / 20 = 9.22 x 10^17 s, about 2.9 x 10^10 years (1.2 x 10^10 at 50 a second), so no shard, save or ban expiry reaches the end and a plain comparison is correct for the life of a world. The 32-bit form drafted first (about 2.7 years, and a wrap-safe comparison valid only over half of that, about 1.36 years) is gone; it would have made every saved timer wrong in an MMO that runs a year. A tick stored in memory costs 8 bytes instead of 4; the one place a 4-byte tick is kept, a recorder cell, keeps the low 32 bits and is session-local (below). Where the tick and its rate come from is one seam, `ITickSource`, which answers the current `Tick` and the `TickRate` the ticks are counted at, and which a `TickClock` reads once per fixed step. `TickClock` is Core's: a plain class holding the current `Tick`, with `Stepped(tick)` and the hold rule below, and a small driver component Core adds to a hidden object (earliest execution order advances the tick, latest raises `Stepped`). A game with no world instance starts one with one call, `CoreKit.Time.StartClock(source)` (or `StartClock(TickRate.PerSecond(20))`, which builds the default source at that rate), and a world instance starts one per world the same way, so the farming sim's crop timer and the card game's turn timeout advance on the same clock a shard uses. The rate is a setting that lives in one place and is read once when the clock starts: the clock owns no rate of its own and takes it from its source. In a game with no network that place is the default source's setting; with PurrNet it is PurrNet's `NetworkManager` tick rate, and the game keeps no second copy, so the two cannot disagree. Nothing in this area is derived from the rate or from the fixed step: the games start at PurrNet's 20 ticks a second and Unity's 50 fixed steps a second, two cadences, and changing either changes no code. Whoever needs the clock is handed it: Networking's `ServerClock`, its event link and its schedule take the `TickClock` through their constructors, none creates one and none calls `StartClock`, which the game (or a world instance) calls once; the intent ledger stays a plain class a game creates. The default, `GameTimeTickSource`, holds its rate as a setting (starting value 20 a second) and adds the length of each fixed step to a total of elapsed game time; its tick is the whole ticks in that total. The fixed step only measures elapsed time here: the tick is not a count of fixed steps, so a game with no network changes the tick rate or the fixed step alone and installs nothing else. The total is kept in whole microseconds (the fixed step rounded to the nearest), because a step held as a float is not exact: 0.02 as a float is 0.0199999995529651641845703125, fifty of them sum to 0.99999997764825820922 s, and at 20 ticks a second that reads 19 ticks where a second has passed (computed). R0 asserts that 50 steps at the starting values give exactly 20 ticks and 600 s give 12,000, and repeats it with the fixed step at 0.01 s and at 0.025 s. The source follows the steps that Unity runs, so it stops where fixed steps stop (a time scale of 0 stops physics, `Line.md` Limits) while PurrNet's source keeps counting on wall time (`Networking.md`, "One clock"); R0 runs it at a time scale of 0 and records what it does. The clock reads the source's rate once at start and every seconds-to-ticks conversion (`TickRate.FromSeconds`, the ledger's grace time, a timed modifier set, a restored duration) goes through that one value. If a source later reports another rate, the guard `core.clock.rate_changed` trips and shows in the observations, so a rate edited behind the clock's back is a number and not a silent drift. A source that answers the tick it answered before leaves the clock where it is (with PurrNet at the games' rates that is the normal case, 2.5 fixed steps to a tick, computed); a source that answers lower holds the clock, which never goes backwards, and the held step is counted under `core.clock.held`.

What time survives a save and a restart. A save holds no tick rate and no tick: every duration in a saved section is written in seconds, as a 64-bit float, and converted to ticks at load through the `TickRate` of the world that loads it, so a world saved at 30 steps a second loads at 50 and nothing is refused for a rate. `TickSpan` is an in-memory type and no saved section holds one, nor a `Tick`, nor a rate; the package check fails a section field of those types (a claim on living). The world instance, which owns the clock, writes the world's elapsed time in seconds into the world's section (WorldObjects owns that section; instance data, timers and the elapsed time sit in one section, so a timer stored as an absolute time and the time it is compared with are always restored together). World time is not a second counter: it is the seconds restored from the save plus the ticks advanced since the load times `StepSeconds`, so the one tick the host advances is the only clock. A crop planted at 1,000 s that matures at 1,000 + 86,400 s has the same remaining time after a weekly restart. A section that lives outside a world instance (a player's timed modifier set, kept with the player) writes the seconds that remain, and the loader converts them to a span from the current tick. Computed: a 64-bit float has 53 mantissa bits; a year is 31,536,000 s and needs 25 of them, which leaves 28 fraction bits, a resolution of 2^-28 = 3.7 x 10^-9 s, far below one 0.02 s step. The conversion rounds to the nearest tick and never turns a duration above zero into zero ticks, so a timer is off by at most half a step of the loading rate; R0's round trip test states that bound. Time while the process was not running is not simulated, so growth resumes where it stopped; the section also records the wall-clock UTC seconds of the save, and a game that wants crops to grow offline reads it and advances the world by a catch-up it chooses, which is a value and the game's. Two things are session-local and never saved: the recorder's ticks (32 bits, a 10-second window) and the guards' window state (rebuilt empty on load). Core's tick is PurrNet's tick when PurrNet is present, not a second clock: with PurrNet installed, Networking's `PurrNetTickSource` answers the seam from PurrNet's tick plus a constant per-world epoch (the restored tick minus the synced tick, zero for a new world). The restored tick is computed at load from the saved elapsed seconds through the loading world's `TickRate`, so the save still holds no tick and no rate; the epoch is the one place that number is used. `ServerClock` keeps no offset of its own, and a joining client is handed the world's elapsed seconds and converts them at its own rate (claims on networking, answered below). Every saved section carries a header with its name, its layout fingerprint and its length (developer, 2026-10-24; Persistence's, with the old layout refused by name and no compatibility path before a package ships to customers). The fingerprint is a hash of the layout description that Core's packing exposes from one function (`CoreKit.Packing.Describe(type)`, ordered field names and types as text), which both the surface writer and a saved section's header call (Living's claim, accepted), so a section type whose layout changed is detected without a second source of truth. `persistence inspect` prints each section's name, fingerprint and length, and an old layout is refused by name as `failed:`; a save upgrade, if one is built, is named in the Persistence pitch in the one grammar (a start and status pair if it can outlast a reload) and this area names none. UI's layout section and Switchboard's settings section carry the same header and no rate. `SeededStream` is Core's own code and takes a 64-bit seed (SplitMix64 seeds the state, xoshiro256** draws; both are published generators), because Unity.Mathematics is a package on 6.3 LTS and a built-in module only from 6.5, so Core on the engine alone cannot use its `Random` at a 6000.3 floor. `Fork(key)` gives a child stream per region or object whose values do not depend on what other streams drew, which generation needs. Its golden vectors are fixed by tests; its statistical quality is not measured, and its first story runs a published test battery. `InstanceId` is a 64-bit opaque value, area 6's layout: a kind bit (a placement id, derived by the caller, has it set), a 31-bit lease and a 32-bit counter, never reused. Callers see equality, packing and `LeaseOf`, never the bits. `IIdentityAllocator.Allocate()` takes no argument because its only scope is the world that owns it; the 32-bit id per scope key of the first draft is retired. The default `LocalIdentityAllocator` belongs to a world instance (never static) and takes its leases from a local issuer of the same shape, whose next lease is one number saved in a section beside the world's others; Networking supplies the authority's allocator over its lease table. The value zero is never issued and means no instance (a claim on area 6: its first lease is 1). A row of the WorldObjects store carries the id in 8 bytes, not 4 (area 8: 47 bytes a row against 42, computed there as 12 + 16 + 4 + 2 + 8 + 1 + 2 + 2). No id takes a Steam type or a PurrNet connection as its key. `SeededStream.Algorithm` is an integer naming the draw sequence (SplitMix64 seeding, xoshiro256** draws); the golden vectors fix it, and a world's fingerprint, which is a Persistence section (area 5), records it, so a changed algorithm shows as a mismatch the fingerprint reports and repairs nothing. The bit-level writer, varints, caller-owned buffers, decode limits and counted sections that Networking's first slice needs are the packing capability, which area 6 specifies.

**Determinism harness (`Spellbound.Core.Testing`).** A simulation assembly proves itself deterministic by running the same seed and ticks and comparing a hash of the result with a golden value per region (`Assert.GoldenHash`). The jobs whose output must match across machines (a generation job, the world's fingerprint) compile with `FloatMode.Deterministic`; a job whose output is only local (the awaken and sleep job decides which proxies exist near this peer) does not, and the mode is not forced on the whole assembly. The assembly's identity asset lists the jobs that must match in `machineMatchedJobs`, and the check (Living's rule V5, a text scan of the source) fails a listed job whose declaration lacks the mode and a listed name that no longer exists; it fails nothing that is not listed. The harness keeps no list of its own and reads the same field. The Unity manual page ("Float precision and determinism", Burst 1.8 and 6000.6) says the mode gives consistent results across supported platforms on 64-bit architectures, turns off some floating point optimisations and flushes subnormals, and that disabling optimisations may negatively impact the performance of floating point calculations; it gives no figure. Today no job in Corsairs, GeoForge or Core sets the mode (a search for `FloatMode` returns nothing), so every budget in WorldForge's `CLAUDE.md` (worst frame under about 8 ms, stamp and prep under about 1 ms per chunk) was measured in the default mode. R0's measurement story therefore runs today's WorldForge job chain and the awaken job in both modes on the reference world and compares the numbers the W2 gate uses (World.md), and W2's gate reads that result; the list is fixed from that result, and a listed job that blows its budget in the mode goes to the developer as a decision with the figures, never into the check as an exemption. The harness stays the proof of a result per platform, run on every platform the line supports. WorldForge's golden worlds use it.

**Stepping a world's physics (WorldObjects' world instance).** The world instance steps its own physics scene once per fixed step, as the map servers of the big MMOs run each world's own loop (developer, 2026-10-24); Networking's clock steps nothing and only delivers messages. The games start at PurrNet's 20 ticks a second and Unity's 50 fixed steps a second: two cadences, both settings read once at start, neither derived from the other (2.5 fixed steps to a tick, computed). The clock driver is Core's and exists for every clock; the physics step is the instance's own small component, added only for a world whose scene the instance must step. The physics driver reads `Time.fixedDeltaTime` each step and passes it to `Simulate`, never the tick's step, and Networking's audit prints both numbers and fails a driver that passes another step. A scene that holds a PurrDiction `PredictionManager` is left alone: the manager steps a predicted world's physics (developer, 2026-10-24), and the rule for the rest of that process (the default scene in script mode, the other worlds' step) is Networking's N10 probe, which runs before L3's driver story. What runs in a fixed step is:

| Order in the step | Who | What it calls |
|---|---|---|
| 1 | Core's clock driver, earliest | Reads the tick source and advances the `TickClock` to it (default: one step; with PurrNet, PurrNet's tick plus the world's epoch, which is the same tick for two or three fixed steps in a row at the games' rates); holds if the source is lower. Present in every game that started a clock, with one world or many |
| 2 | Every script, in the execution order set on its component | Reference frames write their poses, then riders' `ReferenceFrameBinding` reads them, Navigation's follower and crowd advance and supply the move, then the drivers of `MotionClaims` move bodies |
| 3 | The instance's latest component (a scene it must step) | `PhysicsScene.Simulate(Time.fixedDeltaTime)` once, on the world's own scene; absent for a scene that holds a `PredictionManager` and for the default scene while Unity steps it |
| 4 | The same component after the call, or Core's clock driver, latest, when Unity or a predictor steps the scene | Raises `Stepped(tick)` on the clock (`WorldStepped` on the instance) every fixed step; Networking's hub flushes the world's regions on it, at most once per tick. On the default scene it fires before Unity's own physics step of that fixed step, so a batch carries the scripts' state of this step and the physics result rides the next one |

```csharp
public sealed class WorldStepDriver : MonoBehaviour {
    void FixedUpdate() {
        if (!world.StepsOwnPhysics) return;
        world.Physics.Simulate(Time.fixedDeltaTime);
        world.RaiseStepped();
    }
}
```

With one world on the default scene Unity steps physics and nothing of ours does, but the clock still runs, so a tick advances and `Stepped` fires in a one-world game. A game with no world instance has the clock and no physics driver at all. If Unity runs several fixed steps in one frame the driver steps once in each. Physics may fall behind the clock after a hitch (developer, 2026-10-24): Unity caps game time per frame (Maximum Allowed Timestep, 0.3333 s in both games, `TimeManager.asset:7`) while PurrNet counts ticks on wall time, so after a 500 ms frame about 16 fixed steps run and 10 ticks are counted (Networking's computation). The driver steps once for each fixed step Unity gives it and never runs extra steps to catch up. It reports the lag as a `Cost` through the world's context (`worldobjects.world.physics_behind_clock`, in milliseconds, the figure Networking's capacity report prints) beside the step's own cost (`worldobjects.world.physics_step`). A forced catch-up, as other games do, is held for a later discussion once the games iterate; it is recorded as held, not decided against. GeoForge's collision parts are created in the physics scene of the world instance that owns the volume group, and that instance steps them with the rest. Unity steps only the default scene by itself and a local physics scene "does not simulate on its own and is stepped by script" (Networking's ledger row, read there through search excerpts), and PurrNet's runtime has no `Simulate` call (Networking's search); that `Simulate` may be called from a latest-order `FixedUpdate`, and that this is the position the default scene's own update has after the scripts, are read in the manual and run by Networking's story, which is theirs; R3d's order test, which includes a hitch case that asserts the lag is reported and no extra step is run, and Networking's two-world smoke (a falling body) depend on this driver and on that story.

Its reference figure is the prefab of a playable character of the game, a field that validation checks with `CharacterKit.Body.IsPlayable`, and an artist makes a new contract from the Create menu in the game's rules folder, validated through `IAuthoredDefinition` (R1). The builder and its button stay in Character; ArtPipeline runs the dry run at import as the artist's preview. Operations: `character sockets` and `character ragdoll` return `succeeded:` with the text, or `failed:` with the error string.

**An inventory transaction (Inventory).**

```csharp
var transaction = new InventoryTransaction(intentKey);
transaction.Move(chest, chestSlot, player, playerSlot, quantity);
var receipt = transaction.Commit(intentLedger);
if (receipt.Rejected)
    Reject(receipt.ReasonId);
```

Commit checks the whole transaction against the containers as they are, then applies it, or applies nothing. Every change to a container is a transaction: there is no protected slot writer and no raw writer left in the engine (developer, 2026-10-24, confirmed). A transaction commits in one process, and Inventory asks one seam whether that process may write every container the transaction names, `IContainerWriteGate.CanWrite(containerId)`, which answers yes by default so a single-player game installs nothing. Who may write a replicated container (owner, host or server) is Networking's configuration per replicated thing, with no privileged default, and `Inventory.Networking`, a bridge to the protocol assembly, implements the gate from that configuration and replicates what a committed transaction changed from the writer. A player's container replicates from its owner: the transaction is applied on the owner's machine and its source is bound `Owner`; a game that wants the final say binds the same source `Host` or `Server`. No authority replica of the player container is built here. Saboteer is owner-authoritative: a player's hotbar and bag are written by their owner, so a drop, a swap, a sort or a stow between the player's own containers commits at once on the owner and replicates from there, with no host answer, no server check and no escrow step. A move between containers that have different writers is a linked move, in the next section. A game that builds its own container on the engine keeps no writer either (question 22). Corsairs' `PlayerBagEngine` is a sealed subclass of `InventoryEngine` in the game assembly, which `internal` locks out, and it writes slots in its own sort and merge code (`PlayerBagEngine.cs:103,156,172`); the save load calls `Engine.SetItemAt` (`PlayerInventory.cs:104`), and so do `EquipmentInventory.cs:122` and the crafting console commands (`CraftingConsoleCommands.cs:111,176`): seven call sites. R6c moves them. A save load is a mint under the reason `save.load`, and a sort or a merge is moves inside one transaction, so the audit still sums to mint minus burn. An `audit` operation sums every container by item id and compares the sum with mint minus burn. A transaction is a pooled value, not an allocation per loot, as `TreasureChest` uses scratch collections today (`TreasureChest.cs:22-23`). Creating or destroying items is an explicit step with a reason (`Mint(itemId, quantity, reasonId)`, `Burn`), counted under the reason. Committing the same `IntentKey` again returns the first receipt without touching a container. The chest, the world item and the trader all use the same two lines.

**A linked move, and what each client sees (Inventory, R6d).** An item moving between a container its owner writes and one the host writes, such as a player's hotbar and a shared chest, goes as two linked steps that each commit at once, under one `IntentKey` (developer, 2026-10-24). A move must never show as lag, a stutter or a wait on any client, and nothing on screen blocks for the second step. The first step is always the one on the source's writer, whichever peer that is: this section walks the owner writing the source (hotbar to chest), and "The host writes the source" below walks the other direction (chest to hotbar), which is the one Saboteer's chest and world item take use most.

```csharp
var link = new LinkedMove(intentKey);
link.Withdraw(hotbar, hotbarSlot, quantity);
link.Deposit(chest, chestSlot);
var receipt = link.Commit(intentLedger);
```

Both halves carry the one `IntentKey`. Each container's replication source takes part by marking itself dirty with the move's key, `notifier.MarkDirty(this, intentKey)`, an overload of Networking's O(1) flag, so the batch that carries a half names its partner; `Inventory.Networking` makes that call from the committed step, and Inventory itself knows no notifier.

Step 1, `Withdraw`, is a transaction on the owner's machine that commits on the frame of the click: the stack leaves the hotbar and sits in the link's entry in the ledger, an in-flight entry the audit counts and that is not a container (accounting only: to the container model and to every client's data the stack is in no container, and what a screen draws from it is the view's presentation state, as Networking has it). Step 2, `Deposit`, is a transaction on the host: the stack leaves the entry and enters the chest in the host's first step after the intent arrives. The owner sends the replication of step 1 and the intent for step 2 in one reliable message, so the host applies both in the same step and flushes both in the same batch. A repeat of the key changes nothing in either step, and the audit counts the pair as one move: `inventory audit` prints `succeeded: 0 items missing, 1 linked move`.

| Who is looking | The item leaves the first container | The item appears in the second | What waits |
|---|---|---|---|
| The player moving it | On the frame of the click | On the same frame: the view draws the stack in the chest slot from the in-flight entry, and the host's batch replaces the drawing with the real item when it arrives, with no change on screen. At an 80 ms round trip that is at most 130 ms after the click (r/2 up, up to one tick at the writer, r/2 down; assumed ping, computed) | Nothing. No spinner, no locked slot, no delayed frame |
| The host's own player | When the owner's change reaches the host | In the same host step | Nothing |
| Another client that observes only the chest | It never sees the hotbar, which is private to its owner | When the host's batch reaches it: r/2 up, up to one tick, and its own r/2 | Nothing; the chest updates as any replicated change does |
| Another client that observes both containers | Both halves on the same frame, never one without the other | The same frame | At most one tick (0.05 s at the starting tick), held only while the partner half has not applied, then both apply together |

How long the item is in neither container: in the model, from step 1 to step 2, which is half the round trip plus up to one fixed step (0.02 s) for the host to apply the intent (computed, not measured); on the mover's screen it is zero, because the view draws the stack in the chest at once, and on any other screen it is zero too, because a client that observes both containers applies both halves on one frame. If the host refuses step 2 (the chest is full), its receipt says so and the owner commits a third step that returns the stack from the entry to its first slot under the reason `link.returned`, counted as the same move: the stack slides back in the owner's view, the one case a player sees, and it is true. A timer never returns a stack, because step 2 might still land later and the item would exist twice; an entry still open after `linkWarningSeconds` (a field of `IntentLedgerSettings`, default 10, converted to ticks when the ledger is created) trips the guard `inventory.link.unsettled` and shows in the audit as an open link. The drawing is the view's: Inventory's view reads the open entries of the ledger and draws a stack in its target slot, and the container model is never told a stack is there that the host has not committed (a claim on UI). R6d's stories test it with PurrNet's simulated latency and loss and send the repeated intent twice.

**The host writes the source (R6d, third story).** Taking a stack from a chest the host writes into the player's own hotbar uses the same four lines in the other order; `Commit` asks the write gate which machine writes each container, so the code does not change with the direction.

```csharp
var link = new LinkedMove(intentKey);
link.Withdraw(chest, chestSlot, quantity);
link.Deposit(hotbar, hotbarSlot);
var receipt = link.Commit(intentLedger);
```

Step 1, `Withdraw`, is a transaction on the host: the stack leaves the chest into the host's ledger entry in the host's first step after the intent arrives. It cannot commit on the frame of the click, because the owner does not write the chest, so on the click the owner's machine does three things on that frame and waits for none: it sends one reliable message with the intent and the key; it holds the deposit as a pending entry in its own ledger (accounting only, which reserves no slot and writes no container); and its view draws the stack leaving the chest slot and flying to the hotbar slot (the view's presentation state, as above). Step 2, `Deposit`, is a transaction on the owner: when the host's batch for the chest arrives carrying the key, the owner commits the stack into the preferred slot, or the first slot of the hotbar that accepts it, on the frame the batch applies. The hotbar replicates from its owner as always, and the host closes its entry when the hotbar's batch carrying the key reaches it. Because the data of the hotbar changes only after the host has committed step 1, the stack can never be in two hotbars.

| Who is looking | The item leaves the chest | The item appears in the hotbar | What waits |
|---|---|---|---|
| The player taking it | In the view on the frame of the click; in the chest's data when the host's batch arrives | In the view on the same frame, drawn from the pending entry; the real item when the host's batch has arrived: at most 170 ms after the click at an assumed 80 ms round trip (r/2 up, up to 0.09 s on the host, r/2 down; Networking's figure, computed) | The move never. A use or a drop of that very stack in those 170 ms is held and runs when the real item lands |
| A second taker of the same stack | In the view on its click | In the view, then the drawn stack goes back to where the chest's data says it is: gone | Nothing; the loser sees the stack fly and fade, at most 170 ms after its click |
| The host's own player | In the same step | Not applicable: the host's hotbar replicates to others | Nothing |
| A client that observes the chest and the taker's hotbar | Both halves on the same frame, never one without the other | The same frame | At most one tick (0.05 s at the starting tick), held only while the partner half has not applied |

Two takers of one stack. The host applies intents in the order they reach it within a step, the same arrival order that owner mode already ends in (`Line.md` Limits). The first `Withdraw` commits and the stack sits in the host's entry under the first key. The second names a slot that no longer holds that stack and is refused by the host with the reason `link.source_changed`; the loser's machine drops its pending entry and its drawing. No data was ever written to the loser's hotbar, so no stack exists twice, and no timer decided anything. What the loser sees is true and rare: the stack flies toward its hotbar and fades, because the chest it replicates says the stack is gone.

The other refusals, none by a timer. (1) The hotbar cannot accept at step 2 (full, or the preferred slot taken and no other accepts): the owner sends a return intent and the host's third step puts the stack from its entry back into the chest under the reason `link.returned`, counted as the same move; the owner's view slides the stack back. (2) The owner leaves with the entry open: the departure proves that step 2 can never land from that machine, so the host returns the stack at the participant-left event under `link.returned`; the owner's last reliable batch is applied before that event if a deposit did land, so it is never also returned, which rests on PurrNet delivering reliable ordered messages ahead of a disconnect (not read; N2's simulator case checks it). (3) A slow host: the entry stays open past `linkWarningSeconds` and trips `inventory.link.unsettled` in the audit, and nothing returns the stack. If the chest is full again when a returned stack comes back, the stack stays in the entry and the guard trips; that double failure is shown and not repaired.

The alternative that removes the 170 ms hold of a use (the owner takes the stack at once and the host's refusal takes it back) lets a consumed item be refused afterwards, so it is not taken. R6d's third story tests two takers of one stack under simulated latency and loss, asserting that exactly one hotbar receives it, that the loser's view settles on the replicated chest, and the three refusals above.

**The intent key and ledger (Core, the only ones).** `IntentKey` is an actor id from Core's identity seam plus a per-actor sequence, and `IntentLedger` is the bounded window of keys already applied. Both live in Core and nowhere else: Inventory's `InventoryTransaction` takes Core's key, so a single-player farming sim that installs Inventory and not Networking compiles and replays correctly (it supplies a local counter, `IntentSequence`), and a co-op build carries one key type and one window, not two to convert between. Networking.Replication stamps its commands with Core's `IntentKey` and keeps no window of its own; it is the supplier of actors and sequences, which is why it is listed as the key's source and not its owner (a claim on area 6, which listed `IntentKey` in its own assembly). The ledger belongs to the world instance, like the context, so two worlds do not share a window. A window exists for an actor who is present, not for every actor ever seen. The supplier of actors calls `ledger.Depart(actor, tick)` when an actor leaves (Networking does from its participant-left event; a single-player game never calls it). The window is dropped when the grace time has passed, `departureGraceSeconds`, a field of `IntentLedgerSettings` (default 300, converted to ticks at the world's step when the ledger is created, because a resend arrives within seconds), and `ledger.Return(actor)` before then cancels the drop so a reconnecting player keeps the window. Memory follows the actors online plus those inside the grace time, not every actor ever seen. R1b's soak connects and disconnects 20,000 actors in turn on a world sized for 5,000 and asserts that the ledger's bytes (a reading under `core.intent.ledger_bytes`) never exceed the figure for 5,000 actors plus those inside the grace time.

**World operations (WorldObjects).** Accepted from the command line area's claim: group `worldobjects` ships `presets`, `spawn`, `find`, `inspect` and `remove`, replacing Core's `list` and preset routing. Shapes, as the command line area fixed them (group, verb, arguments, text result): `presets [--prefix <text>] [--offset <n>] [--limit <n>]` lists preset ids; `spawn <preset> <x> <y> <z> [--count <n>]` creates instances through the world's allocator; `find <preset> [--within <metres>] [--near <x> <y> <z>] [--offset <n>] [--limit <n>]` reads the region index and prints id, position and state; `inspect <id>` prints one instance's preset, region, state and packed data length; `remove <id>` deletes one. `presets`, `find` and `inspect` are `Reads` and run on the peer that was asked; `spawn` and `remove` change a thing, so they run on the peer that decides for the thing they name, which Networking's router finds from the world's write policy, and carry the developer audience. Each takes `--world <name>` and defaults to the only world, and refuses with the list of worlds when there are several. An unknown preset id in `spawn` or `find` fails with up to three candidates by edit distance over the registered preset ids, so `rare-ore` returns `rare_ore`. The mechanics under them (the index, regions) are area 8's; `worldobjects regions` is area 8's operation.

## Directions

**A. Vocabulary in Core, mechanisms in the packages that own the noun, a doctrine, a soak (taken).** No new package. The five mechanisms land in Core, Character, Inventory and Diagnostics. It wins the scenario because every handover has one owner and every owner reports through one model.

**B. A `Mechanics` or `Robustness` package that holds ride, containment, transfer and the recorder (rejected).** The scenario text invites it ("a package, several, a framework"). It fails the homes test twice: a farming sim buying transfer would receive ride and containment, and Inventory's transaction would be owned by a package that does not own containers, so two packages would own the noun "move an item". It is also exactly what revision 3 warned against: a family named for a feeling. Alternative to A.

**C. Deterministic replay as the debugging mechanism (rejected).** Record inputs and seeds, replay the playtest in the editor. It is the boldest answer to "without reproducing", and the line already gives ticks and seeded streams. It fails on the engine: the Unity physics reference says Enhanced Determinism keeps the simulation consistent only "provided that the game inserts the actors in a deterministic order" and costs performance (Physics project settings reference), and the manual-simulation page says a fixed timestep is needed for reproducibility with other challenges remaining; our bodies are rigidbodies, ragdolls and a streaming mesh collider whose insertion order depends on frame timing. A replay that cannot be trusted to reproduce is a worse black box. Alternative to the recorder plus guards. Kept as a "Beyond" item: turning a dump into a repeatable soak that runs N times and reports the probability of the same guard trip.

**D. Doctrine and lint only (rejected as the whole answer, kept as one part).** Seven written rules and checks catch the next copy of the ride-frame component but cannot count a rescue in a playtest or give a stranger ride and containment for free. Alternative to A, which includes it.

**E. Reparent the rider under the ship in the Unity hierarchy (rejected, a detail inside A).** PurrNet's soft parent syncs in the reference frame "exactly as if parented there, but the Unity transform is left untouched, no real reparenting, no hierarchy sync" (`NetworkRigidbodyBase.cs:1548-1552`). Real parenting inherits scale and breaks ragdoll bones' joints. Alternative to the soft-parent bridge.

## The doctrine, seven rules

Written once, in the line's reference, enforced by area 7's check where a check is possible.

1. **A body has one driver at a time.** Ragdoll, carry, rescue and a game's locomotion are drivers on one arbiter. No system tests another system's state. Check: a type outside the arbiter that writes a body's position while a claim is active is a failed play-mode assertion in the soak.
2. **A frame moves before its riders.** Frames carry an earlier execution order than riders; riders read the reference frame's applied pose of the same step. Check: a validator reads the order values of every `IReferenceFrame` and `ReferenceFrameRider` in the project.
3. **Velocity leaves a frame as relative plus the reference frame's velocity at the point.** Only `ReferenceFrameBinding` does that arithmetic.
4. **Prevent before rescue.** A body waits for its support (`SupportGate`); the rescue guard exists for what slips past.
5. **A thing is moved, minted or burned, never merely set.** Items change container through a transaction; the three verbs are counted under a reason; a repeated intent changes nothing.
6. **Everything that can go wrong is counted under a key, never only logged.** No new serialized `trace` boolean: the observation settings asset turns key groups up or down. Check: a lint on `[SerializeField] bool trace*` in package code, and a package that declares keys has no front door without a context parameter.
7. **A simulation assembly reads time from a `Tick` and rolls from a `SeededStream` passed in, and ids from an allocator.** No `Time.time`, no `UnityEngine.Random`, no static mutable state of its own (a static readonly key is immutable and allowed; every reading, budget, recorder, guard state and ledger lives in a context or world the instance owns), and a saved duration is seconds, never a Tick, a TickSpan or a rate, converted to ticks at load; the tick rate and the fixed step are settings read once at start and nothing is derived from either. Check: an assembly scan of every assembly the identity declares a simulation assembly, the deterministic float mode on the jobs its identity lists, and `Assert.GoldenHash` for its output.

## Limits

- Every cost figure is a target until R1b story 3 measures it; no claim here depends on one.
- Whether a concave mesh collider can be tested for "inside" with a physics overlap is unverified; the default `IContainmentSpace` over physics therefore offers floor, fall and no-support checks only, and the embedded check needs the GeoForge adapter or a consumer's own space. R4 story 1 tests it.
- No simulated reference frame exists in either game yet; a ship hull is designed from the scripted elevator and PurrNet's soft parent, and its first real test is R7b.

Fix: the tick clock is Core's. `TickClock` (a plain class) and its small driver, with `CoreKit.Time.StartClock(rate)`, run in every game that starts one: earliest order advances the tick from the tick source, latest order raises `Stepped`. A world instance starts one per world with the same call. What stays the instance's, and only for a world on its own physics scene, is the `Simulate` call. This is the same path the observation context already has (a game with no world instance creates its own). Test: R0 gains a story that runs the clock in a scene with no world instance and checks a crop timer in seconds fires after the right number of fixed steps.

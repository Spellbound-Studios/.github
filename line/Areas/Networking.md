## What this area decides

For networking the line owns one package, Networking. It owns how replicated world state gets from the authority to the peers that should see it, how a joiner catches up, how a client asks for a change, how an event reaches an audience, how interest becomes PurrNet visibility, and the checks that keep all of it honest. It does not own transport, RPCs, spawning, ownership or movement (PurrNet), prediction (each game, at its pitch), lobbies (Studio.Online), the meaning of any payload (the package that owns the data), or the step of a world's physics (the world instance). Who may write a replicated value is not Networking's call either: it is a setting on each thing a game binds, with no privileged value.

Networking depends on Core and bridges PurrNet. That is the shape Decals has with URP: the store compiles without the render pipeline and the URP backend is the default bridge. Here the protocol compiles without PurrNet and the PurrNet adapter is the default bridge, in the same repo.

The design in one paragraph. Networking is two assemblies. `Spellbound.Networking.Replication` is engine-only and has no PurrNet type in its public surface: the contract a data package implements to be replicated (`IReplicatedSource`), the dirty set, counted sections, sequence and gap logic, the snapshot pager and its shared cache, the interest map, leases for identity allocation (the authority implementation of Core's allocation seam), and a loopback simulator that runs the whole protocol in memory. `Spellbound.Networking` is the thin PurrNet adapter: one `ReplicationHub` module per region identity that carries every source of that region in one flush per tick, a region streamer that turns the interest map into PurrNet whitelists, an event channel, and one operation gateway; it compiles only when PurrNet is installed. Data packages never see PurrNet: their `.Networking` bridge assembly implements the contract against the protocol assembly only.

### The contract a data package implements

```csharp
public interface IReplicatedSource {
    uint SourceId { get; }
    ulong BaseFingerprint { get; }
    void Attach(IDirtyNotifier notifier);
    void WriteChanges(ref BitWriter writer);
    void ClearChanges();
    void ApplyChanges(ref BitReader reader);
    bool WriteSnapshotPage(ref SnapshotCursor cursor, ref BitWriter writer);
    void ApplySnapshotPage(ref BitReader reader);
    void ResetToEmpty();
}

public interface ICommandSource : IReplicatedSource {
    bool TryApplyCommand(ParticipantId sender, ref BitReader command);
}
```

`BitWriter` and `BitReader` are Core's, from the packing gaps the developer is closing (a bit-level writer, pack into a caller-owned buffer, decode limits); the names here are provisional. The contract mentions no player, connection or PurrNet type. `ParticipantId` wraps a 64-bit value that the adapter fills from `RPCInfo.sender`. The one rule of the line holds here: no library takes a Steam type or a PurrNet connection as a player key. `ParticipantId` is the key; the adapter fills it from the authenticated sender at the edge, and nothing past the adapter (the lease table, the intent actor, a source) sees a `PlayerID`, a Steam id or a connection.

`IDirtyNotifier.MarkDirty` is an O(1) flag set on the source: a dig that touches 120 voxels calls it 120 times and the hub holds the source once in its dirty list.

`BaseFingerprint` is the hash of whatever the source's records are deltas on: the procedural base of a world (seed, generator versions, rule set) for voxel edits and for placed instances, zero for a source that holds its whole state. The source table of the spawn payload carries it, and a client whose own base differs reports a base mismatch before any record is applied, and does not resync (a resync would be answered with the same records against the same wrong base). A source whose records are keyed by a caller-derived 64-bit id (the hash of rule, cell and ordinal) sends only deviations from the base, never the base itself, which is what lets a region woken again be rebuilt rather than re-sent.

Two rules the contract states and the simulator tests. Apply is idempotent: a record carries the final state of the thing it names (a tombstone for a deletion), never an increment, so a record applied twice leaves the same state. Order inside a section is the source's, and sources write in key order so two machines pack the same state to the same bytes.

### Who may write a value

Who may write a replicated value is a setting on each source a game binds, never an assumption of Networking. `hub.Bind(source, WritePolicy.X)` takes the policy as a required argument, and the settings asset holds no default for it: a policy left `Unset` is an error in the audit, so no policy is privileged and none is chosen for a game that has not said. Two things in one game may differ: Saboteer binds its terrain edits and its players' containers `Owner`, and a game that wants a final say over its population binds that source `Server`.

| Policy | Who applies first | What travels | A validator | What the writer waits |
|---|---|---|---|---|
| `Owner` | The writer's own machine, at once | The changed records, up to the host, which applies them in arrival order and flushes them to the observers | None, and the mode may not ask for one. Decode and size limits stay: they stop a malformed packet from crashing a peer and judge nothing | Nothing. Others see the change after the upload and the host's next flush |
| `Host` | The hosting player's machine, which is the authority | A command up, the batch back | The source's `TryApplyCommand` | A client waits one round trip plus up to one tick; the host's own player waits the tick (computed) |
| `Server` | A dedicated server | The same as `Host` | The same | The same, for every player |

`Host` and `Server` are one code path in PurrNet (a ServerRpc on a host runs inline with `info.sender` set, purrnet skill, RPCs); they differ in what the audit expects and in the cost sheet. Owner mode needs nothing beyond the contract's two methods: the writer's source marks itself dirty, its `WriteChanges` goes up in one ServerRpc stated `requireOwnership: false`, the host calls `ApplyChanges` on its copy (the copy a late joiner's snapshot and a save read), and the next flush carries the records to every observer. A record is a final state and apply is idempotent, so the writer applying the echo of its own record changes nothing. Two rules keep owners consistent: a writer ignores an incoming record for a key while a write of its own to that key is not yet echoed, so a quick drag does not flicker back to an older value; and when two owners write one key within a round trip the host's arrival order is the final order, because the host's flush is what every machine applies last. The simulator checks the second rule with two owners, one key, and reorders and delays by seed, asserting equal digests at the end.

`PrivateReplicationHub` sends only to the owner of its identity (a hand, a container); bound `Owner`, the host still keeps the copy for saving and for a rejoin. Computed, not measured: in owner mode the writer pays no wait, and another player sees a change after half a round trip of upload plus the host's next flush. The round trip of `Host` and `Server` is priced under "Cost, priced" as what a game pays when it chooses them.

### A move between two writers

An item that moves between a container one peer writes and a container another peer writes goes as two linked steps (decided 2026-10-24), each committing at once on its own side and both stamped with the same Core `IntentKey`, so a repeat changes nothing. The pair itself is Runtime's design. The rule that binds this area: the move never shows as lag or a stutter on any client. What a client sees, and when, with the starting tick of 0.05 s and a round trip written r (computed, nothing measured):

| Who | Sees | When |
|---|---|---|
| The mover, who writes the source | The item leaves the source at once and shows in flight over the destination slot, a presentation state of Inventory's view and never a data state; input is never blocked | On the frame of the click |
| The peer that writes the destination | The item appears in the destination when step 2 arrives and commits | r/2 after the click |
| The mover, when step 2 is confirmed | The in-flight item turns into the real item in the slot, on the frame the batch applies | r/2 up, up to one step for the host to apply (0.02 s), up to 0.07 s to flush, r/2 down: at r of 80 ms, at most 170 ms (assumed ping, computed) |
| A third client that observes only the destination | The item appears; it never sees the source, which is private | r/2, up to 0.09 s on the host (apply step plus flush), and its own r/2 |
| A third client that observes both containers | Both halves on the same frame, never one without the other | When the later half arrives, held at most one tick |
| Anyone, when step 2 is refused (a full chest in host mode) | The mover sees the in-flight item return to the source; a third client that observes both saw neither half | One round trip plus up to 0.09 s, as step 2 would have taken |

How step 2 reaches the mover's screen. There is no reply to the command and no second channel: the destination's hub flushes the record to its observers, the mover included, in the batch it was going to send anyway. The record carries the intent key, the mover's view matches it to its own in-flight item, and the writer's pending mask keeps an older echo from flickering the slot in the meantime. The linked halves reach a client that observes both as two batches in one tick, and the hub fixes the frame problem rather than hoping the two arrive together: a batch names its linked partner (`MarkDirty` takes the intent key of the move), and a client holds a half only while the partner hub is one it observes and the partner has not applied, for at most one tick, then applies both in the same frame. A client that does not hold the partner applies at once. The hold is the joining client's buffering by sequence, reused, and costs the one batch of a linked move at most 0.05 s, and only when the partner is late; the simulator checks it with reorder, delay and drop between the two halves, asserting that no frame shows exactly one half to a client that observes both.

One message up, one pass down. The up half is the linked upload. The mover's machine sends the records of step 1 (the sections of its own sources that the move marked) and the packed call of step 2 in one ServerRpc on the gateway's path, which already sends one packed call as one RPC; the payload gains attached source sections, an extension inside the gateway and no new system. The channel is reliable and ordered and the message is one, so the host holds both steps or neither. In one step the host applies the sections to its copy of the mover's container and runs step 2 through `RunHere`; a refusal is Runtime's receipt. The down half: both sources are dirty from the same step, so both hubs flush on the same stepped event of the same tick, back to back. When both sources are bound on one hub the two halves are one batch under one sequence. When they sit on two hubs (a private hub for the hotbar, a region hub for the chest) they are two batches in the same pass, and the hold above makes a client that observes both apply them on one frame. "Both steps in one batch" therefore holds for one hub and is "one pass, one frame" for two; Runtime's claim is amended to that. The flush figure is Networking's: a change waits at most 0.07 s from its mark (up to a tick, then one step, computed in "Stepping each world's physics"); with Runtime's apply step of 0.02 s the host's worst case from the message's arrival is 0.09 s, and the 130 ms Runtime computed becomes 170 ms at an assumed r of 80 ms. The mover's screen waits for none of it.

What the test proves, and what it cannot. The simulator asserts, with drops, delays, duplicates and reorders by seed, that one hub gives one batch and that two hubs give no frame showing one half to a client that observes both. The second-process test asserts the same frame at four simulated latencies. PurrNet's simulated loss is set on its UDP transports (`Transports/UDPTransport.cs:224-233`, `Transports/PurrTransport.cs:688-700`); whether a reliable packet lost under it is resent was not read, so the loss half of R6d runs in the simulator and the second-process test claims latency only until N2 reads it. Designed here and proved by N2's linked upload story; nothing was run.

A leaver with a link not yet sent. If the mover disconnects before the message arrives, the host holds neither step: its copy of the mover's container still holds the stack and the destination never saw the call, so there is nothing to hold, return or time out. The leaver's machine took its in-flight entry with it, and Runtime counts that under `link.abandoned`. Networking tells the ledger one thing, through `ParticipantLeft`: `Depart(actor, tick)`, with no timer and no returned stack (`linkWarningSeconds` and the guard `inventory.link.unsettled` are Runtime's). A mover whose message arrived has both steps applied, whatever happens to the connection after.

### Where an operation runs

An operation line typed on one machine runs on the peer that the write setting of the thing it acts on says decides, whichever face typed it (the console, the window, the Unity CLI, a test). `OperationGateway` has no default route.

Which thing a line acts on. An operation that changes replicated state marks the parameter that names the thing, its target (a claim on CommandLine: one marker on `ArgumentAttribute`, reported by `OperationDescription`). Networking asks the sources bound in the world which one holds that id, through `IOperationTargetSource` in the protocol assembly (`Holds(targetId)` and `OwnerOf(targetId)`, implemented by each data package's bridge for the ids it owns: an `InstanceId`, a container id). The `WritePolicy` of the source that holds it decides:

| Policy of that source | The call runs on | How it gets there |
|---|---|---|
| `Owner` | The machine that owns the thing: the host for a thing the host spawned (a deposit in a world region), the player for a thing on a `PrivateReplicationHub` (that player's container) | The owner's own call needs no wire. From another machine: one ServerRpc to the host, which runs it when it is the owner or relays one TargetRpc to the owner. No validator and no authorizer, because owner mode may not require one |
| `Host` or `Server` | That peer | One ServerRpc; size and rate limits first, then `IOperationAuthorizer` with the authenticated sender |

A call whose target no source holds is refused with `failed:` and the target named. A call that marks no target (a group-wide operation) uses the `OperationRoute` of its group, a setting with no default; `Owner` there means the machine that typed it, because a call with no thing has no other owner. Decode and size limits stay in every mode.

Reads run where they are asked. An operation whose effect is `Reads` runs against the replica of the peer that was asked and is never sent; a dry run is routed like the write it previews, because the deciding peer holds the state it would change, and its answer comes back as `previewed:`; a replica can be half a round trip plus one flush behind its owner (computed), and the answer claims nothing more. Writes and destroys are the ones that route.

Who sends. Every face calls `OperationHost.Run`. With Networking installed the adapter registers one router with Core's operation host (a claim on CommandLine: a one-method seam whose default is "run here"), and the host asks it before it runs a write: here, or send. The console, the window, the Unity CLI and a test therefore behave the same and no face decides. The owner's answer comes back as the same text with its status word first, so the peer that typed the line reads the owner's result. The deciding peer runs a received call through `OperationHost.RunHere`, which never asks the router, so a call cannot bounce between peers. The target marker `ArgumentAttribute.Target`, `OperationDescription.Target`, `IOperationRouter`, `OperationHost.Router` and `RunHere` are Core's (CL1 stories 12 and 13); `IOperationTargetSource` stays in `Spellbound.Networking.Replication` because it names a peer; the gateway registers as the router. N4b's operation stories wait for CL1 story 13.

The `authority` audience (decided 2026-10-24). On an operation the word means "runs on the peer that decides" for the thing the line names. Nobody holds it as a role: the receiving peer is the decider by construction, and the sender is checked by the audiences it holds (`IAudienceResolver`; in Saboteer every player holds `player` and an `Owner` route asks for nothing more). Writes go to the owning or deciding peer and reads run where they are asked; the marker on the target parameter and the router seam in Core's operation host are area 2's to write in Core, and this file's claim on them stands as accepted.

Saboteer routes its operations `Owner`; a dedicated production server routes them `Server`, which is the operator route. The agent's two-build test (a host build and a client build of Saboteer, each driven by `unity command --runtime <exe> spellbound_run`) walks like this, and is not yet run: on the client, `inventory add --container 12 --item copper_ore --count 3` names container 12, which a `PrivateReplicationHub` binds `Owner` to the host's player; the router sends it, the host runs it and answers `succeeded: ...`, and the client prints that answer; `inventory list --container 12` on the host build reads the host's copy and on the client build the replica, which agrees after the host's next flush.

public sealed class CropFieldSource : ICommandSource {
    private readonly CropField field;
    private readonly DirtySet<int> dirtyPlots = new();
    private IDirtyNotifier notifier;

    public CropFieldSource(CropField field) => this.field = field;

    public uint SourceId => StableHash.Fnv1A32("farm.crops");

    public void Attach(IDirtyNotifier notifier) => this.notifier = notifier;

    public void WriteChanges(ref BitWriter writer) {
        using var section = writer.BeginCountedSection();
        foreach (var plot in dirtyPlots.InKeyOrder()) {
            writer.WriteVarUInt((uint)plot);
            field.Plots[plot].Write(ref writer);
            section.CountRecord();
        }
    }

    public void ClearChanges() => dirtyPlots.Clear();

    public void ApplyChanges(ref BitReader reader) {
        using var section = reader.OpenCountedSection();
        while (section.TryRead()) {
            var plot = (int)reader.ReadVarUInt();
            field.Plots[plot].Read(ref reader);
            field.RaisePlotChanged(plot);
        }
    }

    public bool TryApplyCommand(ParticipantId sender, ref BitReader command) {
        var plot = (int)command.ReadVarUInt();
        if (!field.CanWater(sender, plot))
            return false;

        field.Plots[plot].Water();
        dirtyPlots.Mark(plot);
        notifier.MarkDirty(this);
        return true;
    }

    public bool WriteSnapshotPage(ref SnapshotCursor cursor, ref BitWriter writer) =>
        field.WritePlots(ref cursor, ref writer);

    public void ApplySnapshotPage(ref BitReader reader) => field.ReadPlots(ref reader);

    public void ResetToEmpty() => field.Clear();
}

### How it works, in the order a joiner sees it

1. **Open.** The streamer instantiates the region identity from the consumer's prefab, binds the sources and seals the hub. A hub opened to an observer before it is sealed, or sealed with no source, logs one error and refuses; it never half works. A source whose data is still loading reports not ready, and the region stays closed to observers until it is, so Persistence's storage seam never blocks a tick. Binding happens in `OnInitializeModules` on every peer, because on a client the spawn payload is read before `OnEarlySpawn` (purrnet skill, Lifecycle). The spawn payload starts with the region key, and `OnRegionReady(key)` runs before any source applies anything, so a source can attach to the right store first.
2. **Enter.** The interest map says player P enters region R. The streamer calls `WhitelistPlayer(P)` on the region identity (`Components/NetworkIdentity/NetworkIdentity.Rules.cs:35`). Enters are spread over ticks, nearest region first, up to a per-player budget.
3. **Snapshot.** When PurrNet builds the spawn packet for P, the hub's `OnSerialize` (`Components/NetworkModule/NetworkModule.cs:164`) writes the region key, the source table (the Core id of each source, in index order) and the current sequence S. If the encoded snapshot is at or under the inline limit it follows, and arrives before `OnEarlySpawn`. Over the limit the payload says "paged" and pages go out as TargetRpcs, built lazily, shared by every joiner whose S is within the ring depth, and paced by the join scheduler in bytes per tick. The snapshot is taken from live state, unflushed changes included. Because apply is idempotent, a change that is in the snapshot and again in the next batch is harmless.
4. **Catch-up.** `OnSerialize` has no player argument, so the hub notes S in `OnPreObserverAdded(player)`, which PurrNet runs after the spawn packet is built (`HierarchyV2.cs:2712-2742`, purrnet skill). In `OnObserverAdded(player)`, if the hub's sequence has moved past S, the batches S+1 to now go to that player in one TargetRpc from the batch ring (default depth 8 flushes). A quiet region sends nothing. If the ring no longer holds S+1 the player is sent to the paged route. This closes the window between the spawn packet and the first live batch without the server keeping any per-joiner queue.
5. **Live.** A flush is one `ObserversRpc` per region per tick, only when a source is dirty: a 16-bit sequence compared modulo 65,536, the server tick as a small delta, then sections of source index, byte length and a counted record list. The length prefix lets a client skip a source it does not know and report it. A client still joining buffers batches above S and applies them in order after the last page. A duplicate is ignored.
6. **Gap.** A batch whose sequence is not the next, an unknown source, or a source that throws on apply puts the client in `Resyncing`: it drops the region's state, sends one ServerRpc for a fresh snapshot, and rejoins through the paged route. Resyncs queue in the same join scheduler as joins, so a server restart cannot make every client resync into one tick, and each sender has a cooldown. A watchdog turns a join that never finishes into a resync after a configured time. Snapshot defect 12 ("pending forever") cannot occur.
7. **Command (sources bound `Host` or `Server`).** `Submit` sends one ServerRpc with `requireOwnership: false` stated explicitly and a size limit; the server checks the per-sender rate; the source validates against `ParticipantId` taken from `RPCInfo.sender`, which on a server is the authenticated player and cannot be forged (purrnet skill, RPCs). No argument carries a player id. A source bound `Owner` does not take this step: see "Who may write a value".
8. **Leave.** The exit radius is larger than the enter radius, and a region with no observers closes only after the linger time. Closing despawns the identity; the data stays in the owner's store.

Identity: leases, never slots. An instance id is a 64-bit `InstanceId` that belongs to the world, not to a region: the region (more exactly the partition, a reference frame and a cell) is only where the row currently sits. A runtime id is one kind bit (0), a 31-bit lease and a 32-bit counter; a placement id, the caller-derived hash WorldObjects accepts, has the kind bit set, so the two kinds cannot collide. Core owns the type (claim 1 below); callers see an opaque wrapper with equality, packing and `LeaseOf`, never the bits, so the layout is not API and changes before the first release by re-saving, never by translating. A lease is a number issued once in a world and never again. The holder mints ids by counting up inside its lease, with no per-region counter anywhere, so there is no counter that has to move with a region.

- Who holds a lease. The authority takes a fresh lease at process start or host session start. A client takes one the first time it names an id, in one TargetRpc per player, never per region; a game that never predicts never draws one. A lease is never reused, not after a disconnect and not after a restart.
- Accepting a client-named id. The server accepts it only if the lease table says the lease was issued to the authenticated sender and the counter is above the highest it has accepted from that lease (commands ride the ordered reliable channel). Otherwise the command is rejected with a counted reason. An id is never renumbered, because the client has already used it. The earlier "answer a collision with the next free counter" is withdrawn.
- Never reuse. A deleted instance's id is not handed out again. A saved reference, an intent still in its replay window, a journal line or a sleeping record that names it resolves to "no such instance", never to a new object. This answers the reuse question by removing reuse.
- Saved ids across sessions. The default `ILeaseIssuer` grants from a reserved block and makes the block's upper bound durable before it grants any lease in it. The bound is one number in a record of its own, written through Persistence's storage seam with a flush before the grant returns, outside the world's sliced save and independent of it. The first lease in a process waits for that write before the region opens, and a client's lease request is a TargetRpc that waits for it as well. The block size is a value (default 64). On start the issuer's next lease is the recorded bound, so a lease granted from a block that did not finish is skipped, never reissued. A lease is therefore never below the bound of any row that any slice or any per-player record has written, whatever order the slices, the player records and a crash fall in. The cost of a crash is the unused leases of one block, 64 of 2,147,483,648 (computed), and a client's lease from that session is dead: it asks for a new one.
- The save checks the ordering. The world's section stores the bound at the moment of the save; a load refuses a world whose stored bound is above the durable bound, with both numbers named, and the fix is to restore the lease record with the save. Nothing is translated. The simulator case that checks this kills the process after a slice that holds rows under lease L and before the world is saved again, restarts, grants a lease, mints, and asserts that no minted id equals a saved one, with the slices, a per-player record and the kill point varied by seed.
- Size, computed. A 32-bit counter gives 4,294,967,296 ids per lease: at an assumed 2,000 creations a second from the server that is 2,147,483 s, about 24.9 days, and a farming co-op host planting and harvesting 500 plots 132 times uses 66,000 ids of it. Running out is a lease roll, not a failure: an observation fires at 90 percent and the holder takes a new lease. A 31-bit lease gives 2,147,483,648 leases per world: at 1,000 new predicting players a day that is about 5,900 years, and at a login wave of 100 new leases a second 248 days (computed). A lease table entry is a lease, a participant and a counter, 16 bytes.
- Who a player is. One rule and nothing structural beyond it: no library takes a Steam type or a PurrNet connection as a player key. The key is `ParticipantId`, filled by the adapter from the authenticated sender. `ILeaseIssuer` is a replaceable policy with an in-process default and one rule, that no lease is issued twice in a world. How a shard, an account service or a handoff between processes uses these is not decided here, and the measurement in N3 is the only MMO work left in this area.

Per-joiner blocks inside the spawn payload were considered and dropped: `OnSerialize` has no player argument, so a per-joiner value cannot ride it.

Host: the hub sends with `excludeSender: true`, which skips the host's own copy (`Components/NetworkIdentity/NetworkIdentity.Broadcasting.cs:348`, source-read), so no receiver carries an `isHost` guard. A `PrivateReplicationHub` overrides `ownerOnly` (`NetworkModule.cs:54`) so private state reaches only its owner, whatever the write policy. Cached snapshot pages are released when their sequence leaves the ring window and no joiner is still reading them.

PurrNet drift is contained in one assembly. `Spellbound.Networking` is the only code that touches PurrNet; its assembly definition names the PurrNet versions it was written for through `versionDefines`, and a version outside the range compiles the assembly out with a warning rather than silently (Line rule 2). The fingerprint includes a hash of the `ReplicationSettings` asset as well as the module and RPC layout, so a client built with a different cell size or flush cadence is refused as loudly as one built with a different module order.

The write policy is a required argument of `Bind` and the settings asset holds no default for it ("Who may write a value"). The relay path exists only for sources bound `Owner`, and it carries the authenticated sender; a bare `[ServerRpc]` anywhere else is still flagged by the audit.

Every value is a field on `ReplicationSettings`, with a neutral default: flush cadence in ticks (default 1, so slow state can flush every fifth tick), ring depth, page budget in bytes per tick per joiner and per server, inline snapshot limit, command size and rate limits, resync cooldown, watchdog time, and two serialized trace toggles (batches, snapshots) that need no code edit. The asset is checked by a `ReplicationSettingsCheck : IDefinitionCheck<ReplicationSettings>` in `Networking.Editor` (Core.Editor's check seam; Core never changes for it): a write policy left `Unset`, exit radius not above enter radius, a positive page budget, an inline limit below the active transport's reliable batching size, flush cadence at least one. The check runs in the inspector and by `networking audit`, and a finding in a valid call is reported `failed`. The hub is for state that must arrive and be right. Continuous motion belongs to `NetworkTransform` and its siblings, which the purrnet skill's decision ladder already assigns.

### An instance changes partition

A creature walking, a drop rolling or a cart pushed over a 128 m border; and a thing stepping onto a ship, which is the same operation because a partition is a reference frame plus a cell (`Unity.md`, the store contract).

1. The id does not change. It has no region in it, so an intent key, a rider's `ReferenceFrameId`, a navigation footprint, a saved reference and a journal line all keep naming the same thing. WorldObjects offers one operation, `Transfer(id, toPartition)`, that moves the row between its column sets in one authority step and runs resolve handlers once (claim 3).
2. The authority marks both partitions dirty in the same tick. The instance source writes a departure in the old one (the id and the destination key) and an arrival in the new one (the id and the whole row: preset, pose, data). An arrival is the full row, not a delta against the base, because the destination's base does not hold it.
3. A client applies by id, in any order. It keeps the partition each row currently sits in. Arrival: put the row in the arrival's partition. Departure toward B: if the row is already in B do nothing; else if the client observes B, set the row's partition to B (the arrival overwrites it with the same state); else remove the row. A client that observes only A removes it at the departure. One that observes only B receives the arrival and never knew the departure. One that observes both ends in the same state whichever batch it applies first, and a repeated arrival or departure changes nothing.
4. A joiner into B during the move gets a snapshot built from live state, which already holds the row; a later departure from a partition the joiner does not observe is ignored.
5. A thing standing on a border must not transfer every tick. The partition changes only when the position is a margin beyond the border (a value on WorldObjects' policy, claim 3), the same idea as the interest dead band.
6. A placed thing (placement id) that leaves its home partition is written as the removal-from-base deviation it already is, with the destination, and an arrival under the same placement id.
7. What the hub does not carry. `DynamicInstanceSyncModule` (544 lines) today carries runtime object creation and the switch of an instance to and from a physical entity (`DynamicInstanceSyncModule.cs:107-236, 281-286`). Its replacement is `WorldInstanceSource` on the population layer: create, delete, the switch as a row flag, and transfer. The position of a thing that walks every tick is continuous motion and stays with PurrNet's transform components or the game's own choice; the hub carries identity and discrete state. That choice per mover is open and is listed in the limits.

8. A reference frame-local row (a thing on a ship's deck) sits in a partition that names the reference frame and the cell. Its pose is stored relative to the reference frame, so a moving ship does not dirty its riders; the reference frame's own pose is the reference frame owner's data, replicated by the reference frame owner's source or by PurrNet's transform, never by the rider's partition. A client observes a reference frame's partitions when it is within the layer's radius of the reference frame's current position, which the viewer registry and the reference frame map give the streamer. A thing stepping from the world partition onto a deck is the transfer above with a different destination key. A reference frame partition has a stable `ReferenceFrameId` key, never the identity's own id. Its rows change only on a placement, a removal or a move on the reference frame, so a ship with no changes sends nothing, and the reference frame's pose travels as the reference frame owner's data through the reference frame map. A game with no reference frames never meets this path, because Core's default `ReferenceFrameId` means the world (area 3 confirms).

The simulator cases that pin this: an observer on A only, on B only, and on both with reorder, duplicate and delay between A's and B's batches; a joiner into B during the move; a thing that walks over the border 100 times with the margin, asserting two records per real crossing and equal state at every tick; and a rider moving from the world reference frame onto a ship reference frame.

### Many worlds in one process

The line runs several worlds in one server (WorldObjects row, Line rule 11, LV5's MmoServer), and every other area keeps its state per world instance. Networking does the same. The rule: nothing in Networking is static and nothing in it covers the process; each object below is created by one world instance, serves that world and no other, and a second world gets its own.

| Per world instance | What it holds | Why one per world |
|---|---|---|
| `ViewerRegistry` (Core's type, created by the world instance) | The viewers of this world, from this world's streamer | WorldObjects' wake-up and GeoForge's chunk interest read it, so world B never wakes instances or loads terrain around a player of world A |
| `RegionStreamer`, its `InterestMap` and its regions | Layers, enter and exit state, the join and resync queue | A region key is a reference frame and a cell with no world in it, so it is unique only inside one streamer |
| Lease issuer and `LeaseTable` | Leases issued in this world and the durable bound | A lease is issued once in a world; two worlds never share a number space |
| `ReferenceFrameIdentityMap` | Reference frame to network identity | Core's default `ReferenceFrameId` means the world, so two worlds both hold a reference frame with the same default key |
| `ServerClock` schedule | Scheduled events in this world's `Tick`; the tick adapter's one shift is also this world's | The schedule reads the `TickClock` it is given (Core holds the clock, started with one call in every game, and a world instance passes its own); in a process with PurrNet the adapter advances Core's tick from PurrNet's, and a restored world's elapsed seconds come from its save section ("One clock") |
| Event link | Who is in this world, and `Region` and `All` audiences | The player broadcast covers the process, so the link filters recipients to this world |

How a world is served:

1. **Scene.** Each world is a PurrNet scene loaded with `PurrSceneSettings.physicsMode` set (`ScenesModule.cs:44`, as in Limits). Its region identities spawn into that scene. PurrNet keeps which players are in a scene (`ScenePlayersModule.IsPlayerInScene`, `AddPlayerToScene`, `ScenePlayersModule.cs:308,342`). Whether PurrNet's default visibility already follows scene membership is not read here; the first story of the two-world smoke reads it. The streamer whitelists only its own world's regions, so the design does not depend on the answer.
2. **A player is a viewer of one world.** Moving a player to another world removes the viewer from the first registry, which closes that world's regions for them after the linger time, and adds it to the second: a viewer crossing worlds raises `Removed` in one registry and `Added` in the other. Each WorldObjects store and each GeoForge chunk manager reads the registry of the world instance that owns it, one per instance and never static, and the streamer fills that same instance. No region of world A is ever whitelisted for a player who is only a viewer of world B.
3. **Events.** `Audience.Region(layer, position)` and `Audience.All` resolve inside the link they are sent through, and each world instance has its own link, so region chat at a position in world A reaches observers of A's region at that position and nobody in B. `Audience.Participants(list)` and `Audience.Group(id)` name people, not places, so they are not scoped to a world: a party chat reaches its members wherever they are. A process-wide announcement is a `Participants` list the sender's game builds; Networking has no audience that names the whole process, because that is the mistake this section removes.
4. **Operations.** An operation on one world of several takes `--world world:3` (`CommandLine.md`, the rule for operations on one world), defaults to the only world and refuses with the list of worlds when there are several. `regions`, `hub`, `resync`, `status` and `smoke` take it; `audit` and `simulate` read no live world.
5. **The cost.** One streamer per world means the join and resync budgets are per world unless the server sets a process budget; both exist in `ReplicationSettings`, the process budget as the cap over the sum. N3 reports bytes and observers per layer per world.

The checks: `networking smoke --worlds 2` has two halves. The simulator half runs two worlds beside a solo run each and compares digests per tick, with the same coordinates edited in both and a region chat sent from the same position in both. The PlayMode half loads two scenes with their own physics scenes and adds a region chat that must reach only its own world's observers, a viewer in world A that must not wake or load anything in world B, and the falling body of the next section. LV5's MmoServer takes the region chat and the falling body as steps (claim 12).

### One clock

Core's `Tick` is PurrNet's tick when PurrNet is installed. There is one clock, PurrNet's, and Networking holds no second one: it does not count time or run its own steps, and `ServerClock` holds no offset of any kind. The clock that counts steps is Core's `TickClock` (decided 2026-10-24), started with one call in every game; `ServerClock`, the event link and the schedule take the clock they are given and never create one, and the intent ledger is a plain Core class a game creates. It stores a scheduled event as a Core `Tick` and fires it on reaching it (below). This amends the checkpoint 3 answer, where `ServerClock` read a per-world epoch.

How the bridge binds them. Core's world clock reads a tick source (the default advances once per fixed step for a game with no network). `PurrNetTickSource`, in `Spellbound.Networking`, advances Core's `Tick` from PurrNet's tick on `tickModule.onReliableTick`, which PurrNet raises once for every tick it counts. The normal `onTick` is not used: past `maxTicksPerFrame` PurrNet still counts the tick and raises the reliable events but skips the normal ones (`CoreModules/Ticks/TickManager.cs:204-232`; the first draft hooked `onTick` and would have lost every tick past the cap). `syncedTick` is the server's `localTick` on the server and the client's estimate of it on a client (`TickManager.cs:20-28`). The rate is PurrNet's, `NetworkManager._tickRate` (default 20, `Managers/NetworkManager.cs:82-83`) with `tickDeltaDouble` as the step (`TickManager.cs:73`); the world's tick step in seconds is read from it and never set twice. It is the tick's step and not the physics step: they are different cadences ("Stepping each world's physics").

How a joiner starts. The spawn payload hands the joiner the world's elapsed seconds and the PurrNet server tick they were taken at: zero seconds for a new world, the saved duration for a restored one (a save holds seconds and no rate, decided 2026-10-24). The joiner converts the seconds to ticks at its own rate once and sets one private shift, `elapsed ticks minus that server tick`, inside the adapter. Core's tick is then PurrNet's synced tick plus the shift, so a joiner needs no tick count from the host and transit time does not skew it. The host sets its own shift the same way when it loads the world (zero for a new world). The shift never changes in a session and lives in the adapter only, because PurrNet's `localTick` is a 32-bit count that starts at 0 when the server starts and has a private setter (`TickManager.cs:15`) while Core's `Tick` is 64-bit, and advancing by differences alone would drift upward on every backward sample. Several worlds in one process share PurrNet's one tick and hold one shift each. The 32-bit count wraps after about 6.8 years of one server session at 20 Hz (computed).

What a client sees. PurrNet overwrites a client's synced tick at each clock-sync sample (once a second by default), rounded to whole ticks, with no smoothing (purrnet skill, `movement-and-time.md`, Ticks). The adapter never lets Core's tick go backwards: a sample that lowers the value holds the tick until the count catches up. Ticks are raised from Unity's `Update`, at most `maxTicksPerFrame` per frame (default 5) with normal callbacks (`TickManager.cs:133`); a tick beyond the cap skips the normal callbacks of identities and listeners and the observation `ticks skipped` counts them, but Core's tick still moves for it. A client compares against `syncedPreciseTick` for the fraction. All of this is source-read and not run; the shift, the hold rule and the cap are checked by the second-process test in the clock story of N4.

When an event fires. A scheduled event due at tick T fires in the clock stage of the first world step that sees Core's tick at or above T (step 1 of the world step: it reads the tick source, then runs the due events). It fires once, in order of due tick and then of scheduling, whether or not the tick it was due at had its normal callbacks, and it is told how many ticks late it ran. It is never matched against a single tick, so a tick that a hitch swallowed delays the event and never loses it. It fires from the world step, not from PurrNet's tick event, so it always runs at the same place in the order of clock, scripts, one `Simulate`, stepped event, whatever frame it landed in. Two worlds sharing a process each fire their own schedule in their own step.

Three time bases, and a hitch. Unity's fixed steps run in game time and are limited per frame by the project setting Maximum Allowed Timestep, 0.3333 s in both games (`TimeManager.asset:7`; Unity manual, Time settings: "Physics calculations and `FixedUpdate` events will not be performed for longer time than specified"). PurrNet's ticks run on unscaled wall time with no limit on how many it counts (`TickManager.cs:204`). Core's tick is PurrNet's count plus the shift. After one 500 ms frame at 0.02 s per step: Unity runs about 16 fixed steps (0.3333 s over 0.02 s, rounded down) and gives up the rest; PurrNet counts 10 ticks (0.5 s over 0.05 s), raises the normal callbacks for 5 and the reliable events for all 10; Core's tick moves by 10. The simulation clock has advanced 0.5 s and physics 0.32 s, so they differ by about 0.18 s from then on (computed), which is what Time.time does against wall time in any Unity game after the same frame. The design takes this as it is and says so: timed things (timed modifier sets, the intent ledger's grace time, binding and rescue timeouts, a world's elapsed seconds) follow the tick, the time players and operators live in; bodies follow Unity's physics, which refuses to spiral. The world instance's driver reports `physics_behind_clock` per world (the seconds it stepped against the seconds the clock advanced since the world loaded), so the difference is a number. A forced catch-up, as other games run it, is held for a later discussion once the games iterate; it is not decided against. The figure for that discussion: closing the 0.18 s of the 500 ms frame takes 0.18 s over 0.02 s, 9 extra steps in the next frame (computed), a longer frame that risks the next hitch. For now physics falls behind and the lag is reported.

A frame cap below the tick rate drifts nothing. At 15 frames a second (66.7 ms a frame) Unity runs 3 or 4 fixed steps and PurrNet counts 1 or 2 ticks a frame, both inside their limits (computed); the fixed steps of one frame all read the same Core tick, and the tick then jumps by one or two at the next frame. That is expected, because a tick is not a step count. Below about 3 frames a second (over 0.3333 s a frame) Unity's limit starts to bite every frame and the case above applies every frame. A second world that overruns slows every world in the process, because Unity's one fixed loop calls every driver; the capacity report sums `physics_step` over worlds so the shared loop is a number.

The N4b clock test reads the tick rate and the fixed step from the settings, states its three cases in seconds and derives their tick and step counts from those two values, so changing either setting changes no line of the test. The cases: a 500 ms frame (events due inside it fire once each, in due order, late by the right number of ticks, none lost), a frame cap of 15 a second (no drift between elapsed seconds and ticks over 600 ticks, computed 30 s), and a second world whose step is made to overrun (the first world's `physics_behind_clock` grows and its events still fire on time). It records `physics_behind_clock` in milliseconds per world as a trend and gates on nothing about it. The MmoServer stranger (LV5c0) runs the same cases and waits for N4b.

### Stepping each world's physics

The world instance steps its own physics scene, once per fixed step (decided 2026-10-24), as the map servers of the big MMOs run their own loops. Networking steps nothing: its clock advances no physics, calls no `Simulate` and only delivers messages.

Why someone must. Unity steps only the default physics scene by itself; a local physics scene made with a `LocalPhysicsMode` "does not simulate on its own and is stepped by script" (`Unity.md` ledger row S40, read through search excerpts). PurrNet does not step it either: a search of `NetworkingDev/Library/PackageCache/dev.purrnet.purrnet@3e107d88dcfc/Runtime` finds no `Simulate(` call. So the driver is the world instance's: a component with the latest execution order that calls `PhysicsScene.Simulate` once per fixed step on its own scene, after the scripted reference frame poses are written and the riders' bindings read them (claim 13; Runtime and WorldObjects own the driver and its story). With one world on the default scene nothing of ours runs, unless the process is in script mode (below).

Two cadences, both settings. The tick rate (PurrNet's `_tickRate`) and the physics fixed step (`Time.fixedDeltaTime`) are settings read once at start; nothing in Networking is derived from either as a constant, the audit reads both and prints their ratio, and changing either changes no code and breaks nothing. 20 ticks a second and 50 fixed steps a second are the starting values the games run today (`SaboteurDev/ProjectSettings/TimeManager.asset:6`, `CorsairsIsleDev/ProjectSettings/TimeManager.asset:6`, `SaboteurDev/Assets/_Project/Scenes/StartScene.unity:2922`, `CorsairsIsleDev/.../NetworkManager.prefab:58`); the figures below are computed at those values and are the developer's to move by need. The driver passes `Time.fixedDeltaTime` to `Simulate`, never the tick's step. At the starting values that is 2.5 fixed steps for each tick, neither a whole number of the other, and they need not agree. What needs a tick (timed sets, a scheduled event, the ledger's grace time, the world's elapsed seconds, a flush) counts ticks; what needs a step (bodies, riders, reference frames) counts fixed steps. Without PurrNet the default tick source advances once per fixed step, so the two coincide there and a game with no network sees one rate. A driver that passed the tick's step would run a second world's physics too fast (at the starting values, 0.05 s of physics every 0.02 s, 2.5 times), which is what the audit rule catches: the audit prints the fixed step, the tick step and their ratio as information, and fails a driver that passes `Simulate` any step other than `Time.fixedDeltaTime`.

What Networking does around it. The fixed step runs in the world instance's order (decided with Runtime): the clock stage reads Core's tick and fires the due scheduled events, scripts run, `PhysicsScene.Simulate` is called once, then a stepped event fires. The hub flushes on that event, which Core's clock raises on every fixed step, at most once per PurrNet tick: a dirty source waits for the first stepped event after a new tick, so a batch holds a whole step and never half of one, and a change waits at most until the next tick and one step after it (0.05 s plus 0.02 s at the games' rates, computed). A world with no step driver of ours flushes on PurrNet's tick event, which Unity raises from `Update` after the frame's fixed steps (Unity manual, order of execution), so it also reads the last completed step.

Other values of the two settings, priced for the developer to set by need (computed from this file's figures, the framing being 5 B of hub framing plus the 13 B left of a 21 B module RPC with an 8 B payload, about 18 B a flush; N2 measures the 50 a second row once; nothing depends on the outcome):

| Way to make the rates agree | What it asks of the games | Price |
|---|---|---|
| 20 ticks and 50 steps (starting values) | Nothing: PurrNet is at at 20 ticks, physics at 50 steps; both are settings | An event runs in the first world step after its tick, at most 0.02 s later; a change waits up to 0.07 s to flush |
| PurrNet to 50 ticks a second | `_tickRate` 20 becomes 50 in both | Up to 2.5 times the flushes: up to 540 B/s more per observer per busy region (30 more flushes of 18 B), 3.8 KB/s for a lobby of 8 with one busy region; a NetworkTransform's smoothing buffer (`ceil(tickRate x 0.15) x 2`, `NetworkTransform.cs:305`) is about 2.5 times larger. | Fixed step to 0.05 s | `Fixed Timestep` 0.02 becomes 0.05 in both | All physics and every `FixedUpdate` at 20 a second: 36 files under Saboteer's Assets and 16 under Corsairs' mention `FixedUpdate` (grep). The feel cost is not measured, and Saboteer puts local feel first |
| A tick of 25 a second | `_tickRate` 25 in both; two steps per tick | 1.25 times the flushes: up to 90 B/s more per observer per busy region; the only rate that is a whole number of 0.02 s steps without moving physics |

When a world predicts. PurrDiction's `PredictionManager` (one per scene) sets `Physics.simulationMode = Script` for the whole process when it wakes (`dev.purrnet.purrdiction@6f49a3b2846e/Runtime/Core/PredictionManager.cs:130-134`), sets `Time.fixedDeltaTime` to its tick step (`:561-564`) and steps its own scene's physics with `Simulate(delta)` inside its prediction pass (`:1897-1901`). Read in source, not run, three consequences follow. The scene that holds a manager is stepped by the manager, so the driver must leave it alone or that scene is stepped twice. The default scene stops stepping by itself in script mode, so a world on the default scene then needs the driver too, which the sentence "with one world on the default scene nothing of ours runs" denies. And the fixed step of the whole process becomes PurrNet's tick step, so every other world's driver steps at the tick step and the two cadences are one cadence in that process. The rule for the driver, decided on 2026-10-24 and proved by N10 before L3 freezes it: it steps a world's scene unless a `PredictionManager` lives in that scene, and it steps the default scene when the process is in script mode. A process that predicts one world and runs others therefore works, at the price of physics at PurrNet's rate in all of them; a game that cannot pay it keeps prediction to a process of one world. Question 3 in "Decisions" asks whether to adopt the rule.

Cost. The capacity report records `physics_step` per world, reported by the world instance's driver as a Cost in milliseconds, next to the body count and `physics_behind_clock`, also per world, so a second world's price is a number and not a claim.

### The far channel for object changes

Status, 2026-10-24: decided as one planning story now (World's W6.3, counted in W6 and not again here; N8 is its name in this file and holds no story) and an epic of its own (N9) after the far-field renderer is measured. The design below is what the planning story starts from; nothing here is built before that measurement.

The problem. Instancing draws far trees from regenerated placements, and only deviations are replicated, so past the population layer a chopped forest stands again and a player-built house is missing. Replicating those regions at a 2 km radius would be 16 regions each way: 33 x 33 = 1,089 regions per player on a surface and 35,937 in 3D (computed), each a PurrNet identity with a whitelist entry.

The design. A third layer, `horizon`, replicates the picture only, in cells of 1,024 m (a value), radius 2, so a player has 25 identities on a surface or 125 in 3D (computed) reaching about 2.5 km. Its one source, `PictureSummarySource` (in `WorldObjects.Networking`), writes per cell two lists keyed by id: placement rows no longer drawn, and added rows that are drawn (preset, quantised pose). It carries no data and no modules. It flushes every 100 ticks (5 s at PurrNet's 20 ticks a second), so a change appears at distance within that interval plus transit; that bound is a value, not a measurement. Instancing draws a region from live rows when the population layer holds it, and otherwise from the regenerated base minus the removed ids plus the added rows; the overlay stays until the live region is ready, so nothing pops back. The client-side store of those lists is a seam on WorldObjects that Instancing reads (claim 4). Dug ground reaches a far client through GeoForge's coarse edit summary, bound to the same layer prefab, so terrain and objects share one identity per cell; felled and placed objects reach it through the far summary contract. Who may write a voxel edit stays the per-source setting, and `GeoForge.Networking` adds no default of its own.

The cost, computed. A removed id is at most 8 B before delta coding, so a cell where a crew chopped 2,000 trees is at most 16,000 B in its snapshot, paged at join, then about 8 B per new change; at 20 observers and 10 trees chopped in a flush that is 20 x (80 + 5) B per 5 s, 340 B/s. Egress is observers times bytes, as for every layer. N3 reports bytes and observers per layer, the horizon layer next to terrain and population.

### Saving on a server

The line gave this area "Persistence's storage seam not blocking the server tick". The loading half is in "How it works", step 1. The saving half cannot be closed inside this area, and what follows is what this area requires of the save path and what it measures.

1. A save is never one synchronous pack of every section on the simulation thread. Each section owner hands over, on the tick and inside a per-tick budget, either a consistent copy or a list of dirty ranges; packing and storage run off the simulation thread behind Persistence's storage seam. The capture contract is Persistence's design (L8) and is filed as claim 5.
2. What Networking supplies: the dirty information it already keeps (the regions whose sources changed since a save), readable through WorldObjects' read-only region view, so a save writes changed regions and does not rewrite the world.
3. The budget is a setting and a check. Observations `save slice milliseconds` and `ticks over budget` are declared through Core. LV5's MMO server project runs a synthetic world with a save in progress and fails if any server frame over 20 ms is attributable to a slice.
4. Packing throughput is unmeasured. N3 measures bytes per millisecond for instance and edit sections on its synthetic world before L8 chooses between copying memory and slicing the walk. No figure is claimed here.

### Installing PurrNet

PurrNet is Networking's one third party (Line rule 6). It is not on a registry: both games install it by git URL in the manifest, `https://github.com/PurrNet/PurrNet.git?path=/Assets/PurrNet#dev` (`NetworkingDev/Packages/manifest.json:16`, `CorsairsIsleDev/Packages/manifest.json:30`), and a `package.json` cannot declare a git dependency (Unity manual, "Git dependencies", as `Workflow.md` records). So Networking treats PurrNet the way the line treats a sibling package.

1. `Spellbound.Networking` and `Spellbound.Networking.Editor.Adapter` carry a `versionDefines` entry on `dev.purrnet.purrnet` that defines `PURRNET` over a bounded range, and `defineConstraints: ["PURRNET"]`. With PurrNet absent they are not compiled and the project opens normally. Every assembly that references `Spellbound.Networking` (Studio.Online, a game's) carries the same constraint. The data bridges reference `Replication` only, so they compile either way. Whether a constraint on a symbol defined by `versionDefines` skips an assembly cleanly is read from the manual (Line rule 2 cites the same pages) and is the first story of N2 to prove.
2. `Spellbound.Networking.Replication`, its simulator and its tests do not need PurrNet: a stranger runs the protocol suite before installing it.
3. `Spellbound.Networking.Editor` holds the bootstrap, built like every package's Core bootstrap (Line rule 16). With PurrNet missing, the Networking tab of the Spellbound window says so and offers `Client.Add` with the address and tested range from the catalogue row, after the window's Git client check.
4. Rule D1 (`package.json` dependencies equal what the assemblies use) gets one written exception, claim 6: a third party named in the package's sentence, gated by a `versionDefines` constraint and recorded in the ledger with its address and range, is checked against the ledger and the gate, not the dependency list.
5. A listing is an undated story after both games run on the line. Whether the Asset Store's dependency validation accepts Networking with this gate and no declared dependency is area 10's test, run when a listing is planned. If it does not, the listing is a question for the developer, not something this design works around.
6. The gate never fails silently. A constraint that skips an assembly gives no error, and a PurrNet that moves past the bounded range would skip the adapter, Studio.Online and a game's own networked assemblies while the project still builds. `Spellbound.Networking.Editor` is not gated, so it reads the installed version of `dev.purrnet.purrnet` through the Package Manager's package info at each domain reload. When Networking and PurrNet are both installed and `PURRNET` is not defined, it logs an error through Core that names the installed version and the tested range, the Networking tab shows the same line in red, and an `IPreprocessBuildWithReport` stops the player build with that message (Unity scripting API, `UnityEditor.Build`). A project with no PurrNet at all stays quiet: that is the supported state of a project that does not network. The range is written once, in the catalogue row, and rule D3 compares each asmdef's `versionDefines` range with that row. There is no list of required bridges: a second list is a second place to drift, and the two installed packages are the declaration. PackageCheck's L2 does more than compile the pair at their latest versions: it asserts that `PURRNET` is defined there, so a PurrNet major that leaves the range turns the line's own test red the day it lands (claim 35). The first story of N2 proves the constraint behaviour, the version read and the build stop in one probe; the story count does not change.
7. The floor: PurrNet declares `unity: 2022.3` (`package.json:10`), so the line's 6000.3 floor holds for the adapter. Networking declares no Burst or Mathematics package; Core's writer is its only numeric dependency. The 6.3 test row runs the protocol suite, which needs no PurrNet; the adapter suite runs where PurrNet is installed.

### What a game that predicts gets

- Every batch carries a sequence and the server tick it was flushed on, and the hub raises `BatchApplied(sequence, serverTick)` on the client, so a prediction layer can order replicated state against its inputs.
- Applying a batch is idempotent by sequence. A replayed simulation tick re-runs simulation, never a network apply, so a consequence cannot fire twice because of Networking. Resolve handlers run on the authority only (Line: WorldObjects separates change from consequence).
- Ids a client names are minted in its own lease and checked by the server, so client and server agree on what an object is called, and a rejected one is rolled back, never renumbered.
- Boundary rule: a thing is predicted by a prediction manager or replicated by a hub, never both. The predicted world stays small (the purrdiction skill, Choosing, step 5); everything else is a source.
- What it does not give: movement prediction for a world. See the limits.

## Directions

**A. Pure protocol core, one hub per region carrying every source, interest into PurrNet visibility (taken).** Wins the scenario on all three columns; testable without a second process; one wire layout per region instead of one per source.

**B. Our own subscription layer, no identity per region (rejected).** Alternative to A. The server keeps per-viewer region subscriptions and sends region batches as TargetRpcs to lists of subscribers; clients hold plain region objects. It removes the cost of one PurrNet identity per region (the spawn packet of about 70 to 80 B plus FinishSpawn, `costs.md`, and a whitelist entry per pair). Rejected because the approved line says the region reaches players through PurrNet's visibility (Line, Networking row: who observes an identity is PurrNet's), because it rebuilds spawn, visibility and late-join machinery PurrNet already ships, and because it forks the game from every PurrNet tool. Revisit if N3's measurement shows identity or whitelist cost dominating a shard's budget; then it is a line change, not a quiet swap.

**C. Lift `StateSyncModule` into a package and keep one module per source (rejected).** Alternative to A. The smallest step. Rejected: it moves the copy rather than removing the repeats, keeps one RPC and one positional module per source (a layout nothing checks), keeps `byte[]`, keeps the late-join design whose defects the snapshot lists, and cannot be tested for remote behaviour without a second process.

**D. PurrNet's own Sync types (`SyncDictionary`, `SyncList`, `SyncVar` of structs) (rejected).** Alternative to A. Zero code. Rejected by cost: every change is its own message carrying the whole value, every late joiner costs one TargetRpc per field, a `SyncList` indexer write is sent twice and the whole list follows a tick later (`costs.md`, Sync types), and structured data would have to use PurrNet packing, against the studio rule. Right for a few small rarely changed values; the hub is for the rest.

**E. The replication contract in Core instead of in Networking (rejected).** Alternative to the bridges. Persistence could also write dirty sections through it. Rejected by Line rule 4: Core grows only when two packages need the type, and Persistence needing it is a guess. Trigger to revisit: Persistence's design asks for dirty-section writes; then the pure assembly's contract moves to Core and the bridges lose one reference.

## Limits

- No capacity figure is claimed: shard size is a measurement N3 owns, with the interest map and the flush fan-out driven by synthetic viewers, because one machine cannot drive thousands of real connections (one NetworkManager per process, purrnet skill).
- The order between the spawn packet's inline snapshot and the first live batch is source-read, not shown at runtime; gap detection is the safety net, and N2 includes a second-process test.
- Whether PurrNet's default visibility follows scene membership is not read; the design whitelists only its own world's regions, and the two-world smoke reads the answer first.
- Stepping a second world's physics assumes `PhysicsScene.Simulate` may be called from a late-ordered `FixedUpdate` with the fixed step; the manual page is read by the story that builds the world instance's driver (Runtime and WorldObjects), and the ledger records it as read through search excerpts only. Networking steps nothing.
- Host mode's wait on a client's own container is computed from the tick step and the lobby's ping, not measured, and is the cost only of a game that chooses host or server mode; owner mode's half round trip before others see a change is computed too; no Steam round-trip figure exists in this pitch.
- In owner mode two writers of one key within a round trip end in the host's arrival order, and the loser sees its own value first and the winner's after; the simulator proves the end state, not that the flicker is acceptable to a player.
- One clock is source-read: the adapter's shift, the rule that a client's tick never goes backwards, and the per-frame tick cap are checked by the second-process clock test in N4b, not run. PurrNet's 32-bit tick wraps after about 6.8 years of one server session at 20 Hz (computed). The hitch case (a 500 ms frame, a cap of 15 frames a second, a busy second world) is computed in "One clock" and run by the same test.
- PurrNet's ticks run on unscaled time and Unity's fixed steps on game time (`TickManager.cs:204`; Unity scripting reference, `Time.timeScale`: with a time scale of 0 `FixedUpdate` stops): a game that pauses with a time scale of 0 stops physics while ticks and scheduled events go on. How each game pauses is not read here.
- Unity has one fixed loop for the process, so one world whose physics overruns the fixed step slows the steps of every world in it; the capacity report sums `physics_step` over worlds against the fixed step, and no design inside Networking removes the shared loop.
- A reference frame keeps its `ReferenceFrameId` across a respawn only if its owner derives it from a stable identity (unchanged).
- A restored save older than the lease record is refused by name, through the section header of the lease record, and not repaired; the lease record and the world are restored together. The lease record holds no tick rate.
- One region is one PurrNet identity, so identity count is the shard's scale cost; direction B is the fallback and a line change.
- Receivers allocate one array per batch with `ByteData`; `BitData` is a view whose lifetime ends with the callback (`PackByteData.cs:86-101`), measured in N2, not assumed.
- Core's writer, buffer and limit work is in progress; N1 cannot finish before it, and the names here are provisional.
- Movement for a world at MMO scale is a gap: PurrDiction has one predicted world per scene, a transcript that grows with players squared and no interest management (purrdiction skill, MMO), and PurrNet has no prediction. Owner-authoritative movement with server checks is the only built-in answer; the gap is named here and not built around.
- PurrDiction's physics takeover sets the simulation mode and fixed timestep for the whole process (`physics-and-hits.md`, purrdiction skill), so a process that hosts several worlds can also run PurrDiction physics in one of them only under the ownership rule in "Stepping each world's physics", at the price that every world then steps at PurrNet's tick step.
- A server running many worlds loads each as a PurrNet scene with `PurrSceneSettings.physicsMode` set (`CoreModules/Scenes/ScenesModule.cs:44`, `SceneHistory.cs:82`) so each has its own physics scene; Unity creates one only when a scene is loaded with a `LocalPhysicsMode` (Unity 6000.4 scripting reference, `LocalPhysicsMode`). Character's support probe must cast through the world's own physics scene.
- The operation gateway is a static RPC for the sake of needing no scene object; the codegen builds a static packet with `RPCInfo` (`CoreModules/RPCs/RPCDeltaPackingHelpers.cs:29`), but that `info.sender` arrives authenticated on a static RPC is not yet shown by a test, and the fallback is the player broadcast, whose subscriber receives the authenticated player.
- Moving a player between processes (a shard border) is not designed and not decided, and no pitch is planned. Networking is per process; the one rule on player keys holds, and the measurement in N3 stays.
- The lease layout is 1 kind bit, 31 lease bits, 32 counter bits, fixed from Saboteer's first Steam release built on the line, the first ship to a customer. The sizes are arithmetic on assumed rates (2,000 creations a second from the server, 1,000 new predicting players a day), not measurements of any game.

- Saving is not closed here: the capture contract is Persistence's (L8) and packing throughput is unmeasured. A full save as one synchronous pack stalls every connected player for as long as it takes beyond the tick's spare time; this design requires that it never be one, and measures the slice.
- Whether the Asset Store accepts a listed Networking whose adapter is gated on an undeclared PurrNet is area 10's test, run when a listing is planned; the listing is undated.

Fixed.** The reader is right: the streamer, the viewer registry, the lease table, the reference frame map and the event link were all written as if there were one world, while every other area keeps state per world. **2. Physics and the tick fall out of step under a hitch (serious). Fixed: `ServerClock` fires on reaching a tick, not on matching it, once and in order, in the clock stage of the world step, telling the event how late it ran, so an event at a swallowed tick is late and never lost; it fires on counted (reliable) ticks, which is every tick. ## Answers to the checkpoint red team

Ten findings from independent readers landed on this area in the second run. Answered in plain words: fixed in this file and the fragment, rejected with the reason, or marked as not fixable here. The author had no subagent tool, so each answer was checked against source and arithmetic by the author alone.

**1. The shard border and the id layout (serious). Fixed.** The reader is right that a slot is per process and per session. Ids no longer carry a slot, a region or a process. An id is a kind bit, a 31-bit lease and a 32-bit counter, and a lease is issued once in a world and never again. Two processes mint under different leases, so they cannot mint the same id; a region handed over arrives with its ids intact; there is no per-region counter to move. The handoff itself is not designed or decided; the one rule on player keys holds. The layout is an opaque 64-bit type, so changing it before the first release is a re-save and not an API break. The reader suggested reserving authority bits or going to 64 bits; this does both.

**2. PurrNet has no install route (serious). Fixed, with one part unverified.** The adapter and its editor half compile only when a `versionDefines` entry on the PurrNet package defines `PURRNET`, the way Core is treated. The protocol assembly and its simulator compile without PurrNet. The bootstrap offers PurrNet's address from the catalogue. Rule D1 gets a written exception, filed as claim 6, for one third party named in the sentence. Not verified: that the manual's constraint behaviour is exactly as read (the first story of N2 proves it) and that the Asset Store accepts a listing with an undeclared gated dependency (area 10's test, run when a listing is planned, which is undated). If the store refuses, listing Networking is the developer's question; nothing here works around it.

**3. IViewerSource has two owners (serious). Fixed as suggested.** It moves to Core with a small default registry. Three packages use it, which is Line rule 4's test. A mining game without WorldObjects compiles; a farming sim without Networking wakes instances by the registry. `ViewerCellChanged` is withdrawn because a cell needs a geometry, which Core does not have; consumers compute the cell from `Moved`. Filed as claim 2.

**4. The 16-bit counter was never sized (serious). Fixed.** Sized in "Identity: leases": a 32-bit counter per lease is about 24.9 days at an assumed 2,000 creations a second from the server, and exhausting it is a lease roll with an observation at 90 percent. The farming host's 500 plots harvested 132 times use 66,000 ids. Reuse is removed: an id is never handed out again, so a saved reference, an intent, a journal line or a sleeping record that names a deleted instance finds nothing, never a new object. Saved ids need no remapping because the next lease is saved with the world and every new lease is above every saved id.

**5. An object that moves region has no design (blocker). Fixed in this area's part; two parts are claims.** The id is independent of the region, as the reader suggested. "An instance changes partition" gives the departure and arrival records, the client rule for any order and for observing A only, B only or both, the in-flight joiner, a margin against border flicker, the placed-object case, the simulator cases the reader asked for, and what replaces `DynamicInstanceSyncModule` (create, delete, the switch as a flag, transfer). Not fixed here: the store's `Transfer` and the margin belong to WorldObjects (claim 3), and the per-tick position of a walking creature stays outside the hub and is an open per-mover choice, stated in the limits.

**6. The 16-bit counter per region (minor). Fixed with finding 4.** It named the same defect. It also asked for a generation or epoch per scope persisted with the region; this design uses a lease instead because a generation attached to a region changes meaning when a thing changes region, which finding 5 requires. Decided, 2 settles it.

**7. Far trees go stale (serious). Fixed.** A third layer, `horizon`, replicates the picture only, with a coarse summary keyed by placement id, 1,024 m cells at radius 2, flushed every 5 s by default. It is priced against the 1,089 and 35,937 identities of a radius-16 near layer, and N3 reports it next to the near layers. The store the client keeps and Instancing reads is a seam filed as claim 4. The staleness bound and the 8 B per removed id are values and an assumption, not measurements.

**8. Instance changes bound to the radius-3 layer (serious). Fixed.** The reader is right and it was a mistake in the After example: the instance source and the voxel source shared one prefab. They are now separate prefabs on separate layers (instances on population at radius 1, voxel edits on terrain at radius 3), the example and the cost table say so, and the receiver ratios are computed (5.4 times on a surface, 12.7 times in 3D). N3's benchmark reports bytes and observers per layer so a wrong binding shows as a number. The change to World.md's units table is claim 4. The cell size in the example was also 64 where the world's chunk is 128; it is 128 now.

**9. Saving on a server (serious). Partly fixed, partly not fixable here.** The requirement is written down: a save is never one synchronous pack on the simulation thread, owners hand over a copy or dirty ranges inside a per-tick budget, packing and storage run off the thread, and LV5's MMO server project fails on a tick over 20 ms attributable to a slice. Networking supplies the dirty-region information and the observations, and N3 measures packing throughput. The capture contract is Persistence's design in L8, which no area owns and which this area cannot edit (claim 5). Until it is designed and measured, the claim "the save does not block the tick" is a requirement, not a result.

**10. The 16-bit per-player counter (serious). Fixed with finding 4.** The third report of the same defect. Its suggestion of a 32-bit counter inside a 64-bit id is what the layout does, and its reuse rule is "never reuse".

Could not fix, summed up: the handoff between processes (not designed, and no pitch); the capture contract for saving (Persistence's design); the store's transfer operation and the far deviations view (WorldObjects and Instancing, as claims); the Asset Store's behaviour with an undeclared gated dependency (area 10's test); how a walking creature's position reaches clients (the game's pitch).

Could not check: PurrNet behaviour across two peers (nothing here was run; the join order is source-read), the cost of a whitelist call or an identity at thousands of players, and any Core API that is still being written.

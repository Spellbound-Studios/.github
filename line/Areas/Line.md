## The scenario, walked

A new engineer joins. They read one screen: four kinds, twenty-three packages on a map with every arrow pointing down, and a four-question procedure. Then they answer, without asking anyone:

| Question they are asked | What they say in ten minutes | Why |
|---|---|---|
| Where does a ragdoll go? | Character, because it is a body falling, which any game with bodies wants | A mechanism a stranger wants: library. The sentence that covers bodies is Character's |
| Where does the Steam lobby go? | Studio.Online, because Steam is a service we chose | Glue for a chosen service: Studio. Not a game's, because two games want it |
| Where does "whispers are pink" go? | Studio.Online, as a Switchboard profile asset | A value for a library seam, the studio's taste |
| Where does the guild tab go? | Corsairs, as its own profile | It names one game's world |
| Where does a sync module base class go? | Networking, never Core | Core knows nothing of connections (rule 14) |
| Where does a new voxel generation pass go? | WorldForge, never GeoForge or Pro | One package owns generation; GeoForge turns data into meshes |
| Where does an item's affix tooltip line go? | The widget is UI's; an affix as text is Modifiers' UI bridge; which affixes we show and in what words is Studio.Gameplay's | A mechanism and its value separated first |
| Where does a tenth package for a new concern go? | A new repo from the template, one kind, one sentence, bridges downward only | Requirement 18 |

That is the test the rest of this file must pass.

## Kinds

Four kinds, because four different answers to "what may it depend on and what may it own" exist. A fifth would have the same answers as one of these.

| Kind | What it is | May depend on | Must not own | Count |
|---|---|---|---|---|
| Foundation | The one package every other package shares | The Unity engine modules only. No Unity package, no third party | Anything drawn, any scene object, any mechanism fewer than two packages need, any knowledge of connections | 1 |
| Library | One sold mechanism, usable by a stranger | Core; the Unity packages its sentence requires; the one third-party package its sentence names; another Spellbound library only when its sentence names it (hard) or through a bridge assembly compiled only when that library is installed (optional) | A second concern; a value a game tunes; a scene layout, bootstrap order or manager; anything the consumer cannot replace | 20 |
| Tool | An editor-only workflow with no runtime of its own | Core; a library hard only when its sentence names it, otherwise a bridge, the same as a library (rule 2) | Runtime code; the data format of a library it checks or authors for | 2 |
| Studio | Private, installed by our games, our one way of using the libraries | Anything, including Steam and PurrNet | A mechanism a buyer would want; a package's internals (`InternalsVisibleTo` is forbidden) | 5 packages in 1 repo |

Games are not a kind. A game installs what it needs and edits nothing.

The precedents. Unreal gives each module a host type that decides where it loads: Runtime, Editor, UncookedOnly, Program (`EHostType` in its API reference). Our kinds carry the same idea one step further: the kind decides what the package may depend on and own, not only where it loads. Bevy ships one crate per subsystem (`bevy_ecs`, `bevy_render`, `bevy_ui`) and a `bevy` facade that re-exports them behind Cargo features; a consumer can depend on `bevy_ecs` alone. One package per mechanism transfers; the facade does not (see the rejected direction). Unity itself splits simulation from rendering as separate packages (Entities and Entities.Graphics), which is the shape WorldObjects and Instancing take. numpy, scipy and pandas layer primitives, operations and a front door, which is the library-design skill's layer list and the shape inside every one of our packages.

## The line

Twenty-three packages the studio publishes (one foundation, twenty libraries, two tools), five private Studio packages in one repo, two deletions. Names follow the naming rule: a package is named for its one-sentence job. The id is `com.spellboundstudios.<name lower-cased>`, the root namespace `Spellbound.<Name>`, for every package including Persistence, which drops its odd `com.spellbound` id.

### Foundation

| Package | Job in one sentence | Depends on | Must not own | Today |
|---|---|---|---|---|
| **Core** | Gives every package one vocabulary: how to log, pack bytes, identify a thing, roll from a seeded stream, place a pose in a reference frame, measure a cost against a budget, declare an operation, and validate what a designer or an agent authors. | UnityEngine modules only | Anything drawn or spawned; the world-object framework; any console view; any Unity package (Entities, Mathematics, Burst, TextMeshPro, Input System, uGUI all leave); anything that knows about connections or players | Core 1.1.9, with 62 of 124 runtime files being a world-object framework that pulls Entities, TextMeshPro, Input System and uGUI into a card game that wants logging |

Core keeps its name because the sentence is the industry's meaning of the word (`bevy_core`, Unity's core modules) and because it is the one name every consumer types first. The rule that stops it accreting again: Core accepts a type only when a second package needs it. A game or Studio wanting it is not enough; that is how the world-object framework got in.

What stays: the logger and its sinks, the tallies, packing and the bit writer the developer is adding, FNV hashing, hash and resource registries with a provider seam instead of a fixed `Resources` path (a renamed or deleted thing's old id is reported, never redirected), `SingletonManager`, weighted tables, assembly scanning. One rule on the bytes, because the same packing is the save format, the wire format and WorldObjects' instance data: a change to packing itself (the bit writer) is a Core major, and until a package ships to customers it means re-save, re-author and re-import, with no reader kept for the old layout (rule 15). What is new in kind, each because at least two packages need it and none may invent its own:

- The operation registry (`[Operation]`): the one way every package declares what an agent or a person can call. Area 2 designs it.
- The observation model: meters and counters every package reports through, each with a cost declared against a budget and a quality level the consumer may set, so Horizon, Instancing, Volumetrics and GeoForge degrade under one policy instead of four knobs. Area 3 designs it with Diagnostics; the policy that picks levels is the game's or Studio's.
- The simulation vocabulary: a tick, a seeded random stream with no engine call inside it, and an identity allocation seam whose default hands out ids locally and whose authority implementation lives in Networking. WorldObjects, Modifiers, WorldForge, Places and Networking all need them, and the rule that `Time.time` and `UnityEngine.Random` never appear in a simulation assembly is only enforceable if the replacement exists. This is the seam that makes "a game that never predicts pays nothing" true. Area 3 and area 6 design against it.
- The reference frame vocabulary: a thing that moves and carries others is a `ReferenceFrame`, never a frame, because a frame is what Unity renders (decided 2026-10-24). Core holds the noun, its id (`ReferenceFrameId`), a `ReferenceFrameDirectory` per world so a reference frame is found by its id, and an up field whose default is world up. The binding that remembers which reference frame a body stands on and keeps its offset (`ReferenceFrameBinding`) is coordinate math and lives in Character.Body, not here. WorldObjects stores poses in reference frames, Navigation paths across them, TetherShop's elevator riders are Character riding a reference frame. The underwater game replaces the up field and installs nothing that assumes a sky. Area 3 designs riding.
- The authoring contract: a definition type in any package is a ScriptableObject that implements Core's validation contract; Core.Editor runs the validation and writes the one report an agent reads, the same check fires in the inspector, and the asset is made through Unity's own pipeline (the inspector, or the Unity CLI's asset commands and `run_script`) so there is one form and never a second. Each package supplies its own validator (is this ore pocket reachable) and its own preview (draw this place) through the contract, so Core never knows what a voxel is. A package adds its own check to a definition type another package owns through the check seam in Core.Editor: one interface, `IDefinitionCheck<T>` (the spelling decided 2026-10-24), one attribute and the lines that find and run registered checks, so Navigation reports an unreachable ore deposit on a Place without Places ever learning its name, and Core never changes for a new package (decided 2026-10-24). Requirement 15 asked this of every package; the ScriptableObject is the format, by decision 4.
- An audience on every operation: an operation declares who may call it (anyone, the authority, a developer build) as a tag with no connection knowledge behind it. Networking enforces the tag where a call crosses the wire, and UI's text surface hides what the audience forbids. Area 2 designs the tag, area 6 the enforcement.
- Widened at the developer's review (2026-10-23), each because two packages asked for it and none is an opinion a game replaces: counters, guards and the intent ledger (area 3); the ground vocabulary, a surface source and an occupancy query (area 5); the viewer source (area 6); the package identity asset and the severity scale of a finding (area 7); four editor controls in Core.Editor that every package's inspectors and windows share (area 11). Rule 17 governs how Core changes once it has shipped.

The parse of a typed line into an operation call is pure and stays in Core; what draws the line typed is UI's. Pooling is the one thing Core offers today that Unity also ships (`UnityEngine.Pool`, an engine module): requirement 4 says Unity's wins unless area 8 measures a reason, so `ObjectPool` is listed with area 8 and not in the sentence.

Measured reason: in both games no Spellbound assembly starts compiling until `Unity.Entities.Graphics` finishes, at 27.9 s of a 35.4 s wall in Corsairs and 16.1 s of 20.4 s in Saboteer, because Core references it. A Core that depends on the engine alone could start at the `UnityEngine.UI` mark, 6.4 s and 3.6 s. Core's own work is under 3 s. The gain is whole for every dev project and every consumer without ECS. For the two games it is small, because their own code still waits for Entities.Graphics and because the line adds about forty bridge and presentation assemblies at a measured 0.2 to 0.8 s of CPU each (0.21 s for an assembly without the Entities weaver, 0.81 s as the average over today's twenty-seven), spread across cores; the wall gain for Corsairs is bounded by the 2 s between where its game code starts today and the Entities.Graphics mark. The honest claim is: L1 pays for itself in every package project and every non-ECS buyer, and costs the games nothing they do not already pay (Audit, section 6; the per-assembly figures are the audit's, the forty is a count of the bridges column).

Five, because the wishlist already asks for places shared between Saboteer and Corsairs, so the content home exists from the start. A Studio package is created only when its dependency set differs from every existing one. Studio packages follow the same two dependency rules as libraries: a hard dependency only on what every game installing the cluster needs, a bridge for the rest, and presentation in a `!UNITY_SERVER` assembly. That is what lets the MMO server install Studio.Gameplay without UI and Studio.Online without Steamworks. A cluster is opt-in per game: the seventh game that wants its own skill or magic system writes it against Inventory and Modifiers and leaves Studio.Gameplay out, and nothing in a library changes for it.

## Rules of the line

1. **One sentence, one owner.** A package owns what its sentence says and nothing else. Two sentences never cover the same noun.
2. **Dependencies are named in the sentence.** A library depends hard on another Spellbound library only when its sentence names it (GeoForge Pro on GeoForge). Everything else is a bridge: an assembly inside the package, compiled only when the other package is installed, through `versionDefines` in the assembly definition (Unity manual, "Assembly definitions", conditional compilation). A bridge's `versionDefines` expression names the range of the other package it was written for, so a version outside the range compiles the bridge out with a warning from area 7's check rather than silently; and that check installs every bridge pair at their latest versions and compiles them together, which is the line's compatibility test. Installing a package never pulls in a package its consumer does not use. Networking follows the same rule: it depends on Core and bridges PurrNet, so its protocol assembly carries no PurrNet type and all eight packages that bridge Networking target the protocol assembly (decided 2026-10-24); the split is discussed again when the package is built.
3. **Bridges point down or sideways, never up.** The layers are: Core; the mechanisms (WorldObjects, Inventory, Modifiers, StateMachine, UI, Switchboard, Persistence, Networking, Diagnostics, GeoForge, Places, Decals, Volumetrics, TetherShop); the composers, which read several mechanisms (Character, WorldForge, Navigation, Instancing, Horizon); the tools; Studio. A bridge lives in the higher package and references the lower (`WorldForge.GeoForge`, `Instancing.WorldObjects`), so no cycle can form. Between two packages of the same layer, the one whose data crosses hosts the bridge (`Inventory.UITK`, `GeoForge.Networking`, `GeoForge.Places`), and UI, Networking and Persistence never host a bridge to a data package, so they never learn its name and never become dependency magnets.
4. **Core grows only for a second package.** A type enters Core when two libraries need it, it has no engine dependency beyond the engine modules, and it carries no opinion a game would replace. Games and Studio do not count. Core's whole surface is reviewed against this rule at every Core major, because Core is the one package every buyer holds at one version. Core holds vocabulary, never a binding or a behaviour a game would tune: the reference frame noun is Core's and the frame binding is Character.Body's. Rule 17 says how Core changes once it has shipped.
5. **Unity packages are allowed where the sentence needs them**, and declared in `package.json` as floors. The floor is 6000.3: the line supports the current LTS, and the previous LTS until Unity's support for it ends. The studio edits on 6.4 and moves to 6.7 when it ships; from that move on a floor compile runs in the push gate, and area 7's check runs the tests on both LTS rows, 6.3 included. What Unity 6.7 and the first Unity 7 alpha change for the two games and the packages is summarised in `Revisited/UnityChanges.md` (checkpoint 4): Unity 7 removes the built-in render pipeline and deprecates HDRP, which confirms the URP-hard packages; 6.7 is the last Unity on Mono and Unity 7 runs on CoreCLR; Unity's support page runs 6.3 LTS to December 2027; the 6.7 LTS date is the studio's estimate, since no Unity page read gives one; nothing forces either game to change before Saboteer's demo. Burst, Collections and Mathematics, declared as packages, for any library whose sentence has a hot loop over many things (WorldObjects, GeoForge, WorldForge, Navigation, Instancing, Volumetrics); URP hard for Horizon, Instancing and Volumetrics, with no backend seam, and as the default behind Decals' seam; Cinemachine as a bridge in Character; the Unity Pipeline package as a bridge in Core for the command line, the assembly `Spellbound.Core.Pipeline`, compiled only when `com.unity.pipeline` is installed (area 2). Entities is nowhere in the line: WorldObjects' store is native columns and Instancing draws with Unity's BatchRendererGroup.
6. **One third party per package, named in the sentence.** PurrNet in Networking, Steamworks in Studio.Online. Nowhere else.
7. **A name is the job.** When the sentence changes, the name changes with it and every consumer is updated in the same change (rule 5 of `Rules.md`, no shims). Four names change here: Chat to Switchboard, Controller to StateMachine and Character, VolumetricFog to Volumetrics, Core's object folders to WorldObjects. Persistence keeps its name and takes the studio id. This is the pre-1.0 form of the rule; rule 15 says what happens after.
8. **Every package ships the same parts**: `Runtime` where the kind has one, `Editor`, `Tests` (edit and play), `Samples~` (always there, the UPM standard), operations (declared through Core, including the ones a test of the package needs), the AI context that reaches a consumer's project without copying (an `AGENTS.md` with generated operation blocks), an identity asset, a committed surface file, a documentation index, and the copyright header on every file. The front door of every package is `<Name>Kit`; a bridge assembly with a public surface carries a second door, `<Package><Other>Kit`, which `core context` lists. A default a consumer needs to run the package lives in `Runtime` as a replaceable default; an opinion lives in `Samples~` (Character's walk, run, jump and fall are a sample, because a concrete state is an opinion), and Core ships an operation that imports a sample, since the Unity CLI has none. A package lives at `Packages/<name>` in its dev project, an embedded package cloned and edited in place, once a one-story probe proves git and Git LFS inside that folder. Area 7 writes the convention and the check, PackageCheck runs it; area 2 the operations and context.
9. **Studio compiles against public surfaces only.** When Studio needs something a package does not expose, the package is missing an extension point; that is a package story, never `InternalsVisibleTo`.
10. **Nothing predicts, everything allows it.** WorldObjects separates change from consequence and keeps no presentation; Networking carries ticks and sequence numbers; nothing in Core knows a connection. A game that never predicts pays nothing.
11. **Presentation is its own assembly and never compiles on a server.** A package that both simulates and draws (WorldObjects, Character, GeoForge, Decals, TetherShop, Switchboard through its UI bridge, and the Studio packages) keeps the drawing in an assembly with `defineConstraints: ["!UNITY_SERVER"]`, the define Unity sets for the Dedicated Server platform (Unity manual 6000.4, "Dedicated Server build"). The MMO row below is built from this rule.
12. **No package relies on domain reload.** Static state is reset explicitly on play mode entry and nothing scans `AppDomain` at static construction (Persistence does today). Unity is turning domain reload off by default for new projects, a claim the OpenAI opinion makes with a citation that area 8 verifies against the 6000.4 and 6000.6 manuals before the Core stories rely on it.
13. **One form for content, one validation.** Every definition a designer or an agent authors is a ScriptableObject, made through Unity's own asset pipeline (the inspector or the Unity CLI), never a hand-written asset file and never a second text format of ours; every definition type implements Core's validation contract, and Core.Editor runs it and reports for all of them. A designer's assets keep their data in Unity's own serialization, and Core packing serves saves and the wire only, so a Place's layers are Unity fields and no asset is the only copy of packed bytes. Validation reports a stored field the type no longer has as an error. Core.Editor holds the check seam, one interface, `IDefinitionCheck<T>`, and one attribute, through which a package adds its own check to a definition another package owns (decided 2026-10-24); the stale-field error carries the stored value's text and nothing is written anywhere to keep a lost value (decided 2026-10-24).
14. **A depth budget.** No chain from Core to a game's code is longer than four links (Core, a mechanism, a composer or a bridge, Studio, the game is the longest the map allows), because every link in the chain is a serial compile. L1 measures the chain after the split; a package whose bridges would lengthen it is a line change.
15. **Before 1.0 and after.** Everything is pre-release today, so nothing is kept for compatibility until a package ships to customers (rule 5 of `Rules.md`): no old packing readers, no `core migrate`, no section migrations, no redirect table, no format versions kept as a compatibility path, no `FormerlySerializedAs`. A breaking change means re-save, re-author, re-import. Until then a package releases from a beta branch as `1.0.0-beta.N`; Core, public already at 1.1.9, takes a baseline tag and releases the rewrite as `2.0.0-beta.N`. The day a package ships to customers it is 1.0 (Core 2.0), and from then semantic versioning governs it: a breaking change is a major, a Core major is a release of the whole line because every package holds one Core, and a package whose sentence changes after 1.0 is retired and a new package takes the new sentence, rather than renamed under a buyer's feet. Buyers hold the previous major for one LTS cycle. A renamed, retyped or removed serialized field of an authored type after the first ship is a major, by semantic versioning (decided 2026-10-24). Area 10 writes the policy into the release pipeline; area 7 checks it. A game sold to players counts as shipping to customers from its first release built on the line (2026-10-24), and it ships only after the final tags of every package it installs exist, so the roadmap dates Saboteer's first Steam release after the removals Saboteer still needs (estimated June 2028, confirmed by the developer's note of 2026-10-24: Saboteer does not release until the packages are final).
16. **Core ships the Spellbound window.** Core.Editor holds one window that lists every package of the line, shows what is installed and at which version, installs or updates a free package in place through the package manager's `Client.Add` from a git URL with a path and a ref (`?path=/Packages/<name>#<ref>`; decided 2026-10-24: a buyer installs a released tag, `#v<version>`, a project the studio works in follows a branch, `#beta`, because nothing of ours is pinned, and a shipped game follows the maintenance branch of the Core major it shipped on, `#release-<major>`, never `main`; the mode is one committed project setting, and shared workflows are called at `@main`), greys out a paid package the project does not own and links to its store page, and opens documentation and samples. Every other package carries one bootstrap file that offers to install Core when it is missing, and every Core-referencing assembly is constrained on Core's define, as area 7 wrote it. The window ships with Core and installs everything else; it is how a buyer and a game get Core, and how a person sees what the line offers.
17. **Core's clock, and the release promise.** After Core 2.0, the stable tag of the rewrite above the baseline `v1.1.9`, a change between majors is additive only. A Core major happens at most once per Unity LTS cycle and ships with the line's move to that LTS, so a buyer re-saves and re-authors at most once per cycle; the roadmap carries that as a steady-state budget. The promise to a buyer (decided 2026-10-24): a major about every 12 months, the upgrade offered at a reduced cost, and inside a major a year of bug fixes and maintenance with no API break. The maintenance branch of a major is `release-<major>` in every repository, cut when that Core major's final tags are made; the tag gate compares a tag with the package's own range entry on that branch, and a fix reaches a buyer on the previous major through the catalogue's line for that Core major. The 12-month cadence and the one-major-per-LTS rule agree while Unity ships an LTS about yearly, so the cadence is a target the release calendar shows, never a gate.

## Area 1's questions, answered

**What Core is for, and what leaves it.** Core is the vocabulary the rest of the line speaks: how to log, pack, hash, identify, pool, sample, declare an operation and report a measurement. It leaves the world-object framework to WorldObjects, the console view to UI, ECS to area 8's answer, and every Unity package to the libraries whose sentences need them. The audit's compile numbers are the measured reason; the stranger test is the other: a card game installs Core for logging and saving and today receives Entities.

**What is a package and what is not.** A package is a mechanism a stranger would pay for, or an editor workflow that authors a library's content, or one of four private Studio clusters. Shared code that is the studio's opinion (equipment), the studio's services (Steam) or the studio's taste (pink whispers) is Studio and never sold. Code one game wants is that game's. The procedure in `Homes.md` beside this file decides every case in four questions.

**Who owns constructing the world, and who owns placing things in it.** Three packages, coupled in authoring and separate in mechanism. WorldForge constructs: it plans and generates data from any source and hands each kind to its builder. Places owns an authored unit of content as a bag of typed layers; a place is one of WorldForge's sources, and when a designer shapes a point of interest they shape its terrain layer (captured and baked by GeoForge's editor bridge, sculpted by Pro) and declare its object layer in one asset, then play it alone in Places' gym with the character and commands the gym profile names. WorldObjects owns what a placed thing is at runtime and instantiates placement records, whichever package emitted them: WorldForge from its biome population rules (which candidate points get ore, weighted how), Places from the object layer a designer declared. So the designer's experience is coupled (one asset, one workflow, one preview) and the code is not: GeoForge never knows what a place is, Places never knows what a voxel is, WorldObjects never knows what a biome is, and population rules have one owner, WorldForge. The developer's suspicion was right about the workflow and the answer is to couple it there only.

**Where the developer console lives.** Nowhere as a package. Its registry is Core's operation registry, the one every package already declares into for the command line, so the console and the command line are two views of one list. Its parser is Core's. Its view is UI's text surface. Its commands are each package's operations, Studio.Tools' house set and the games' own. Chat's second registry is deleted.

**Whether UI separates its framework from its widgets.** Yes, as two runtime assemblies in one package, `UI.Widgets` (the kit, the theme, the bindings) and `UI.Screens` (the view stack, focus, cursor, escape, layout edit mode), not as two packages. The editor and Studio.Tools reference `UI.Widgets` alone, which is what makes "the editor is a consumer of the same kit" possible. They stay one package because they share the theme, the dependency set and the buyer, and because the measured cost of an extra assembly is 0.2 s of post-processing against a package's release cycle. Area 11 designs both.

**What Controller is.** Two things that never belonged together. StateMachine is the developer's favourite part and a library any game wants, including the racing game and the card game that want no body. Character is the body: capsule, probe, sockets, ragdoll, camera rig as a bridge. The five unused dependencies go with the split.

## Studio: one package or several

| Option | Delivers | Costs |
|---|---|---|
| **One repo, five packages by dependency cluster (recommended)** | One dev project, one version tagged on the repo, one release; a game installs the clusters it uses by git URL with a path (`?path=/Assets/Studio.Gameplay`), so a seventh game without a world takes Studio.Online and Studio.Presentation and never pulls Inventory, Modifiers or Places through Studio | Five `package.json` files to keep honest; a game takes a whole cluster (Saboteer gets skills and talents with its equipment), and the day a game wants half of one the cluster splits |
| One private package | Simplest: one repo, one manifest line | Its dependency list is the union of everything we glue, so every studio game installs every library we have ever used; compile references cost even when unused (Controller paid 0.84 s of post-processing for Entities it never touched) |
| One package per idea, each its own repo | A seventh game takes exactly our equipment and nothing else | Ten repos, ten dev projects and ten release cycles for two people; the glue between ideas (equipment grants modifiers the skills read) crosses package lines and the private packages start bridging each other |

Bevy's repository is the precedent for the recommended shape: many crates, one repo, one version. The id scheme is `com.spellboundstudios.studio.<cluster>`. The sold packages stay one per repo: Asset Store publishing wants one product per package folder whose name matches its `package.json` (Unity, "Publish UPM packages to the Asset Store"), a constraint that never binds Studio because Studio is never sold. Studio is the line's first customer: every extension point a library has exists because Studio or a stranger needed it, and Studio compiling against public surfaces alone is the proof the line is extensible.

## Directions

**A. Fewest packages, big families (rejected).** Core, World, Character, Items, UI, Online, Studio: seven packages, each a family of assemblies. It wins the ten-minute test by brevity and loses requirements 2 and 3: a farming sim installing World for places gets voxels, far terrain and navigation, and the compile cost of a reference is paid whether or not it is used (Controller: 0.84 s of post-processing for Entities, against 0.21 s for a package without it). Families are also how Core grew its world-object framework. The map below shows the whole line in one screen anyway, so the brevity was not needed.

**B. One mechanism per package, bridges in the data owner, a strict layer order (taken).** Every package has one sentence and one buyer. Joins are optional assemblies that compile only when both sides are installed, hosted by the package whose data crosses, pointing down a fixed layer order. The cost is twenty-three repos and dev projects, which is what the template, the convention and the check in areas 7 and 10 exist to make cheap, and what one gate per person per day prices.

**C. A kernel and plugins (rejected).** Core as a tiny kernel with a plugin registry every package registers into at startup, the way Bevy's `App` takes plugins, and a `Spellbound` facade package that installs the whole line behind feature defines. It gives one entry point for everything and loses to the library-design skill directly: a plugin registry is a bootstrap order and a manager every consumer must adopt, and the facade is a dependency magnet that pulls every package into every project. The facade's good half, one entry point per package, survives as the front door each package ships (area 2). The whole-line install survives as a template project (area 10), which is a convenience, not a dependency.

## Ideas kept and cut

Kept, and where each lands:

1. Core depends on the engine alone; the gate on every compile moves from the Entities.Graphics mark to the UnityEngine.UI mark. (Core)

## Decisions, all decided

Revision note, 2026-10-23: all four were decided at the developer's review of the 2a page and confirmed at the review of the full page the same day.

1. **Studio's shape: decided.** One repo, five packages by dependency cluster. The developer's condition is flexibility over ten games: a game that wants to reinvent its skill system, its stats or its magic writes it against Inventory and Modifiers and simply does not install Studio.Gameplay; the libraries never change for it. The developer's reading is right: a studio with two games can keep two skill systems, one in each game, or lift one into a Studio package the day the second game wants it and install it there; a spell made of Modifiers data moves between games that share the same skill mechanism, and an equipment system ports by moving it from the game that wrote it into Studio and installing it in the other. The rule that decides which: one game wants it, it is that game's; two want it as is, it is Studio; a stranger would want it, it is a library. Every Studio package has its own tests in StudioDev, and the stranger projects of area 7 prove the libraries stand without Studio. A mechanism every game wants the same way, like a ragdoll, is a library (Character) and is replaced through its seams, never by forking.
2. **How a buyer and a game get Core: the Spellbound window, not a readme.** The standard UPM way is a `package.json` dependency by id and version, and the package manager resolves that only from the Unity registry or a scoped registry; it cannot follow a git URL from inside a package (Unity manual, "Git dependencies"), and an Asset Store package cannot make the store install another store package. So without something of ours, a buyer of Inventory would read a readme and install Core by hand. The line adds the thing the developer asked for: a Spellbound window in Core.Editor that lists every package of the line, marks what is installed and at which version, installs or updates a free one in place through `UnityEditor.PackageManager.Client.Add`, which takes a package id or a git URL (Unity scripting reference, `PackageManager.Client.Add`), greys out a paid one that is not owned and links to its store page, and opens each package's documentation and samples. Because the window lives in Core, every paid package carries one small bootstrap file that does one thing: if Core is missing, offer to install it the same way. Core is free and public already; the window ships with Core and installs everything else from a git URL with a path and an exact tag (decided 2026-10-23), so a buyer and our games take one road. This is rule 16 above; area 7 designed the window as part of what every package ships.
3. **The name of the networked text package: Switchboard, decided.** The word for the thing that routes messages between parties; decided as a placeholder on 2026-10-23 and confirmed as the final name on 2026-10-24 (checkpoint 5).
4. **The text form for authored content: the ScriptableObject is the one form, decided.** The developer's point stands: a ScriptableObject is already text on disk (Unity's YAML, with these projects on text serialization), designers already author them in the inspector, and a second format of ours would reinvent that wheel. One push back, and it changes the design rather than the decision: the YAML Unity writes is its own internal shape (fields by serialized name, references as GUID and file id pairs, a `.meta` file per asset), and hand-writing it is what requirement 15 rules out, because a mistyped field is dropped silently on import and nothing validates it until the editor loads it. So the agent does not write YAML. It creates the same ScriptableObject through Unity's own asset pipeline, which the Unity CLI already exposes (`create_asset`, `set_serialized_field`, `run_script` in the Pipeline package), and the designer creates it in the inspector; both roads end in one asset. What the line adds is not a format but a contract: every definition type in every package implements Core's validation contract, Core.Editor runs it and writes the one report an agent reads, the same validation fires in the inspector, and the preview is the asset in the editor plus a capture. A package may offer a front door for making definitions in code (`Items.Define(...)`) as a convenience over the same pipeline, never as a second format. YAML as a bulk import (five hundred affixes from a sheet) is a later tool over the same assets if a designer asks for it, not a thing the line owns now.

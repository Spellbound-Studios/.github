The builder the agent ran in step 6, which a person could run from a menu item or the Places window instead. `GeoForgePlacesKit` and `WorldObjectsPlacesKit` are the bridge doors (below): the layer types live in the bridge assemblies, so the packages' own doors cannot return them.
```csharp
public static class BuildCaveOreVein {
    public static string Run() {
        var draft = DefinitionDrafts.Create<PlaceDefinition>("CaveOreVein", place => {
            var cave = place.AddLayer(GeoForgePlacesKit.CarvedVolume(new Vector3Int(64, 24, 64),
                carve => carve.Capsule(new Vector3(0, 4, 0), new Vector3(24, 4, 0), 3f)));
            place.AddLayer(WorldObjectsPlacesKit.Scatter("rare_ore", 14, cave));
        });

        return draft.Report.ToText();
    }
}
```

`DefinitionDrafts.Create` makes the ScriptableObject with `ScriptableObject.CreateInstance` and `AssetDatabase.CreateAsset` in the drafts folder, runs the validation, and hands back the asset and its report. It is the "front door for making definitions in code" that decision 4 of the line allows over Unity's own asset pipeline; for a definition whose fields are plain values the agent may use `create_asset` and `set_serialized_field` instead; a definition that holds a list of references to different types (a place's layers, a preset's modules, a kind's checks) cannot be written that way, because Pipeline's converter throws for managed references (survey), so such definitions are authored by `run_script` or a front door builder only.

## After

### The idea in one sentence

An operation is a public method on a package's front door that is also callable as a line of text, so the same declaration serves C#, the in-game console, the editor window and an agent on the Unity CLI, and nothing is declared twice.

### Names, and why the front door is not named for the package

Each package has one front door: a `public static class <Name>Kit` in its root namespace (`InventoryKit`, `PlacesKit`, `CoreKit`). The suffix is forced by a measured defect, not taste. The root namespace of a package is `Spellbound.<Name>` (line rule 7), so a front door named `Inventory` would sit beside a namespace of the same name, and any code inside `namespace Spellbound.*`, which is every game and every other package, resolves `Inventory` to the namespace and fails with CS0234 (survey table, last compile row). With the suffix the name is still guessable: type the package name and let the editor complete it. The developer decided the word on 2026-10-23 (see Decided).

The front door is a thin index, not a god object. Its members return the concept's entry objects (`CoreKit.Operations`, `InventoryKit.Containers`), each an ordinary instantiable class that tests construct on their own; the static holds only the default instance and resets on `SubsystemRegistration`, so a project with domain reload off still starts clean (line rule 12).

### The public surface in Core (`Spellbound.Core.Operations`)

| Type | What it is |
|---|---|
| `OperationGroupAttribute(name, job)` | On an assembly: the package name as the group and its one-sentence job, the line's sentence. The name is the package name in lower case with the dots removed (`studiotools` for Studio.Tools), and area 7's check requires that. A second assembly of the same package may carry the attribute with the same name and no job; the catalog merges them into one group |
| `OperationAttribute(name, description, effect)` | On a public method. `Audience` (a string, default `developer`) and `Availability` (anytime, while editing, while playing) are optional properties |
| `ArgumentAttribute(description)` | On a parameter. The name comes from the C# parameter, written `kebab-case` on a line. `Target` (default false) marks the one parameter whose value names the thing the operation acts on; an operation marks at most one |
| `OperationEffect` | `Reads`, `Writes`, `Destroys`. A fixed classification the host acts on, not a game decision |
| `OperationAudiences` | Constants for `anyone`, `authority` and `developer`. `authority` means "runs on the peer that decides" (decided 2026-10-24): an operation tagged with it is not refused to a caller for lacking it, it is sent to the peer that decides for its target, and that peer judges the sender; nobody holds `authority` as a caller audience. The audience is an open string, so a game adds `moderator` without editing Core |
| `OperationCatalog` | Finds the groups and operations of every marked assembly, lazily at first use, through one internal assembly-listing call (so a switch to `UnityEngine.Assemblies.CurrentAssemblies`, which area 8 cites, is one edit). `Find(prefix)` lists by prefix and `Describe(group, name)` returns an `OperationDescription`: group, name, summary, each argument (name, type, default, summary, legal values, and whether it is the target), effect, audience, availability and a stable `Identifier` (Core's FNV hash of `group.name`). A console completes from this data and calls nothing else. Instances can be registered and unregistered for operations that need live state |
| `OperationHost` | `Run(line, caller)` parses, binds, checks audience, availability and effect, calls, and returns an `OperationRun`. `Run(invocation, caller)` skips the text: the same checks run on an `OperationInvocation`, which is how Networking sends a call as packed bytes. `Router` holds the one `IOperationRouter` (none by default) and `RunHere(invocation, caller)` runs the same checks without ever asking it, which is how the deciding peer runs a call it received ("Where an operation runs"). `Run(line, caller, placeholders)` and `RunAll(lines, caller, placeholders)` take a read-only map of names to text for the placeholders described below |
| `OperationInvocation` | An `Identifier`, an array of already-typed argument values, the target value when the operation marks one, and the line it was parsed from when it came from text. Built by the text binder, or by a caller who unpacked bytes; Core never learns where the bytes came from |
| `IOperationRouter` | One method, `TryRoute(invocation, description, caller, out run)`: false means run here, true hands back the run that carries the answer of the peer that decides. Core knows no connection; Networking registers one |
| `OperationRun` | Completes now or over frames. Derives from `CustomYieldInstruction`, so a Play Mode `[UnityTest]` can `yield return` it; exposes `IsDone`, `Result` and `AsTask()` |
| `OperationResult` | `Status` (`Succeeded`, `Invalid`, `Failed`, `Refused`, `Previewed`), a `Succeeded` flag, a `Severity` derived from the status (information, warning, error) so a view colours a line without a switch, `Text`, and the returned `Value`. The first word of `Text` is the status word and is stable; the rest is prose for people and agents and is not a contract. The console view colours a result by `Severity`, shows lines passed to `Report` as live lines, and relies on the status word being first |
| `OperationTable` | A returned value with named columns and rows. The default renderer writes a header line and aligned rows, so an agent reads a table as lines; the window draws the same value as a grid |
| `OperationSeverity` | Information, warning, error |
| `MarkedAssemblyScan` | Public because Networking is now a second package that needs it: finds the types carrying a given attribute in marked assemblies only. Argument parsers, result renderers and Networking's simulation fixtures are found through it |
| `OperationCaller` | A name and the set of audiences it holds, with `Holds(audience)` so an operation can gate one argument (`artpipeline fix --keep`). `OperationCaller.Development()` holds `developer`. The console, the Pipeline bridge, the editor window and Networking each build one |
| `OperationContext` | A parameter the host fills, never parsed from text: `DryRun`, `Confirmed`, `Caller`, a cancellation token, and `Report(string line)` for progress. The run raises each reported line as an event, which the console view shows as a live line. The Pipeline envelope returns the final text only; whether it could stream is unverified |
| `OperationException(message, hint)` | A refusal the operation itself raises, with a hint the agent can act on |
| `IArgumentParser<T>` | A consumer teaches the line a new argument type by writing a class with a default constructor and marking it `[ArgumentParser]`; the same marked-assembly scan finds it, so there is no startup call to forget. Core ships integers, floats, booleans, enums (the legal values are echoed on failure), vectors, colours, lists, and a reference form for assets by path (`asset:Assets/...`) or by name (`asset:CaveOreVein`, resolved among assets of the parameter's type in the editor, refused with the candidates listed when two match), scene objects (`scene:/Path/To`), worlds (`world:3`) and names a game binds (`player`) |
| `IResultRenderer` | A consumer changes how a returned value becomes text, found the same way. The default renders a string as is, a collection as one line per item, any other value with `ToString` |
| `OperationSettings` | One ScriptableObject, optional, found through Core's provider seam: a trace toggle that logs every line through Core's logger, groups to disable, the audiences the Pipeline bridge holds (the one setting that can grant `approver` to an agent), the drafts folder, a maximum line length, a maximum number of result lines. Every field has a default, so no asset is required |

Twenty-six public types: the twenty in the table, `ArgumentParserAttribute` and `ResultRendererAttribute`, and `OperationStatus`, `OperationAvailability`, `OperationDescription` and `ArgumentDescription`, which the catalog returns. The parser, the discovery scan and the line tokenizer are `internal`. `CommandParameterParser` (168 lines) is the base the new parser grows from, so the work extends what exists: it already parses strings, numbers, booleans, bytes, enums and nullables (`CommandParameterParser.cs:16-98`), and `AttributeCommandRegistry` already parses vectors and lists (`:336-425`).

### Declaring an operation

The same Saboteer command, after:

```csharp
[assembly: OperationGroup("saboteer", "Match commands for development builds.")]

namespace Spellbound.Saboteer.ConsoleCommands {
    [Preserve]
    public static class MatchOperations {
        [Operation("gold", "Adjusts your own gold purse. Negative amounts subtract.", OperationEffect.Writes)]
        public static string Gold([Argument("Amount to add; negative subtracts.")] int amount) {
            if (!SingletonManager.TryGetSingletonInstance(out MatchScore score))
                throw new OperationException("No match score exists.", "Start a match first.");

            score.AdjustGold(amount);

            return $"Adjusted your gold by {amount}. Current balance: {score.Gold}.";
        }
    }
}
```

Volumetrics after: three static methods that return strings, with no `Print` helper, no Core console reference in a rendering package beyond the attribute, and the answer reaches whichever face asked:

```csharp
[Operation("timing", "Turns per stage timing on or off, overriding the profile.", OperationEffect.Writes)]
public static string SetTiming([Argument("True to time every stage.")] bool enabled) {
    VolumetricDiagnosticsHub.Active.TimingOverride = enabled;

    return $"Volumetric timing {(enabled ? "enabled" : "disabled")}.";

```

A line is `group operation arguments`. `saboteer gold 50` and `saboteer gold --amount 50` are the same call. When an operation name is unique across the installed groups the group may be left out, so a player typing `gold 50` in the console still works; an ambiguous name is refused with the candidates listed. The agent always writes the group.

An operation is a public static method on a public static class of the package: the front door or a class beside it, as `MatchOperations` is above. One group may span two assemblies of a package, because a package may have an assembly that needs a third party and one that does not (Networking: the protocol assembly declares `simulate`, `audit`, `journal-replay` and `smoke`; the PurrNet adapter declares `status`, `regions`, `hub` and `resync`, all in the group `networking`; GeoForge's `capture` and `bake` sit in `GeoForge.Places` in the group `geoforge`). The assembly that carries the job sentence is the one that holds the door. Two operations with one name in one group are the duplicate case of the failure table: logged, first found wins. The door sits in the lowest assembly of the package that declares an operation. A package with a plain-types assembly under an opt-in assembly that declares the operations puts the door in the upper one (`UIKit` in `UI.Screens`; `UI.Widgets` holds elements a buyer constructs and needs no door). A Tool's door may sit in an Editor assembly (`PackageCheckKit`, `ArtPipelineKit`), and its operations then exist only where editor assemblies load.

A bridge assembly has a door too, when it holds types a buyer constructs. The two packages a bridge joins cannot name each other's types, and a C# static class cannot be extended from another assembly, so the bridge is the only place the buyer's call can live: `GeoForge.Places` holds the voxel layer type, `WorldObjects.Places` the object layer type, and neither `GeoForgeKit` nor `WorldObjectsKit` can return them. The convention: a public static class named `<Package><Other>Kit` in the bridge assembly `Spellbound.<Package>.<Other>`, so `GeoForgePlacesKit` and `WorldObjectsPlacesKit`. Its name differs from the namespace `Spellbound.GeoForge.Places`, so the CS0234 defect does not recur. It holds constructors and nothing else; operations stay in the package's group. The object layer's `Scatter` takes the layer it rests on as Places' base layer type, so WorldObjects names no GeoForge type. `core context` lists the bridge doors present in the project, and `core context --package geoforge` lists their public members as signatures in its generated block; the doors are found by the assembly and class name pattern, so no attribute is added. A bridge with no public surface has no door. `ReachableDepositsCheck` is not a bridge's: it is registered from `Navigation.Places.Editor`, an editor assembly compiled only when Places is installed (a define constraint on Places' assembly), and Places never references Navigation.

A line may carry placeholders, names in braces that the caller fills from a map it passes to the host: `places gym-start --target {prefab}` run with `{prefab}` set to `asset:CaveOreVeinVariant`. Core fixes no names; ArtPipeline's names are `{prefab}` and `{asset}`. The host fills a placeholder after it has tokenised the line, so a value with spaces or a leading `--` stays one value and cannot add an argument; a name with no value is `invalid: placeholder {prefab} has no value (supplied: asset)`. A chain is `RunAll(lines, caller, placeholders)`, which already runs lines in order and stops at the first result that is not `Succeeded`. Every line runs with the caller's own audiences, so a chain stored in a definition can never do what its caller could not. Skipping a line whose group is not installed is the caller's choice, made with `OperationCatalog.Find`; Core adds no skip status.

### Operations that start play mode, and the gym

Entering play mode reloads the domain in both games, and a reload kills an awaited job and an in-memory chain (survey). So an operation that starts play mode follows the rule of the pair: it returns before the reload with the request written under `Library/Spellbound/`, and a `-status` operation reads the outcome after it. It must be the last line of any chain, because the lines after it would be lost with the reload. The gym is the case, with one owner, Places, and one argument shape, fixed here:

| Line | Available | Answers |
|---|---|---|
| `places gym-start --target <asset> [--item <asset>]` | Anytime | `succeeded: entering play mode, read places gym-status`; in play mode already it loads the gym in place and answers `succeeded: gym loading` |
| `places gym-status` | Anytime | `succeeded: gym loading`, then `succeeded: gym ready, character 'Prospector' at entrance`, or `failed: <reason>` |
| `places gym-leave` | While playing | `succeeded: left the gym`; the refusal in the wrong mode names `editor_play` |

`--target` is one asset reference (`asset:CaveOreVein`, a prefab by name or path, or a placeholder such as `{prefab}`); it is a Place or a prefab, and Places tells them apart by type. `--item` names an item held by the gym's character. The gym's character is always a playable character of the game: Places' neutral default spawns the prefab the project names, Studio.Content's profile offers the studio's playable characters, and a game's own profile wins inside its project; with none named the answer is `refused: no gym character is set` and the field to set. The spellings `--place`, `--prefab` and a positional asset are gone, and `gym-enter` no longer exists: a chain stored in an ArtPipeline kind ends with `places gym-start --target {prefab}`, and the artist's edit-mode chain, an agent and a Play Mode test all use the same two lines.

`[Preserve]` is required on a class that holds operations in a package that reaches a player, because discovery is reflection and the linker "can't always detect uses of reflection" (survey). An editor-only Tool (PackageCheck, ArtPipeline) is found by `TypeCache`, so the rule is moot there. The development builds Pipeline supports today run Mono; stripping behaviour under IL2CPP is unverified. CL1 story 1 checks reflection discovery against Unity's notes for 6.7 and the next major under build stripping, on Mono and on IL2CPP, now on the editor in use and again on the 6.7 beta once the probe installs it (nothing waits for 6.7), with a fixture shaped like the `ui` operations (a package assembly with a class that is reached only by reflection), so the question whether the `ui` operations are found in a stripped development build is answered by the same run. It also gates rule A8: if discovery survives without `[Preserve]`, A8 goes; if it needs it, A8 stays; if it fails, the Roslyn source generator that writes the operation index is the fallback the developer named, and A8 goes with the reflection.

### Checks the packages register

The seam is Core's; the checks are the packages'. Each is a class in the package's editor assembly. The report names what ran in one line, in one format: `checks: ` then each entry as `<name> (<Package>)`, comma separated, the definition type's own validation first. For the type's own validation the name is the type (`PlaceDefinition (Places)`); for a registered check it is the name in its attribute, always `<package>.<kebab-name>` (`navigation.reachable-deposits (Navigation)`). A script finds a check by that token. `core validate --drafts` lists every one that ran, and a check that is not installed is absent from the line, never listed as passed. ### How the faces share it

| Face | Who | What calls the host | Audience held |
|---|---|---|---|
| C# | Any code, tests | `CoreKit.Operations.Run(line, caller)` | The caller the code builds |
| In-game console | A developer or tester | UI's text surface (area 11) over the same host and the catalog's completion data | `developer` in a development build; the game decides otherwise |
| Editor window | A person | The Operations tab of the Spellbound window: a table from the catalog, a form generated from the argument list, a run button, the answer | `developer` and `approver` |
| Unity CLI | An agent | `spellbound_run` in the Pipeline bridge | `developer` by default, changed only by `OperationSettings` |
| Over the wire | Networking, for any write or destroy whose target is decided on another peer | `OperationGateway` in `Spellbound.Networking`, the PurrNet bridge, registered as the host's `IOperationRouter`, sends one call as one RPC to the peer that decides: the operation's `Identifier` and its values packed with Core's packing, from the argument types the description declares. Which peer decides (owner, host or server) is Networking's configuration per replicated thing with no default, and Core assumes none. The receiving peer unpacks them, asks its `IOperationAuthorizer` (an interface in `Spellbound.Networking.Replication`, the protocol assembly with no PurrNet type, which builds the `OperationCaller` from the sender) and runs `RunHere(invocation, caller)`. An argument type that has no pack form (a consumer's own parser type) travels as the text line instead | whatever the authorizer grants |

The packed form exists so the authority never parses hostile text for a call that has typed arguments, and so a call is a few bytes. It is for operations a person or agent triggers; gameplay never goes through an operation (Limits), so no wire cost is added to a tick. Networking owns the rate limit and the authorizer; Core knows an audience tag and a caller, never a connection.

### Where an operation runs

The rule (decided 2026-10-24): a line that changes something runs on the peer that decides for the thing it names; a line that only reads runs where it was asked; the audience word `authority` means "runs on the peer that decides". With one machine, or with Networking not installed, the machine that typed the line decides, so a game with no network sees no change.

| Piece | Home | What it is |
|---|---|---|
| Target marker | Core, `ArgumentAttribute.Target` | The one parameter whose value names the thing the operation acts on (an instance id, a container id). `OperationDescription` reports it as `Target`; catalog load logs an operation that marks two and keeps the first |
| `IOperationRouter` | Core, `Spellbound.Core.Operations` | `bool TryRoute(OperationInvocation invocation, OperationDescription description, OperationCaller caller, out OperationRun run)`. False means run here. The invocation holds the typed values, the target value and, when it came from text, the line (for a value that has no pack form) |
| `OperationHost.Router` | Core | Null by default. The host asks it once per call, after parse, bind, audience, availability and the effect gate, and only when the effect is `Writes` or `Destroys`. A dry run is asked too, because the deciding peer holds the state it would change. A `Reads` operation is never asked |
| `OperationHost.RunHere` | Core | The same checks, never the router. The deciding peer runs a call it received through it, so a call cannot bounce between peers |
| `IOperationTargetSource` | `Spellbound.Networking.Replication`, Networking's | `Holds(targetId)` and `OwnerOf(targetId)`, implemented by each data package's bridge for the ids it owns. It stays out of Core because `OwnerOf` names a peer and Core knows no connection (line rule 14) |
| The gateway | `Spellbound.Networking` | Registers itself as the router, finds the source that holds the target, reads that source's write policy and sends the call to the peer it names, or answers false when this peer decides. It has no default route |

A call that marks no target reaches the router with `Target` empty and Networking uses its setting for the group. The answer comes back as the same text with its status word first, so the console, the window, the Unity CLI and a test read it as if it had run here and no face decides. Which senders the deciding peer accepts is Networking's authorizer, and owner mode requires none. Example: `inventory add --container 12 --item copper_ore --count 3` typed on a client, where container 12 is bound to the host's player; the gateway sends it, the host runs it and the client prints `succeeded: copper_ore x3 added`. A chain run with `RunAll` waits for each routed line before the next and stops at the first result that is not `Succeeded`; a peer that does not answer ends the line with `failed:` and the peer named. Gameplay never rides this path (Limits).

```csharp
public static class SpellboundCommand {
    [CliCommand("spellbound_run", "Runs one Spellbound operation line, the same text the in-game console accepts. Start with: core help", Tags = new[] { "spellbound" })]
    public static async Task<string> Run([CliArg("line", "The operation line, for example: core help", Required = true)] string line) {
        var run = CoreKit.Operations.Run(line, PipelineCaller.Current);
        var result = await run.AsTask();

        if (result.Status is OperationStatus.Invalid)
            throw new ArgumentException(result.Text);

        if (result.Status is OperationStatus.Failed or OperationStatus.Refused)
            throw new InvalidOperationException(result.Text);

        return result.Text;
    }
}
```

Why one command and not one per operation: everything else the agent needs is an operation of Core (`core help`, `core context`, `core validate`, `core preview`), so the console, the editor window and the agent read the same answers, and a package installed tomorrow adds operations without a recompile of the bridge or a change to what `unity command` lists. A line that did not parse or bind throws an `ArgumentException` and a failed or refused operation an `InvalidOperationException`, so Pipeline reports both through its own failure channel instead of a success carrying bad news, and keeps the caller's mistake apart from the operation's (Pipeline preserves `ArgumentException`, `BasePipelineServer.cs`, `DispatchCommandOnMainThread`; which exit code the CLI gives each is for CL2 to confirm, the unity-cli skill reads exit 2 as "rewrite the invocation" and exit 6 as "ran and failed"). A returned `Task` is awaited off the main thread while the main thread keeps pumping, which is what lets an operation in play mode span frames (survey, `BasePipelineServer.cs:2749`). A call longer than the server's budget is run by the caller as Pipeline's own detached job.

Pipeline's server also runs in an Editor launched with `-batchmode` (its status reports `mode: batchmode`, `connectivity.md:160`), so every operation that needs no window is reachable by an agent or a build script with no one at the screen.

Two rules come from Pipeline's own limits. First, jobs live in Editor memory and do not survive a domain reload (`connectivity.md:252`), so an operation that can outlast a reload (an import, a bake, a long generation) is declared as a pair, `<name>-start` and `<name>-status`, with its state written under `Library/Spellbound/` and readable after the reload; `packagecheck check` (rule A10) looks for the `-status` partner of every `-start`. A short operation that finishes inside one call stays a single operation. Second, an operation never opens a modal dialog, because an open dialog blocks every main-thread command and `/api/status` reports `blocked_by_dialog` (`connectivity.md:290-294`); anything that wants a yes takes `--confirm`. Both are rules of the convention, checked in review and by `packagecheck check` where it can.

Edit mode, play mode and a running build are one path. The bridge assembly is a runtime assembly of Core, so Pipeline's editor server finds it in both modes by `TypeCache`, and a development build finds it by reflection over loaded assemblies; `unity command --runtime <exe> spellbound_run` reaches the build (survey). That is how an agent reads a running player's observations or a blackbox dump: `diagnostics blackbox` and `core observations` are `Reads` operations with the audience `developer`, they work with no scene open, and they exist in a build that has Pipeline's runtime server. That takes a Development Build for a standalone target (or `ENABLE_RUNTIME_PIPELINE`) and `enableInBuilds` switched on, which is off by default, and the server answers the same machine only because it binds the loopback address (survey). The transcript's step 19 turns it on, with a person's yes. An operation in an editor assembly (`core validate`, `core approve`) exists only where editor assemblies load, which is the honest answer to "what can a build do". An operation that needs a running game says so: `Availability` makes a refusal read "Available only while playing. Run editor_play first".

`PipelineCaller.Current` builds the caller from `OperationSettings`: the audiences the bridge holds, `developer` unless the studio changed the field.

The Pipeline package is experimental, and its declaration has already changed once: 0.8.0-exp.1 (both games) takes `[CliCommand("spellbound_run", description)]`, while 0.9 takes a group and a name and is run as `unity command spellbound run` (survey). The bridge is the only file in the line that knows either form, and it carries one declaration per Pipeline range, each in its own file behind its own `versionDefines` define, so a Pipeline outside every range compiles the bridge out rather than failing the project. A `versionDefines` miss is silent, and buyers do not install PackageCheck, so the warning is written by Core.Editor, which always loads: at editor load it reads the installed `com.unity.pipeline` version (the registered-package list, as Pipeline's own package-manager command does), and when Pipeline is installed but the bridge type is absent from the loaded assemblies it writes one console line, "Spellbound agent road off: com.unity.pipeline <version> is outside the supported <range>; update Spellbound.Core or install a Pipeline inside <range>". An agent reads it with Pipeline's own `console` command; a person sees it in the Console and in the Spellbound window's Line tab. The ranges are written once, in the bridge files' defines, and a CL2 test run against each supported Pipeline version, and on the 6000.3 floor row, fails when the bridge type is absent. The text the agent is told to run (`core help`) does not change between them, and neither does any operation. This is the strongest reason for one command: the churn costs one file, not one registration per operation.

### Authoring: validate, preview, draft, approve

Requirement 15 and decision 4 of the line: the ScriptableObject is the one form, made through Unity's own asset pipeline, validated through Core's contract. The contract:

| Piece | Where | What it is |
|---|---|---|
| `IAuthoredDefinition` | Core runtime | `Validate(ValidationReport report)`. A definition type in any package implements it. No `UnityEditor` reference, so the type compiles on a server. It carries no version: a changed definition is re-authored |
| `ValidationReport`, `ValidationFinding` | Core runtime | A finding has a stable `Code` (a string the declaring check owns, never reused), a severity (error, warning, information), a `Subject` that is an asset path (so a model file, a prefab or a package folder, `Packages/<name>`, can be the subject, not only a ScriptableObject), an optional `Location` inside the subject (a property path, or a node path in a model), a message, a `Hint` and optional named hints (an open key to a hint; ArtPipeline keys them by DCC id, Core knows no DCC), and an optional `FixCode` that names the fix a package offers for it. `ToText()` writes one finding per line in a fixed order, code first. A report can be filled by any check; only a ScriptableObject definition has to implement `IAuthoredDefinition` |
| The runner | Core.Editor | Validates one asset, a folder, the drafts folder or everything that implements the contract, and writes one report. It times each validator and previewer and reports the milliseconds into Core's observation model (area 3) under the check's code prefix, against a budget the check declares there; the Operations tab and the inspector banner read the figure back from the observation model, so the report has no second channel for timings. It finds the types with `TypeCache.GetTypesDerivedFrom<IAuthoredDefinition>()` and then asks the asset database for those types only, so a project with thousands of other ScriptableObjects does not pay for them |
| The inspector banner | Core.Editor | Subscribes to `Editor.finishedDefaultHeaderGUI` and shows the asset's findings above any inspector, with no custom editor and no change to a consumer's own inspector. The banner revalidates once the asset has stopped changing for a delay set in `OperationSettings` (default unmeasured, a field), and then runs only the type's own `Validate` and the registered checks that say `RunsWhileEditing`. Every other registered check runs when the asset is saved (deferred with `EditorApplication.delayCall`, so never inside a drag), when `core validate` runs and when the person presses Run checks on the banner; until then the banner shows that check's last result, labelled with the time it ran and marked stale when the asset has changed since. A designer sees the same words an agent reads |
| `DefinitionPreviewer` | Core.Editor | An abstract class a package's editor assembly registers for one definition type with an attribute. It returns picture paths and a summary line. Core never learns what a voxel is; Places' previewer draws a place. The summary gains the lines that checks contribute |
| `IDefinitionCheck<T>`, `RegisteredDefinitionCheckAttribute` | Core.Editor | The check seam (decided 2026-10-24: the seam and nothing else, one interface, one attribute and the lines that find and run registered checks). The gap it fills: `Validate` is a method on the definition type, so only the package that owns a type can write its findings, and Places may never import Navigation, so nothing could add "11 of 14 deposits cannot be reached" to a place's report. A package's editor assembly implements the interface for a definition type it does not own and marks the class with the attribute, which carries the check's name (`<package>.<kebab-name>`, for example `navigation.reachable-deposits`) and one flag, `RunsWhileEditing`, default false: `Check(T definition, ValidationReport report)` adds findings, and `PreviewLines(T definition)` adds summary lines to `core preview`. The runner finds the classes with `TypeCache.GetTypesWithAttribute`, reads `T` from the interface each implements, and runs, once per definition asset, every check whose `T` the asset's type is assignable to, after the type's own `Validate`. A check is ordinary editor code: it may read editor project settings or any other editor state, so a check over a settings asset can compare it with the project (Instancing's `VariantSettingsCheck`), and it reads the definition and never writes it. The report is the status line (`failed:` when any error was found, `succeeded:` otherwise), then a `checks:` line naming what ran in the one format of "Checks the packages register", then the findings, so a missing check is visible and not silent; a script or CI step reads the status word, and the Pipeline bridge turns `failed:` into exit 6. A check's codes carry its package's prefix, it is timed like any validator, and its findings are the ordinary findings. The seam is over definition types only: a package folder is a finding's subject (PackageCheck fills the same report), but it has no type to match, so no check is registered over a folder. Core never changes for a new package; the registered checks are listed in "Checks the packages register" below |
| Authored-key scan | Core.Editor | For each asset whose type implements the contract, a line scan of Unity's text form of the asset (Force Text serialization, the default) compares the stored keys with the type's current serialized property paths, resolving managed references by their stored type names, and reports an error finding with code `core.unknown-key` for each key the type no longer has (decided 2026-10-24, detection only, no fix code). A key that a current field names with Unity's own `FormerlySerializedAs` (read from the field's attributes by reflection, on the field under the same parent path) is not a key the type lost: Unity reads its value into the renamed field, so the scan reports it as information with code `core.renamed-key`, naming the key, the field and the hint `save the asset again to drop the old key`, and it never blocks validation or approval. The finding names the asset, the key and the stored value text, read from the same line the scan already reads, cut at a length set in `OperationSettings` and ending in `...` when cut: `CaveOreVein layers[1].density: stored 0.35, the type has no field density; re-author it under its new name before this asset is saved again`. Nothing is mapped, kept or converted: the value is shown so the person or the agent can type it into the new field with the key still in the file, and the key goes away when the asset is next saved, whether the new field was set or not. Nothing is written anywhere to keep the value (decided 2026-10-24). So `succeeded:` after a save means that no stale key remains, not that anything was re-authored; the stub tells an agent to set the new field first and save nothing else (Limits). A managed reference whose type cannot be loaded is not a field the type lost and is never reported as unknown keys: the scan asks Unity for it (`SerializationUtility.GetManagedReferencesWithMissingTypes`, which returns the reference id, the class, namespace and assembly name Unity expected and a summary of the stored data, 6000.4 reference) and reports it once as `core.missing-type`, information when the assembly is not in the project (the message names the assembly, and the package when the assembly belongs to one of the line, so Saboteer's shared place with a scatter layer from a package it did not install validates, previews and approves, the layer carried opaque as the line says), and a warning when the assembly is loaded and the class is gone (a removed or renamed class). The scan skips every stored key beneath a managed reference whose type is missing, so a layer from an uninstalled package is never read as unknown keys. Its enumeration of a type's serialized fields is one public function, `AuthoredFields.Describe(Type)` in Core.Editor, which returns the sorted serialized property paths with their types, one line each (a managed reference list shows as one managed-reference field), the way packing exposes `Describe`; the scan and Living's surface writer both call it, and a fixture test asserts that they list the same lines. A project on binary serialization gets no scan. It rests on Unity leaving an unmatched key in the file until the asset is next saved, which CL4 story 11 proves before the rest is built, for plain fields and for managed references (a place's layer list) alike, and for a field renamed with `FormerlySerializedAs`, whose old key must still be in the file and must load into the new field |
| `DefinitionDrafts` | Core.Editor | `Create<T>(name, fill)` makes the asset in the drafts folder and returns it with its report; `List()` and `Approve(asset, folder)` use `AssetDatabase.MoveAsset`, which keeps the GUID. `Revise(asset)` is the road for content a person has already approved: it copies the asset into the drafts folder as `<name>-revision` with `AssetDatabase.CopyAsset` and returns the copy with its report. The agent changes the copy by `set_serialized_field`, `run_script` or an owner's operation, exactly as it would a new draft, and the Drafts tab shows the revision's report and picture beside the original's. `Approve(revision)` copies the revision's serialized properties over the original with `EditorUtility.CopySerialized` ("copies all serialized properties of a Unity Object from one object to another", 6000.4 reference) and deletes the revision, so the original keeps its GUID and every reference to it, and the by-name argument `asset:CaveOreVein` keeps resolving (the revision's own name differs, so the two never collide). Approval keeps its audience and its refusal while errors exist. Whether `CopySerialized` carries a managed-reference list intact is unverified and is CL4 story 12's first test. A revision holds only the fields of the asset itself. Where it holds a reference to another definition asset outside the drafts folder (a place's voxel layer kept in its own asset), `core revise` ends its answer with one line per such reference, for example `layers[1] keeps its data in asset:CaveVoxels (GeoForge); revise it with core revise asset:CaveVoxels`. Core finds them from the serialized references and the contract alone and names the owner from the asset type's assembly, as the scan does for a missing type, so Core learns no layer type. The layer is revised as its own draft, edited by its owner's operation (a claim on world) and approved with its own report and picture; the place still points at the original asset, so its checks see the new data once that is approved. Judging a place together with a revised layer before approval is not offered. If the original was saved by someone else between the revise and the approve, approve overwrites it; the Drafts tab shows both saved times, and committing stays a person's act |
| `core validate`, `core preview`, `core drafts`, `core revise`, `core approve` | Core.Editor | The operations. `revise asset:<name>` answers `succeeded: draft of CaveOreVein at Assets/Drafts/CaveOreVein-revision` and is a `Writes` operation into the drafts folder only, so an agent holds it. `approve` is a `Writes` operation that requires the audience `approver` |

No compatibility of any kind is kept for definitions before a package ships to customers: there is no format version, no migration step, no schema diff at release and no `FormerlySerializedAs` anywhere in the line. Unity drops a field it cannot match on import without a word, so a renamed or restructured field means the assets that held it are re-authored, and a draft the agent made is cheap to make again. From the first customer on, semantic versioning governs (line rule 15, decided 2026-10-24): renaming or removing a serialized field of an authored type is a breaking change and a major, and Living's release check fails it from the field lines `AuthoredFields.Describe` writes; a shipped game follows the maintenance branch of its Core major, so a rename never reaches it inside a major. Before that, what exists is detection: the authored-key scan lists every asset that still holds a field its type no longer has, with the stored value beside the key, so "re-authored" is aimed at the right assets and the designer sees the number to type, until the asset is saved again and the old key is gone.

The agent writes into the drafts folder (default `Assets/Drafts`, a field in `OperationSettings`), because the person reviewing wants the proposed assets in one place and the project's real content untouched until judged. Approval is an audience: the Pipeline bridge holds `developer` and not `approver`, the Spellbound window holds both, and the refusal in step 16 of the scenario is the gate working. Approve also refuses while the asset has an error finding, so a wrong state cannot be promoted by anyone; saving a draft with errors is allowed, because a half-made asset is normal work. This gate is a workflow gate, not a security boundary: Pipeline's `eval` and `run_script` run arbitrary code with the editor's own rights (`runtime-setup.md` says the same of the runtime server), so it stops an accident and a well-behaved agent, not a hostile one. The developer decided this on 2026-10-23: an agent may not approve its own drafts unless one setting grants it. That setting is the bridge's audiences field in `OperationSettings`; with it unset, no agent approves, and a team that wants an automated approval in CI sets it, which is their decision and one field. Nothing here touches the version control system: approving moves an asset between folders, and committing stays a person's act.

All paths an operation writes are confined to the project's `Assets` and `Library/Spellbound` folders by one Core helper, the same protection Pipeline gives its own authoring commands (`Documentation~/authoring-commands.md`, "The authoring root"). A `Reads` operation may also name a folder of the project's `Packages` (`packagecheck check --path Packages/Core`, `packagecheck release-scan --path Packages/Core`), and nothing outside the project is ever accepted; the writes of the Tool PackageCheck into a package under development are Living's and go through its own confirmed operations.

### AI context: what ships, how it reaches the agent, why it cannot drift

Two layers, with different sources of truth.

| Layer | Holds | Source | Can drift? |
|---|---|---|---|
| Generated | The operation table: group, name, arguments with descriptions and defaults, effect, audience, availability; the package version | The attributes in the installed assembly, rendered by `core context` and written into the shipped `AGENTS.md`, inside Front door, as blocks that carry a hash (`packagecheck fix --rule A3`, Living's file contract) | No: the bar check fails a stale hash at release, and `core context` refreshes the blocks from the live catalog |
| Written | Purpose (the line's sentence), the front door with the smallest working example, the rules, what the package must not be used for, what to do when it cannot do the task | `AGENTS.md` at the package root, in six fixed headings (Purpose, Front door, Rules, Not for, Gaps, Ledger). VolumetricFog already ships one (393 lines) and is the pilot | Only the prose, which area 7's check bounds: it fails when a backticked identifier in the file does not resolve to a type or member in the package, when a heading is missing, or when the front door it names does not exist |

The template ships two files and they are different: a package `AGENTS.md` skeleton with the six headings (the file that ships to buyers), and a root `AGENTS.md` for working inside the package repository (rules for contributors and their agents, never shipped). `core context` prints the shipped one with its generated blocks, the operation table and the package version, refreshed from the live catalog on every call. The file on disk holds the written prose and the same blocks as of the last release, so an agent without the bridge reads the operation table from the file; the two differ only in a dev project with unsaved changes. `core about` prints plain text: each installed Spellbound package with its version (read from the package manager in the Editor; a build has no package manager, so a build prints the groups and operation counts instead), the Unity version (`Application.unityVersion`) and the render pipeline in use (`GraphicsSettings.currentRenderPipeline`, or "built-in" when null). `core ledger` prints every installed package's Ledger rows, and `packagecheck check` (rule A11) fails a row that names a Unity type that does not exist.

Reaching the agent, in three independent ways, so no step depends on a copy someone forgot:

1. `spellbound_run` describes itself in the Pipeline command list, which the stock `unity-cli` skill tells every agent to read. An agent that has never heard of Spellbound is told to run `core help`.
2. `core context [--package name]` returns the written layer and the generated layer for the installed version, read from the package folder on disk. The folder is found by `PackageInfo.resolvedPath`, which serves an installed package and the embedded package under development at `Packages/<name>` alike; `core about` reads the version from the same `PackageInfo`. The first line is the file's path, for agents that read files.
3. `core context-install --target skill|agents|claude` writes a stub into the project, on request. `skill` writes one stub skill file (shown below). `agents` and `claude` write the same text as a delimited generated block into the project's own `AGENTS.md` or `CLAUDE.md`, creating the file if it is missing and replacing only the text between the two delimiter lines on a rerun, so a buyer's own notes are never touched. The stub holds no package facts and no Pipeline spelling, so it cannot go stale: it tells the agent to find the command by search and then gives the operation lines, which are the same under every Pipeline version. It is a file in the buyer's project, so nothing in it may depend on the signature of one Pipeline range. The location per client is the client's convention, which `unity skill install` already knows for its own skill. The target is an enumerated choice and not a path, so the confinement to `Assets` and `Library/Spellbound` is not widened; these three files are the only ones the operation can write outside it. The agent road as a whole needs the experimental Pipeline package; without it an agent reads `AGENTS.md` from the package folder.

### One grammar, for every area

GeoForge Pro is out of scope. Anything that is gameplay, per tick or per frame, is never an operation: operations are for people and agents, and the host reflects, parses and allocates per call.

### Telemetry and the toggle

The host reports calls, failures and duration per operation through Core's observation model (area 3 designs the model; this area only reports into it). The `OperationSettings` trace toggle logs every line, its caller and its status through Core's logger, so a playtest can show which lines ran without editing code (requirement 11). `core history` lists the lines of the session with their status, which is how an agent writes its report and its test.

### What it costs, on a server, and across ten years

- **Compile cost.** The line adds one assembly, `Spellbound.Core.Pipeline`. The line's own figures put an assembly at 0.21 s of compiler CPU without the Entities weaver and 0.81 s as the average over today's twenty-seven (`Revisited/Line.md`, from `Audit.md` section 6). Operations live in each package's existing runtime assembly and previewers in its existing editor assembly, so nothing else is added. The assembly compiles on the 6000.3 floor; the 6.3 test row runs its fixture. It removes the 18 Core console files and, with area 11, the uGUI console they feed.
- **Run cost.** Discovery reads the attribute of every loaded assembly and the types of the marked ones only; today's two scans read the types of every non-skipped assembly (`AssemblyScanning.cs:9`). A call costs a tokenise, a bind and a reflective invoke, plus the duration meter. Neither is measured; CL1's tests measure both on Corsairs' assembly set. Operations are for people and agents, so no per-frame or per-tick path may be one.
- **A server.** The catalog is process-wide and operations take a world as an argument, so a process hosting several worlds shares one catalog and no static world. A slow operation is visible because the host reports every duration through the observation model, and an operation that could exceed a tick returns a `Task` that yields. A line has a maximum length and a result a maximum size (`OperationSettings`), and Networking owns per-caller rate limits (area 6). A production dedicated server has no Pipeline (survey), so its operators reach operations through Networking's authority path, never through `spellbound_run`.
- **Ten years.** Once a package ships to customers (a game sold to players counts from its first release built on the line, with the Next Fest demo exempt; a public release of a package is undated) an operation's name, its argument names and meanings, its effect and its audience are public surface under the semantic version rule (line rule 15). The release pipeline (area 10) stores the text of `core help --all` with every release and diffs it against the last, so a removed or renamed operation is a visible major change. The status word at the start of a result is stable; the prose after it is not. The release promise to a buyer is a rule of the line (decided 2026-10-24): a major about every 12 months with the upgrade offered at a reduced cost, and inside a major a year of bug fixes and maintenance with no API break, so an operation's name and arguments hold for that year; a shipped game follows the maintenance branch of its Core major, never main.

### The in-game console and chat

The console view is UI's (area 11). It owns a text field, history and drawing; it asks the catalog for completion (group names, then operation names, then argument names, then an enum's legal values), calls `OperationHost.Run`, and draws the returned text. It owns no registry and prints nothing through a static event. Switchboard's typed commands that start with `/` run through the same host with a caller that holds `anyone`; its aliases (`/w`, `/r`, `/me`) are profile data that expands to a `switchboard` operation line before the host runs it. Both are claims on area 11. A reproducible UI test is a C# list of lines: `CoreKit.Operations.RunAll(lines, caller)` runs them in order, stops at the first result that is not `Succeeded`, and returns every result, so a test is `RunAll("ui show main-menu", "ui focus start")` followed by an assert on the text of `ui tree`. It is a method and not a script file: a file of operation lines would be a new file kind, which waits for a designer who asks for one. CI runs these tests with `unity test`.

### Moving the games over

No shims (rule 5 of `Rules.md`), no old path kept beside the new. In one change per consumer: the three attributes, `ICommand`, `CommandResult`, `CommandRegistry`, `AttributeCommandRegistry`, `ConsoleCommandRouter`, `PresetResolver`, `ConsoleModule`, `HelpCommand` and `ListCommand` leave Core; `ConsoleLogger` leaves with the console view (its static events are replaced by returned text); Chat's second registry goes with the Switchboard rename. Corsairs' 57 methods become methods that return strings (the 143 `ConsoleLogger` calls become return values); its four listing classes are deleted because `core help --group` lists everything; Saboteer's ten classes become methods; Volumetrics' three change to the new attribute; Chat's sample command is deleted. `ConsolePresetCommand` has no users, so its router goes unreplaced and `list` and `spawn` become WorldObjects' `presets` and `spawn` (a claim on area 3). Saboteer's `PoiBake.BakeFromCommandLine`, which reads `Environment.GetCommandLineArgs()`, becomes a Places or GeoForge operation so the agent and a build script call the same thing.

## Directions

**A. One operation surface, one bridge command (taken).** Every capability is an operation declared on the front door; Core's own operations are the catalog (`core help`), the context (`core context`) and the authoring flow; the Pipeline bridge is one command that runs a line. Cost: our operations do not appear one by one in `unity command`; the agent asks `core help` instead, and the first line of `spellbound_run`'s description says so.

**B. One Pipeline command per operation (rejected). An alternative to A.** Register each operation with `CommandRegistry.RegisterCommand` so `unity command` lists it with Pipeline's own schema and `batch` can chain it. Rejected for four reasons. Two grammars: Pipeline binds `--key value` to its own types while the console binds a line, so the same call can parse two ways unless the console copies Pipeline's grammar and then moves with an experimental package whose registration signature already changed between 0.8 and 0.9 (a `group` parameter was added, per the 0.9 manual). Lost descriptions: dynamic registration reads parameters off the handler and `[CliArg]` carries their descriptions, which Core (engine-only, line rule) cannot reference, so the words an agent needs would not reach `unity command` unless each operation wrote them twice. Listing flood: twenty-two packages at about four operations each put about eighty rows into every `unity command` listing. A second lifecycle: an Edit Mode registration survives Play Mode (survey) but a development build registers at start and an operation on a live object registers and unregisters with it, a lifecycle beside the catalog's own. What it would have given: schema-level validation inside Pipeline, and its `batch`. Kept as a possible later bridge feature for the five or six operations an agent calls most, if a measurement of agent runs shows the one-command shape costing tokens. The living area asked for exactly this shape (flat snake_case Pipeline commands, each taking `confirm` and `dry_run`); I keep the rejection and give it the part that does not need it: `--confirm` and `--dry-run` are enforced once in the host for every operation, and the agent learns the operations exist from the description of `spellbound_run`, from `core help`, from `core context` and from the generated block in the project's own `AGENTS.md` or `CLAUDE.md` when its owner asks for one.

**C. A program of our own (rejected). An alternative to A.** A `spellbound` executable, or a `unity-spellbound` binary on the path (the Unity CLI treats any `unity-<name>` binary as a command), that talks to Pipeline or starts a headless editor. Rejected: Areas.md allows it only "if that falls short", and Pipeline does not fall short; a second program needs installing, versioning and signing for every buyer, and it would duplicate discovery, authentication and connection handling that `unity command` already does with a loopback token. If a shorter spelling is wanted, a one-line bash alias in Studio.Tools gives `spellbound "core help"` for us without a product.

**D. A mirrored skill per package (rejected). An alternative to the context design.** Copy each package's context into `.claude/skills/<package>/` so clients load it natively. Rejected on the Unity CLI's own cost statement: every installed skill's frontmatter is loaded in every session, so twenty-two packages are twenty-two entries before the agent does anything, the copy goes stale when a package updates, and the Unity CLI mirrors only the skill of `com.unity.pipeline` (survey). Served on demand from the installed version, one stub, no drift.

### The boldest version, and why it is not on the page as the proposal

A playtest bug becomes a replayable transcript with no screenshots. The version that works is state replay, not physics replay. The recorded operation lines (`core history`, now stamped with Unity's frame count and the caller) are re-run in order by `RunAll` against the same starting assets and the same saved state, and the result is judged by each package's read-state operation ("inventory show", "worldobjects find"), so the replay proves the state the bug lived in, not the motion that led to it. Unity physics is not reproducible, and the runtime area rejected deterministic replay for that reason, so this area makes no determinism claim. The command line owns the lines half (CL1 story 11, priced). The networking area's replication journal owns the authority's batches and replays in its simulator; joining the two, so that a client's lines and the authority's batches replay together, is a claim on that area and is held until it says yes (CL9, not priced). Until then the page promises the lines half only.

## Decided

1. **The front door is `<Name>Kit`** (`InventoryKit`, `PlacesKit`, `CoreKit`), decided by the developer on 2026-10-23. Reason: a class named like its package fails to compile inside any `Spellbound.*` namespace (measured).
2. **An agent may not approve its own drafts unless one setting grants it**, decided on 2026-10-23. The approval audience is `approver`, held by the Spellbound window; the Pipeline bridge holds `developer`; the bridge's audiences field in `OperationSettings` is the one setting that can grant it.
3. **Operations are found by reflection over marked assemblies, with a gate**: CL1 story 1 checks it against Unity's notes for 6.7 and the next major under build stripping; the source generator is the fallback the developer named, used only if that story is a no-go.
4. **No compatibility of any kind before a package ships to customers**: no format version, no migration step, no `core migrate`, no `core schema` diff, no `FormerlySerializedAs`. A changed definition is re-authored. After the first ship, semantic versioning governs (item 13).
5. **A package lives at `Packages/<name>`**, after the one-story probe in area 7; `core context` finds it through its package info.
6. **The bar check is `packagecheck check`**, an operation of the Tool PackageCheck; Core has no `core check`.
7. **A package may add its own findings to a definition another package owns: yes, as the seam only**, decided by the developer on 2026-10-24. Core.Editor gets one interface (`IDefinitionCheck<T>`), one attribute and the lines of validation that find and run registered checks; each package ships its own checks in its own assembly, and Core never changes for a new package. The example the developer gave in the artifact thread is drawn on the page: `IDefinitionCheck<T>` in Core.Editor, `ReachableDepositsCheck` in Navigation's editor assembly over `PlaceDefinition`, and the `core validate --drafts` report naming both the type's own validation and the registered check. A check's findings use this area's report format: the status word first, `failed:` for a fault found in a valid call.
8. **Validation reports a stored field the type no longer has, as an error: yes**, decided by the developer on 2026-10-24. Code `core.unknown-key`, detection only.
9. **The check interface is spelled `IDefinitionCheck<T>`**, decided on 2026-10-24. It matches `IAuthoredDefinition` and `IArgumentParser<T>`; the attribute, the registered names and the report format are unchanged.
10. **No written note of a lost value**, decided on 2026-10-24. The finding carries the stored value text cut at the length in `OperationSettings`, the agent's notes say to set the new field before saving anything else on that asset, and a save clears the error with the old key. Nothing under `Library/` or anywhere else keeps it.
11. **A line that changes something runs on the peer that decides for the thing it names**, decided on 2026-10-24. Reads run where asked, and the audience `authority` means "runs on the peer that decides". The target marker, the report of it, the router seam and `RunHere` are Core's; the target source is Networking's.
12. **CL8 skips its navigation steps until Navigation lands**, decided on 2026-10-24. The scenario skips steps 7 (the reachability error), 12 and 15 until N2 and N5 land, and the report's `checks:` line shows `navigation.reachable-deposits` did not run. Navigation's check lives in `Navigation.Places.Editor`.
13. **After a package has shipped, renaming a serialized field of an authored type is a major**, decided on 2026-10-24. Semantic versioning decides; the release check fails it. The release promise to a buyer is a rule of the line.

## Limits

The authored-key scan names the assets and shows each stored value, and only until an asset is saved again, after which the old key is gone and nothing can find it, so a green report after a save proves no stale key remains and never that a value was re-entered; whether Unity keeps the key until then is CL4 story 11's first proof. It reads Unity's text form, so a project on binary serialization gets no scan.
- The gym survives the play-mode reload only because the start operation finishes before it; how the CLI reports a call made during the reload is unverified (CL2).
- Replay restores state and never motion; the joined replay with Networking's journal is held.
- Core ships no console. A project without UI has the window and C# only.

- Pipeline is experimental (0.8.0-exp.1); the bridge is one file with a version range, and area 8 tracks the package.
- The floor is Unity 6000.3. I read the 6000.4 reference for `Editor.finishedDefaultHeaderGUI` and the stripping pages; the 6.3 test row is what proves the inspector banner and the bridge fixture there.
- A package folder as a validation subject rests on Unity addressing package content by `Packages/<name>` asset paths; CL4 proves it on a fixture package before PackageCheck relies on it.
- Roslyn source generator, Project Auditor and the test runner are not decided here; the first is CL1 story 1's fallback, the other two are Living's and Workflow's spikes.
- Pipeline's runtime server exists only in development builds or with `ENABLE_RUNTIME_PIPELINE`; a release build has no command line, by Unity's design, and a development build answers only when `enableInBuilds` is on, from the same machine.
- The cost of discovery is unmeasured (CL1 measures it); a call costs a reflective invoke and a parse, so nothing per frame or per tick may be an operation.
- Reflection discovery needs `[Preserve]`; whether it survives build stripping on 6.7 and the next major is unverified and is CL1 story 1, a spike with a written go or no-go; a no-go moves discovery to the source generator, a new tool the developer has named as the fallback.
- A `Task` result completes on Unity's main thread context and Pipeline awaits it off-thread (survey); a call beyond the server's time budget must be run as a Pipeline detached job.
- Text is the result form; a tool wanting structure parses lines or reads a returned value in C#. Pipeline's own envelope sits underneath and is Unity's.
- Without `com.unity.pipeline` the console and the window still work, and an agent can only read the files, `AGENTS.md` first.
- The starting operation names per package are proposals; each owner area confirms them.
- Approval is a workflow gate, not a security boundary: Pipeline's `eval` and `run_script` run arbitrary code with the editor's rights, so the gate stops accidents and a well-behaved agent only.
- Approval moves an asset; it does not decide what is committed, which stays a person's act.
- A packed call carries only argument types Core can pack; a consumer's own parser type travels as the text line. Whether the saved bytes matter is unmeasured; the reason for the packed form is that the authority parses no hostile text for a typed call.
- Progress lines reach the console view and not the Pipeline envelope.
- A job that outlives a domain reload must be a start and status pair; a single awaited operation is lost at a reload (`connectivity.md:252`).
- A production dedicated server has no Pipeline; its operators reach operations through Networking's authority path (area 6), which this file only asks for.
- Whether a Play Mode `[UnityTest]` can `yield return` an operation run is unverified (CL1 story 2); Edit Mode tests need an `IEditModeTestYieldInstruction` that Core, which may not reference the test framework, cannot supply, so operations in Edit Mode tests are called synchronously.

- Navigation's check lives in `Navigation.Places.Editor`, compiled only when Places is installed and unseen by Places (decided 2026-10-24).

- Unity's own command-line tool and MCP server are announced as free, in closed beta, with general release "later this year" (`UnityChanges.md`, page 12). I have not read the tool's own page.

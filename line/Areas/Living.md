## Survey: what was read, and what it cost to learn

Five Sonnet readers gathered facts with file and line references (layouts, manifests and asmdefs of thirteen packages; sixteen dev projects and the BuildPipeline repo; the Release Audit and the Unity Pipeline package; every context file and the last 30 commits of five repos; tests, samples, `Resources`, statics and logging calls per package). I checked the load-bearing ones myself in source and name them where they are used. Outside systems were checked in the Unity 6000.4 and 6000.6 documentation (the floor is now 6000.3, so LV5's first story reads the 6000.3 manual for anything a rule depends on) and the Asset Store Validation Suite pages; each claim below names its source. Measured here, on the developer's machine, with `find` and `grep` (not with Unity): the twelve readable package roots hold 868 C# files and 3.34 MB of source; one `grep -l` pass over all of them for four patterns took 0.23 s wall.

What the survey found that changes the design:

- A folder under `Assets` is not a package. The 6000.4 manual defines an embedded package as one stored under the project's `Packages` directory ("Any package that appears under your project's `Packages` folder is embedded in that project", Unity manual, "Embed a package"). The earlier decided layout put the package at `Assets/<name>`, where Unity's package machinery sees nothing (no dependency resolution, no `Samples~` import button, no version define naming it). The developer decided `Packages/<name>` after a one-story probe, and the design below uses it.
- Safe Mode disables all managed code from the project and its packages, editor scripts included (Unity manual 6000.x, "Safe Mode"). The bootstrap file rule 16 asks for ("offers to install Core when it is missing") cannot run in the state a project is in when Core is missing and an assembly references it. The design below makes it work another way and says what must be probed.
- The Asset Store's own validator already checks single-package structure (22 named checks, among them Samples Structure, Package Dependencies, Documentation, Changelog; Asset Store Validation Suite 0.5), is run from an editor window and documents no command line. It does not look at a family of packages. The line's promise is about the family.
- The studio already owns one check of this kind: Saboteer's Release Audit. Its shape is the right shape and its two weaknesses are known: checks sit in a hard-coded array (`ReleaseAudit.cs:14-25`) and the report has two severities (`ReleaseAuditSeverity.cs:4-7`) with no place for a question only a person can answer.

## After: the design in ten parts

The idea in one sentence: a package declares what it is once, in one asset; everything else the line says about it (the window, the context, the dependency rules, the check, the stranger projects) is derived from that asset, the assembly definitions and the compiled surface, so there is no second place to drift.

One thing is new and is decided: the check is an editor-only workflow with no runtime, which is the Tool kind's definition, so it is the twenty-third package, a second Tool, and not a growth of Core. Name **PackageCheck**, group `packagecheck`, front door `PackageCheckKit`. Every operation below is an operation line in area 2's grammar, `<group> <operation> [arguments]`, run by the one Pipeline command (`unity command spellbound_run --line "<line>"`); a result starts with its status word (`succeeded`, `invalid`, `failed`, `refused`, `previewed`).

### 2. The declaration: `Identity.asset` and the ledger

Two ScriptableObjects, split by how often they change and who may change them. A change to either one's shape means re-author the file; nothing reads an older shape, and Core's validation reports a stored field the type no longer has as an error, so a renamed field is named and never dropped quietly. `Identity.asset` (type `PackageIdentity`, in Core.Editor because the window reads it) ships with the package. The ledger (type `PackageLedger`, in PackageCheck) lives in `Assets/_Project/Ledger` and never ships, so a buyer receives no waivers, no names and no gate records, and merges of answers do not collide with the declaration.

| Field | In | Holds | Why declared and not derived |
|---|---|---|---|
| `kind` | identity | An id string (`foundation`, `library`, `tool`, `studio`); the kinds' rules are assets in PackageCheck, Studio's in Studio.Tools | An id never dangles in a buyer's project |
| `layer` | identity | Mechanism, composer, tool or studio (rule 3's order); defaults from the kind | Not readable from code |
| `status` | identity | Active or retired | Line rule 15 retires a package whose sentence changes; the catalogue line for a retired package carries a plain note saying what replaced it, shown as text, and nothing is forwarded |
| `job` | identity | The one sentence | It is the package |
| `frontDoor` | identity | The public type a newcomer reaches first | Rule A1 checks it exists and has operations |
| `mustNotOwn` | identity | A list of nouns | Feeds the review leads and the window |
| `hotPath` | identity | True when the sentence has a hot loop | Makes P1, P4 and T5 require a budget, a probe and a no-allocation test |
| `deterministicOutput` | identity | True when the package turns a seed and a definition into data | Makes V5 require a golden test and compare its hash with the last release |

Not in either: dependencies and bridges (the assembly definitions say them), operations (the registry says them), samples (the folder says them), the version (`package.json` says it). One fact, one place. The **judgment fields** are `kind`, `layer`, `status`, `job`, `frontDoor`, `mustNotOwn`, `hotPath`, `deterministicOutput`, `simulation`, `machineMatchedJobs` and the whole ledger. They are the fields an agent could edit to make a rule pass (write a dependency into the sentence, set `hotPath` false, add a waiver). The skeleton's `CODEOWNERS` names a person for `Identity.asset` and the ledger, the pull request check prints which judgment fields changed, and a change needs that person's review. That is a control by a human reading a diff, not a lock; no technology stops a person with merge rights, and the page says so.

### 3. The bar: 78 rules, in tiers, each with a reason

Three kinds of rule, because three kinds of answer exist. A **fact** the machine decides and blocks. A **lead** the machine finds and a person or agent answers (the answer is stamped and holds until its subject or the rule changes). A **gate** only a person can give. Three tiers, because the cost differs by orders of magnitude: **read** (files and the loaded assemblies, nothing runs), **run** (tests, samples and snippets execute), **line** (the strangers; only the whole line can say). Every rule has a **revision** and a **maturity**: a new rule is Advisory for one minor release of PackageCheck (it reports as a question and blocks nothing), then becomes a fact; I7 stays Advisory by design. "Why" cites the requirement, line rule, Homes smell, Asset Store check or audit finding that makes the row necessary; a rule with no source is deleted.

A rule that is not a text scan overrides `Check` and reports through the report:

```csharp
public sealed class BridgeHasBoundedRange : LineRule {
    public override string Identifier => "D3";
    public override RuleTier Tier => RuleTier.Read;
    public override RuleDecision Decision => RuleDecision.Fact;

    public override void Check(PackageUnderCheck package, LineReport report) {
        foreach (AssemblyDefinition assembly in package.Assemblies) {
            foreach (VersionDefine define in assembly.VersionDefines) {
                if (!define.Range.IsBounded)
                    report.Fail(this, assembly.Path, define.Line, "The version range is open or empty.",
                        "Name the range this bridge was written for, for example [1.2.0,2.0.0).");
            }
        }
    }
}
```

`RuleTier`, `RuleDecision` and `RuleMaturity` are open id sets (a readonly struct with named defaults), not enums, so a studio adds a "nightly" tier without editing the package. `AssemblyRole` comes from a classifier with a replaceable default: Editor, Tests, Samples and Bootstrap by name; Bridge when `versionDefines` exist; Presentation when the assembly's source names a type from a configurable list (the UI Toolkit runtime, the render pipelines, cameras, renderers, audio sources, canvases) or it already carries `!UNITY_SERVER`; **Simulation only when the identity declares the assembly**, so a character or tween package is not held to the no-clock rule by default. Every extension point (`LineRule`, the classifier, the surface writer, the report sink) has a default and a test that swaps it, as the library-design skill asks, and every rule ships a failing and a passing fixture package. These are shapes; names are placeholders until the boundary sheet.

Today a check is a class, an entry in a hard-coded array, a menu item and a build hook (`ReleaseAudit.cs:14-30`, `ReleaseAuditBuildHook.cs:10-37`). Under the design a check is one class.

On 6000.3 and the studio's editor (6000.4 today): every bridge pair compiles together at latest and at the floor of its range; the previous release of each package compiles against the new Core; the window's plan, run over a project holding the previous major of every package, offers no Core major until every installed package has a release for it; the tests each bridge ships run (ArtPipeline.Character compiles with Character at its latest, and the rig contract asset's `version`, a plain serialized integer read from the asset's text, is inside the range the bridge declares; the project serialises as Force Text, as the template sets it); the bridges to Unity features newer than the floor compile at the floor; the depth chain is measured; the known-good set of each supported major is written, each into its own catalogue lines; the cost of a second set during the overlap year is unmeasured and LV5's first story measures it |

Each project writes a **cost card** per package it installs, from Unity's own build profile (`Library/Bee/fullprofile.json`, the file Audit section 6 read): assemblies, compiler CPU, post-processor CPU, finish time. The gate is structure, which is stable: the same assembly count and the same chain length as the last release on the same editor. CPU is a trend, because a shared runner moves a 0.4 s figure more than any tolerance could hold. A package with a hot path also ships a **probe**, an operation that runs its hot loop at a fixed size and returns its observations; the line tier compares them with the declared budget and with the last release on the same machine (P4). The observation model is area 3's and the load shape area 6's; this area only runs them.

What the cost is not yet known: the Audit measured a rebuild from a cleared Bee cache on a 16-core machine (20.4 s and 35.4 s), not a cold Library on a hosted runner. First import, the Dedicated Server build, the size of a cached Library per project and the runner type are measured in LV5's first story, and until then "minutes" is a hope. L1 helps: Core no longer references Entities, so a stranger's Spellbound assemblies can start at the 6.4 s mark instead of 27.9 s in the Audit's Corsairs figures. A tag in one package runs only the strangers that install it. Because the Unity tiers run on the developer's machine, the hosted-runner questions (cold Library, cache size) no longer gate a push; they remain open for any later hosted run.

**Editors.** The floor is 6000.3 (line rule 5). The studio edits on its current editor (6000.4 today) and moves to 6.7 when it ships; no epic waits for that move. The strangers and the Matrix run on 6000.3 and the studio's editor now (the 6.3 test row, where Burst and Mathematics are still packages), and from the 6.7 move the push gate also compiles every package at the floor, a job switched on by the studio editor's version and not by a date. Two canaries run nightly and are allowed to fail: the 6000.7 beta, and the 6.7 experimental CoreCLR player, so the studio learns what 6.7 will break before it is the floor (`Unity.md` U8). A second editor doubles the cached Libraries; LV5's first story measures that. The floor compile (from the 6.7 move) and the 6.3 test row are local gate jobs: `run-local-tests.sh` on the developer's machine drives the Unity CLI on those editors and posts the statuses (area 10); neither is a hosted-runner job. They cover the bridges to Unity features newer than the floor, which compile at the floor with the feature absent.

A package is not finished until a stranger that installs it passes (L1). That is how requirements 2 and 3 are enforced on every change and not argued once. The six strangers are the ones `Games.md` imagines; a seventh kind of game is a manifest added to the folder.

### 8. Samples, the first hour, and the sample loop

`Samples~` is the source in every repo and a game never compiles it. A git consumer receives the repository as it is, so the tilde is what keeps a sample out of the compile; a define constraint on a visible `Samples/` was considered and refused, because the files would still import, show in the project window and need `.meta` files, and the Asset Store validator wants `Samples~` anyway. `core sample-import --package TetherShop --sample Rope` copies it to `Assets/Samples/<display name>/<version>/Rope`, the path Package Manager uses for its own Import button (Unity scripting reference, `PackageManager.UI.Sample.importPath`), because the Unity CLI has no sample import (Pipeline 0.8, Line rule 8). The first hour (requirement 9) is three machine-checked steps and one human one: the README install lines work and its snippet runs in a fresh stranger project (A5), the sample imports and runs 10 s without a console error (S3), the sample uses only public surface (S2). ### 9. The Spellbound window, the catalogue and the bootstrap

The window lives in Core.Editor (`Window/Spellbound`), plain UI Toolkit with named slots and USS custom properties so UI.Editor can skin the window and the four shared controls without Core.Editor ever referencing UI (area 11, LV6). Pages are found by `TypeCache`, so PackageCheck adds the Check page without Core knowing it. It never opens a modal. Its words are plain: a failed fact is "must fix", a lead is "please confirm", a gate is "needs a person"; fact, lead and gate are for the docs.

| Page | Shows | Does |
|---|---|---|
| Line | Every package of the line from the public catalogue: kind, job sentence, installed version, the known-good version, retired with its note; starter sets (the imagined strangers as buyer-facing "I am making a farming game") | Install or update a package through `PackageManager.Client.Add` with a git URL, a path and an exact tag, or, in a project set to follow a branch or a maintenance branch, that ref (see Install and Three modes below); offer a Core major only by the plan below; install a starter set |
| Package | Job, kind, layer, hard dependencies, bridges with whether each is active now given what is installed ("Inventory.UITK: active, UI 0.3 found. Networking bridge: inactive, install Networking to enable"), operations, samples | Import a sample, open the docs, copy `core context` for an agent, add notes for agents to the project |
| Operations | Every operation in the registry of the installed packages, with description, effect and audience (Core.Editor supplies the content) | Run one with arguments; copy it as a command line |
| Drafts | The definitions an agent or a designer authored and nobody approved yet, with Core's validation report beside each (Core.Editor supplies the content) | Approve or discard |
| Check (dev projects with PackageCheck) | The 78 rows grouped, red and amber | Open file at line, scaffold or fix, answer (one or all current hits), baseline, waive, record a gate |

**The catalogue** is one public text file in a public repo (`Catalogue.txt`), not an asset in Core, so adding, retiring or renaming a package never needs a Core release. One tab-separated line per package and per supported Core major (id, name, kind, status, note, job, install address, known-good tag, the Core range of that tag), so a package has two lines while two Core majors are supported and one afterwards, one per starter set, and one per third party the line names (kind `thirdparty`, with the install address and the tested range in place of a Core range; PurrNet is the first); there is no store column until a listing exists. The window fetches it asynchronously, caches it, draws the cached copy offline, and Core ships the last copy as the fallback. In tag mode "update available" compares an installed version with the known-good version on the line of that package whose Core range admits the installed Core, so a buyer on Core 2 is offered the newest Core 2 tag and never a tag that needs Core 3, so opening the window makes no tag query, except for Core, which follows the plan below; a package's "other versions" list runs `git ls-remote --tags` for that one address, once, when asked. A line of kind `moved` (old address, new address, a plain note) is the answer to a catalogue that has left its address: the window follows it once, keeps the new address in the editor's per-machine settings, says so in plain words, and never follows a second `moved` in the same fetch, so a loop is impossible. This works while something still serves the old address (a stub with one `moved` line). It cannot work if the old host is gone, and that is accepted: the studio never leaves GitHub, so the window fetches the package list from GitHub for good and the studio owns no address of its own (decided 2026-10-24). Until the first customer ships, the address inside Core is ours to change in any release. The release pipeline (area 10) writes the line at the final tag, running as the organisation's GitHub App. The known-good version of each package, for each supported Core major, is the set the Matrix last passed together for that major: a project in tag mode, which is every buyer's, gets the set of its own Core major. A backported fix is a new final tag cut from `release-<major>`; when the strangers pass on that major's set the release Action rewrites that package's line for that major and leaves the lines of the other major alone, so a fix for Core 2 never moves a Core 3 buyer and a Core 3 tag never moves a Core 2 buyer. The line for a major is removed when its maintenance branch is dropped, one LTS cycle after the next major (line rule 15). A project in tag mode moves to the next Core major only by the plan below, and a game of ours that follows a branch is not bound to it.

**What the window offers for Core, and what holds it back.** A Core major is a release of the whole line (line rules 15 and 17), and each package reaches a project when its own tag for the new Core exists, so a project can hold a package that has not moved yet. So the window never compares Core with one version. It builds a plan from what is installed:

1. For each installed Spellbound package it reads the Core range from the package's own constraint on Core (D8 makes it one bounded range per package, read from the assembly definitions under the package's `resolvedPath`). A package with no readable range holds Core at its installed major, and the window says so.
2. It intersects the ranges. The newest Core the project can take is the newest Core in the catalogue inside the intersection. A minor or patch of the installed major is always inside it, because a range is `[floor,nextMajor)`.
3. If the catalogue's Core is a major above that, the window offers nothing for Core and names what holds it back, in plain words: "Core 3.0 is out. Inventory 2.4 and Modifiers 2.1 were built for Core 2 and have no tag for Core 3 yet. Update them here when their tag for Core 3 appears; then Core 3 appears here."
4. If every installed package already has a tag whose range admits the new major, the plan is one step: those tags and Core, applied together in one `Client.AddAndRemove` call so the project never compiles half-moved (the scripting reference lists the method; LV6's first story confirms it takes git addresses). Otherwise the plan is empty and the window explains.
5. A package update whose Core range does not admit the installed Core is offered only inside the same plan, never alone.

The window reads only what is installed; when a package is updated its range changes and the window plans again. The plan is a pure function of the installed ranges and the catalogue, tested in edit mode with fixtures: a project on Core 2 with packages at 2.x and a catalogue at Core 3 offers nothing and names the holders; the same project with the packages at 3.x offers one step; a catalogue with a Core 2 and a Core 3 line for a package, and a new Core 2 fix tag, offers the fix to a project on Core 2 and nothing to a project on Core 3. The bootstrap's compile-out of an assembly whose range excludes the installed Core stays as the last defence, and the plan exists so a buyer does not reach it by pressing "update".

**Pages are found by an attribute.** A page is a class marked `[WindowPage]` with a title and an order, found by `TypeCache`. Core.Editor registers Line, Package, Operations and Drafts, PackageCheck registers Check, UI.Editor registers the Console and Gallery tabs (area 11), and Networking.Editor registers the Networking page, which says PurrNet is missing and offers `Client.Add` with the address and tested range from PurrNet's catalogue row after the Git check (area 6). No package edits the window and Core never learns UI's or PurrNet's name. The window shell is the first story of LV2 and builds on the shared editor controls in Core.Editor that area 11 decided.

**Install.** The call is `Client.Add("<url>?path=/Packages/<Name>#<tag>")`: the path comes before the hash, git dependencies are declared only in a project's manifest and never in a package's `package.json`, and they need a Git client 2.14.0 or later on the PATH (Unity 6000.4 manual, "Git dependencies", as `Workflow.md` records). The window runs `git --version` first. With no client found it says so in plain words and names the one thing to install; nothing else can be done from inside Unity. It does not need Git LFS: no file a package ships is in LFS (rule I4), because a Git client without an LFS client checks out the pointer file where the texture or model should be, and Unity imports that as a broken asset with no message from us. LFS stays for the dev project's own `Assets/_Project`, where only the studio works. Whether Unity's own fetch honours LFS is not documented in what I read, so the design does not lean on it; LV1 story 2 runs the clean install with Git and no LFS client. Every package installs this way; there is no second route until a listing exists (undated, after the two games). `package.json` `version` is written only by the release (V6).

**Three modes, one committed setting.** The window reads one project setting saved in the project, so every person in it has the same (a `ScriptableSingleton` under `ProjectSettings`, Unity's own mechanism; the exact name is read from the scripting reference and LV6m's first step confirms it). **Tags**, the default and every buyer's mode: the window installs the catalogue's known-good tag for the installed Core major, a released version (the line ends `#v<version>`, for example `#v0.1.0`), and the project changes only when the buyer presses Update to a newer known-good tag. **Branch**, for a project the studio works in while a game is in development: the window writes `#beta` before a package's first stable release and `#main` after, and Update re-adds the line so Unity moves the lock file's commit (`Workflow.md`: Unity records the commit hash and moves it only on a new `Client.Add`); the known-good tag is shown beside the line as advice and never written. **Maintenance**, for a shipped game: the setting names the Core major the game shipped on and the window writes `#release-<major>` for every package of the line (decided 2026-10-24: a shipped game follows the maintenance branch of its Core major, never main). Fixes to a major land on its maintenance branch, and the previous major's branch is kept for one LTS cycle (line rule 15). The window cannot say a branch has moved without a network query, so a following line shows its installed commit and Update is always offered; whether the package manager exposes that commit is confirmed by LV6's first story.

**The bootstrap** (rule 16) cannot be code that runs after the damage. If a package is imported without Core and its assemblies reference `Spellbound.Core`, the project has compile errors, and in Safe Mode no managed code from a package runs (Unity manual 6000.x, "Safe Mode"). So every assembly that references Core is constrained on a define that exists only when Core is installed (`SPELLBOUND_CORE`, from a version define on Core's package id), the optional-assembly mechanism `Spellbound.Chat.UIIntegration` already uses for UI; with Core missing those assemblies do not compile, so no compile error follows. The `Bootstrap` assembly has no references and no constraint, so it compiles anyway. Its one class opens a non-modal window, once per editor session across all packages (one shared session key), and writes one console line carrying the install command an agent can read. Core's location is not code: it is an address in a one-line text file beside the class, which points at the catalogue, which names Core's install address, so a moved repository is a data change and not 22 republished packages. Once a package has shipped to a customer it keeps the address it shipped with; that is a limit, said so. The first install of Core for someone who has never seen the line is the public git address in the README of every repo (a store listing is an undated story after the two games). Each bootstrap is one more assembly: priced from the Audit's 0.2 to 0.8 s of CPU per assembly, 21 of them are 4 to 17 s of CPU, mostly off the critical path on a 32-thread machine and 2 to 4 s of wall on a 4-vCPU runner; LV1's probe measures the real delta. This is a probe, not a fact: LV1's second story installs a package without Core in a clean 6000.3 project and a clean 6000.4.8f1 project with no studio credentials and records whether the window appears, no error shows, and Core can be fetched.

**The release promise.** A rule of this area, enforced by the checks that already read the surface. A buyer holds a released tag from the catalogue. The line makes a major about every 12 months; a buyer on the previous major is offered the upgrade at a reduced cost; and inside a major there is a year of bug fixes and maintenance and no API break (decided 2026-10-24). The enforcement has three parts. A pull request to a `release-<major>` branch runs V3's compare and fails any removed or changed public, stored or serialized line whatever its title says, and refuses a title carrying `!` there, so the only changes that merge there are fixes and additions. The tag gate (LV7b) refuses a final tag whose major differs from its branch's, or whose surface differs from the previous tag of that major by anything but additions. A breaking change lands on `main` and ships in the next major, never on a maintenance branch. The cadence is a line of the release calendar (the workflow area), a target the studio plans around that no check fails; the reduced price is a term of the listing, which is undated with the listing, and no machine checks it. The maintenance branch is named for the Core major (`release-2`) in every repo of the line and is cut when that Core major's tags are made. A fix reaches a buyer through the catalogue: the final tag cut from the branch becomes that package's known-good line for that Core major once the strangers pass on it (section 9), and tag mode offers it as an update to every buyer on that major.

**The release scan.** Before a final tag, and before a game's release build is uploaded, `packagecheck release-scan --path <folder>` reads the first line of every text file the release ships (assets, prefabs, scenes, materials and the other Unity text formats) and fails the release when a line starts with a `%UNITY` directive newer than the oldest supported editor writes (decided 2026-10-24). Unity's 7000.0.0a12 notes say a version directive makes an earlier Unity report an explicit error, and a second entry says text files no longer start with a `%UNITY 7.0` line so Unity 6 can open them again (`Unity.md` S51); the page gives no order, so the scan does not guess: it compares against the value the Unity area's re-save test records for the floor editor, and an unreadable line is a `failed:`. Measured on 2026-10-24 with `find`, `xargs`, `head -n1` and `grep` over the eight readable package roots: 732 text files, none starting with `%UNITY`, 0.6 s wall. A Place asset a package ships is a shipped text file and falls under the scan, with a fixture for a Place saved by a newer Unity. The scan is a read-tier text match, so `check.sh` can carry it too.

## Directions

**A. Declare once, derive the rest, prove with strangers (taken).** The identity asset plus the assembly definitions plus the compiled surface are the only inputs; the window, the context, the dependency rules, the check and the strangers are views of them. The cost is a new Tool package, a new test-bed repo and 78 rules to keep honest, which fixtures, cited sources, revisions and the advisory stage are there to bound.

**B. A written checklist run by a person or an agent (rejected).** The library-design skill's `review.md` is exactly this and it has not prevented the drift the audit found in one read: nine of thirteen manifests wrong, seven sample folders leaking into consumers, five packages without tests. A checklist depends on someone remembering to run it on a package they are not editing. It stays as the source of the Code rules, which a machine now runs. Alternative to: the bar.

**C. Rely on Unity's validators and Roslyn analyzers (rejected for now).** Unity's Asset Store Validation Suite already checks single-package structure (22 named checks), and analyzers would give squiggles in the IDE. The suite runs from an editor window with no documented command line and does not see a family of packages; analyzers need a build chain and, to be useful, Microsoft.CodeAnalysis, a third-party library the rules forbid adding without a decision (Rules.md 4), and a prebuilt DLL labelled `RoslynAnalyzer` (Unity manual, "Roslyn analyzers"). Kept: the validator is gate G3 at release, by hand. Revisit when text scans produce more false positives than a baseline can carry; Unity's own Project Auditor, and not Roslyn, is the path, behind a probe with a written go or no-go (decided). Alternative to: the code rules and the structure rules.

**D. One monorepo with every package in one Unity project (rejected).** It would give "everything installed together" and one CI for free. It breaks requirement 17 (one dev project per package), the decided one-repo-per-package, and Asset Store publishing, which wants one product per package folder whose name matches its manifest (Line, "Studio: one package or several"). StrangersDev's Matrix gives the monorepo's one benefit without it. Alternative to: StrangersDev.

**E. The check inside Core.Editor (rejected as the default, kept as the fallback).** It stays inside the approved line and needs no new repo. It gives Core 73 rules no library needs, breaks Core's rule 4, and leaves a stranger with Core's assembly for a job that has no runtime. Alternative to: PackageCheck, which is decided.

## Limits

- The serialized-field section rests on the authored-key scan's enumeration of serialized property paths, which CL4 story 11 proves for plain fields and managed references; a type whose fields only exist at runtime through a custom serialization callback is not seen.
- The read tier's run time in C# is unmeasured. The 0.23 s figure is `grep -l` over 868 files and 3.34 MB and bounds file I/O only; it does no tokenising, parsing or reflection. LV2's last story sets a budget from a measurement on the largest package.
- The stranger projects' run time, a cold Library on a hosted runner, the cache size per project and the Dedicated Server build time are unmeasured; "minutes" is a hope until LV5's first story reports them. The 20.4 s and 35.4 s are a rebuild from a cleared compile cache on a 16-core machine.
- The bootstrap and `Packages/<name>` with the repo, git and Git LFS inside are read from documentation and unverified in a project; LV1 stories 1 and 2 are the probes. Once a package ships to a customer it keeps the address it shipped with.
- Each bootstrap is one more assembly: an estimated 4 to 17 s of CPU for 21 of them, unmeasured.
- A commit status posted from the author's machine is self-attested: the status carries the commit and the report's hash, but nothing stops a person from posting it by hand. That is the cost of not running Unity on a hosted runner; the author runs the tests before review by decision, and a protected main branch makes the status required, not true.
- The shell subset and the C# rules can drift; the shared fixtures catch it only for the rules that have a fixture.
